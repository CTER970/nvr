### Q: event_bus 的回调(on_event)跑在哪个线程上下文?为什么必须快速返回?
- **一句话**: 跑在**发布者线程**(cloud_ai 的 AI 线程)——publish 在 c:176-178 **同步**逐个调用 cb,控制流从未离开调用者线程;同步调用=调用者等 cb 返回,回调里做耗时动作(网络/sleep)就是拖住 AI 线程的采样循环;所以契约规定回调只做「登记+踢线程」,耗时动作放自己的线程——与中断上半部不能睡眠同一条因果。
- **要点**: ①回调=把「做什么」作为参数交出去,由对方在恰当时机调用(控制反转;库调你,不是你调库);②调用发生时 g_lock **已释放**(c:174 解锁在 c:176 调用之前);③项目模范=alarm:on_event 当场读 type/confidence→锁内置 g_pending+cond_signal(c:80-83),响铃延时全在 alarm_thread;④想在回调里发短信(网络数秒)→必须沿用「留记号+踢线程」模式,先建消费者线程再订阅。
- **不这样会怎样**: 回调里同步发短信 5s→AI 线程 5s 不采样、检测停摆;若还持锁调用→死锁(见下一卡)。
- **源码**: `event_bus.c:169-178`;`alarm.c:76-86`(on_event 只登记)、`126-129`(先建线程后订阅);`event_bus.h:18`(契约注释);`cloud_ai.c:277`(发布点)。
- **状态**: 2026-09-01 首次通过(L2)
- **关联**: 06 锁设计卡;2.3B(alarm 线程侧);C2(条件变量=「踢线程」的接收侧)

### Q: publish 为什么要「锁内拷贝订阅数组,解锁后再调用回调」两步?
- **一句话**: 把临界区压成纯数据复制(栈上抄 8 个指针,纳秒级),执行任意回调代码移到锁外——三个理由:防死锁(回调可能反调 event_bus_*,要拿同一把锁)/锁时长有界(契约只能约定、不能保证回调快)/迭代稳定(在副本上遍历,不受并发 subscribe 改动原数组影响)。
- **要点**: ①c:170-173 拷进栈上 cbs[8]/users[8] 并读走 nsub——**拷贝/快照**,不是替换,总线原数组不动;②c:174 解锁;③c:176-178 对副本逐个同步调用;④回调是「别人的任意代码」,持锁跑未知代码=锁占用时长听命于订阅者的代码质量,Web 查询线程(也抢 g_lock,c:228)和别的发布者全被拖住。
- **不这样会怎样**: 持锁调用→回调里再 publish/query→非递归互斥锁当场死锁(publish→回调→publish→等一个永远不释放的锁);即使不死锁,一个慢回调也拖住所有抢锁者。
- **源码**: `event_bus.c:169-178`;对照同函数 c:145-167 快照文件 I/O 持锁(2.3A 审计①,「慢 I/O 出锁」没贯彻到底的对照)。
- **状态**: 2026-09-01 首次通过(L2)
- **关联**: 06 回调线程上下文卡;2.3A 审计①

### Q: ai_fps 配置的实际采样率由什么决定?为什么配置会「形同虚设」?
- **一句话**: 实际周期 = 云处理耗时 + interval_us(cloud_ai.c:311 串行处理完才 c:314 usleep)——串行结构里 usleep 只是**间隔下限**,不是周期控制器;云耗时主导一切,采样率=1/周期。
- **要点**: ①V1 演算:云耗时 8s、ai_fps=5(interval 200ms)→8.2s/张≈0.122fps,只有配置意图的 2.4%(缩水 41 倍);云 5s、ai_fps=1→6s/张;②代码注释自述「只做上限节流」(c:313)——保证的是「两次处理**至少**间隔 interval」,不是「每 interval 处理一次」;③普遍现象:串行管道吞吐由最慢环节决定,**配置声明≠运行实然**;④想真达 5fps 需并行处理+队列,那正是 NVR 放弃的(见最新值语义卡)。
- **不这样会怎样**: 配置界面上写 5fps、用户以为每秒看 5 次,实际 8 秒才一次——审计/演示时必须用实测周期说话。
- **源码**: `cloud_ai.c:302`(interval 循环外算一次)、`311-314`(串行+节流)。

### Q: 为什么 AI 消费者不需要任务队列?被跳过的中间帧去哪了?
- **一句话**: frame_grabber 是「最新值单槽」不是队列——丢中间帧发生在**两道不同闸门**:生产节流丢「成本上不值得编码的帧」(emit 开头按 target_fps 挡,决定多少帧变成 JPEG),单槽覆盖丢「逻辑上已被取代的帧」(新 JPEG 逐张覆盖 g_jpeg 旧值,AI 取到的是取用瞬间最新一张)。
- **要点**: ①监控场景只关心「现在」,最新值语义用 O(1) 内存换掉整条队列;排队处理=涨内存+报警滞后几秒+云耗时主导下必然积压;②`ai_max_queue` 在 conf 解析保存但 cloud_ai.c 零消费(grep=0)=幽灵字段,「可配置≠已消费」(1.8 核对表结论的运行侧证实);③AI 线程一生最多同时持有 1 张 JPEG(串行:取→处理→free);④web/AI 两个消费者各取各的 malloc 拷贝,可能同张也可能一新一旧——B/C 链路在 get_jpeg 调用点分叉。
- **不这样会怎样**: 换成队列:ai_fps 远小于生产帧率时队列必溢出,还得加丢弃策略——绕一圈回到「只要最新」。

### Q: 慢云请求为什么不拖累录像?多线程到底共享什么?
- **一句话**: 同一进程内所有线程**共享同一个虚拟地址空间**(代码/全局/静态/堆/fd 全在一锅),各线程私有仅栈+寄存器+errno——隔离靠的不是地址空间而是**所有权纪律**:AI 线程与录像的共享清单只有 g_jpeg/g_jpeg_size/g_lock 三样,且持锁纳秒级、出锁即深拷贝断连。
- **要点**: ①取帧走 get_jpeg 锁内 malloc 深拷贝,出锁后 AI 手里是与录像**零指针别名**的独立块(b64/请求体/响应全自建);录像的 AVPacket/AVFormatContext/err_count 零共享;②堆是共享的——AI 越界写污染的是相邻堆块,炸的是整个进程,不是只炸自己;③「多线程共享什么/不共享什么」是面试原题,别答成「地址空间隔离」(那是进程间);④共享才需要同步——g_jpeg 单槽+g_lock 的存在本身就是地址空间共享的证据。
- **不这样会怎样**: 共享清单变长(如直接传内部指针)→慢消费者拖快生产者、悬垂/UAF 跨线程伤人。
- **源码**: `cloud_ai.c:289-317`(AI 线程全循环);`frame_grabber.c:192-205`(锁窗口)。
- **状态**: 2026-09-03 首次通过(2.1;初答「地址空间隔离」已当场纠为「别名隔离」)
- **关联**: 06 回调线程上下文卡;06 get_jpeg 契约卡(同一次推演)

### Q: get_jpeg 两条失败路径的输出参数契约为什么不完整?调用方漏初始化会怎样?
- **一句话**: 路径1(无图,c:193-196)显式 `*out_data=NULL`;路径2(malloc 失败,c:198-201)**不写输出直接 return 0**——输出参数处于未定义态,全靠调用方预初始化(cloud_ai.c:304 `jpeg=NULL`)兜底;漏初始化:首轮读栈残留垃圾→free 野指针(glibc abort 或无声堆损坏);第二轮起残留上一轮已 free 的地址→悬垂→double free。
- **要点**: ①free 语义:只归还堆块所有权,**不清零内容、不改指针变量**——UAF 读到旧数据、悬垂指针皆源于此;free(NULL) 合法空操作,故 `if (jpeg)` 是防御性冗余;②可迁移读码法「输出参数契约四问」:成功路径写否/每条失败路径写否/不写时调用方读到什么/调用方初始化否;③「删一行」思想实验=验证所有权理解最快的试金石。
- **不这样会怎样**: (本卡本体即反事实推演)——「free 拿到的只是地址值的拷贝,根本改不了调用者的变量」,free 后要自己置 NULL,free 不代劳。
- **源码**: `frame_grabber.c:190-207`;`cloud_ai.c:304/306-309`。

### Q: cloud_ai 的失败 return 怎么分层?判据是什么?
- **一句话**: 按「通信在哪一层断」自下而上四层——传输层(!resp:curl 没走完,DNS/TCP/TLS/超时)/HTTP 层(≠200:事务完成但状态行报错)/协议结构层(!model_text:200 但信封 schema 不合法)/业务语义层(!json_str+none:信封合法内容违约,none 是合法应答非失败)——判据**「谁定的契约」**:信封归 API 规范、内容归 prompt;b64/body 的 malloc 失败是**第 0 层本地资源失败**(一个字节还没上路)。
- **要点**: ①分层的价值=每条路径接对处置:传输层退避重试、HTTP 层分流(401 换 token/429 退避/5xx 重试)、协议结构层告警不重试、业务语义层调 prompt;②**OOM 伪装传输层**:write_cb realloc 失败返回 0→curl 以 CURLE_WRITE_ERROR 中止→从 !resp 出口现身,需看 CURLcode 区分(回调契约:返回值≠接收字节数即中止);③**唯二无日志静默 return**(c:248/251):b64_encode/build_request_body 内部零 LOG,线上最易漏诊;而 256 !resp 外层静默但下层 c:237 已发声——「这层静默」≠「全程静默」;④**第七条失败路径无独立 return**:括号配平但 JSON 非法(单引号 key)→parse_event_json 返 -1→else 分支(c:282-284)。
- **不这样会怎样**: 不分层=所有失败一个处置:语义层失败也重试→烧 token;OOM 伪装传输层→盲调网络参数治不好内存病。
- **源码**: `cloud_ai.c:248/251/256/261/266/270`(六 return)、`52-64`(write_cb)、`237`(传输层日志在下层)、`282-284`(else 路径)。

### Q: 等待循环为什么是 while 不是 if?谓词里两个条件各挡什么?
- **一句话**: `cond_wait` 返回只表示「该重新看一眼条件」,**不表示「条件成立」**——虚假唤醒(OS 允许没人 signal 也醒)与醒来时谓词已被改变/消费都存在,必须回循环头复验;谓词两半各挡一路:`g_pending==0` 是业务条件(没事接着睡),`g_running` 是**停机通道**(alarm_stop 的 signal 靠它把线程送出循环而非接着睡)。
- **要点**: ①POSIX 契约显式允许 spurious wakeup,if 版醒来不复验=直接往下取脏值;②本代码 if 化侥幸能跑=「外层 `while(g_running)` 补考+101 行 `wait_s<=0` continue」**双兜底**,是巧合不是设计;多消费者/谓词一复杂必出事;③取号叫号模型:被叫醒=抬头再看一眼屏幕,不等于「到你了」;④「取走清零」必须锁内:读-改-写与 on_event 的写竞态,挪锁外清零可能覆盖掉新触发。
- **不这样会怎样**: if 版+谓词只写 `g_pending==0`:stop signal 醒来→查 pending==0 成立→接着睡→pthread_join 永等(线程退不出去);虚假唤醒直通→取走 0 空转一轮(侥幸)或脏值。
- **源码**: `alarm.c:95-97`(谓词+wait)、`98-99`(锁内取走清零)、`101`(兜底 continue)、`144-146`(stop 的 signal)。
- **状态**: 2026-09-06 首次通过(C2;找茬+闭卷骨架,「双兜底侥幸」为学生自主判定)

### Q: 丢失唤醒(lost wakeup)怎么发生?怎么焊死?
- **一句话**: 丢唤醒有且只有两类窗口——①消费者「查完谓词到睡下」有缝(查谓词不持锁进 wait);②「signal 与写谓词」之间消费者能插入(signal 或写谓词至少一个在锁外)——焊法=`pthread_cond_wait` **持锁进**(锁内查谓词+原子【放锁+入睡】)+生产者**锁内先写谓词再 signal**。
- **要点**: ①signal **即焚**:只作用于已挂在等待队列上的线程,响时没人在床=消失不排队;谓词**持久**:g_pending 就位后 signal 丢失无害(迟早查到)——所以规矩的根子是「让谓词先就位、让睡下无窗口」;②wait 内部「放锁+入睡」必须原子,否则通知在挂上队列前响过→睡死;③**反证**:若 wait 不放锁→生产者卡在 lock、消费者睡在 wait 等铃——消费者等铃、生产者等锁,互为死锁对(circular wait);④「锁内先 signal 后写」碰巧安全(消费者醒来必先抢锁,拿到的已是新值)但属依赖隐晦前提的侥幸——规矩仍写「谓词先行、铃声殿后」。
- **不这样会怎样**: V2 交错(无锁查谓词):消费者读谓词见 0→生产者写 5+signal(队列空,铃蒸发)→消费者才躺进 wait→终态 g_pending=5 却永睡到下一个事件。
- **源码**: `alarm.c:80-83`(锁内先写后铃)、`95-97`(持锁进 wait)。
- **状态**: 2026-09-06 首次通过(C2;V2 交错独立构造,「互为死锁对」反证为填空任务亮点产出)
- **关联**: 06 while 谓词卡;C1 V2(栈帧);2.3A(publish 侧锁模式同宗)

### Q: 为什么快照路径必须靠第二次 UPDATE 补?不能 INSERT 一次带全吗?
- **一句话**: 快照文件名是 evt_<id>.jpg,而 id 是 AUTOINCREMENT 在 INSERT step 那一刻才由 SQLite 分配的——真路径依赖 id→id 依赖这次 INSERT→INSERT 又想带真路径,**因果成环**,只能先插行拿 id(last_insert_rowid)、再写文件、再回头 UPDATE 补路径。
- **要点**: ①这不是两段写「写错了」,是自增键策略下的必然;②换键可解:应用侧生成键(时间戳+序号/UUID)在 INSERT 前就已知,路径可预先拼出,一条 INSERT 带全字段、UPDATE 整段消失——代价是自己保唯一性;面试口径「AUTOINCREMENT 把键生成推迟到插入时刻,任何依赖键的外部资源(文件名)都被迫先插后补」;③两段写=两个独立提交(autocommit),掉电掉在窗口内→库路径永空;同一症状(空 jpeg_path)三种病因:UPDATE 败/掉电窗口/快照败——排查同形。
- **不这样会怎样**: 硬要一条语句带真路径→只能预先猜 id(竞态)或改键策略;接受两段写→要认非原子窗口的存在。

### Q: 快照存失败有几种形态?可观测性为什么说不完整?
- **一句话**: 三种形态三级可见性——fopen 失败**零日志纯静默**(行在库、路径空串,唯一 WRN 挂在短写分支不归它);fwrite 短写**有 WRN 可观测**但留孤儿半文件(fclose 照常、无 remove);UPDATE 失败**零日志静默**且造成**三方分裂**(内存有路径/盘上真有图/库里无记录)——web UI 空缩略图是最晚暴露点,且与 fopen 败同症状,「两种病一个症状」无法归因。
- **要点**: ①失败可见性要分级:返回值失败(cloud_ai 日志 id=-1 留痕)/部分失败(短写 WRN)/完全静默(fopen、UPDATE)——同一功能内三级并存=边界处理不一致的反面教材;②UPDATE 静默的根源:c:158 step 返回值无人接(prepare 查了 c:155);③「DB 败日志留痕 id=-1 vs fopen 败无痕」对照;④修法候选(动手池):fopen 失败补日志、短写 else 加 remove(path)。
- **不这样会怎样**: 线上「事件有行没图」投诉进来,日志一片正常——只能逐条查库归因,分不清没写成文件还是写成了没记上。
- **源码**: `event_bus.c:148-149`(fopen)/`150-163`(短写+WRN)/`155-159`(UPDATE)/`cloud_ai.c:277-278`(id=-1 痕迹)。

### Q: 本项目回调机制的全貌是什么?注册、触发、解耦、快与慢怎么串成一段话?
- **一句话**: 注册发生在启动期、触发发生在运行期,两边靠函数指针解耦——alarm_init 开机调 event_bus_subscribe(on_event, NULL) 挂进订阅表;之后全项目唯一的发布者 cloud_ai 每次识别出事件就调 publish:锁内完成入库和快照后放锁,再到锁外遍历订阅表、通过函数指针挨个调用(c:176-178)——此时这一行就是 on_event(ev, NULL)。(学生口述版原文收录)
- **要点**: ①**解耦收益**:event_bus 和 alarm 互不相识,publish 不知道 on_event 这个名字,它只是调表里 whatever——新增 MQTT、邮件等订阅者各写一行 subscribe,发布侧零改动(观察者模式);②**回调跑在发布线程(cloud_ai)的调用栈上**,on_event 被设计成「只递门铃不搬家具」:微秒级完成过滤(类型命中+置信度达标)、置 g_pending、cond_signal 就返回,蜂鸣器响几秒的慢动作由条件变量交接给 alarm 自己的线程慢慢干——通知快和执行慢刻意拆开,谁也不拖累谁;③**事实与策略的分离+失败的不对称隔离**:事件是客观事实,报不报警是长在 alarm 自己配置里的策略;动作面挂了不传染数据面(事件照样入库),底座优先、动作是增强;④**边界**:回调快是纪律不是机制——签名 void、没人掐表,哪个订阅者写了慢回调照样冻住 cloud_ai 的识别循环,完整表述「机制保证解耦,纪律保证快」;报警期间新事件直接覆盖 g_pending、合并不排队=丢旧保新思想在报警侧的翻版。

### Q: g_pending 单槽为什么会「丢事件」?真覆盖窗口在哪?
- **一句话**: g_pending 存的是**电平**(要响多久)不是**边沿**(来了几次)——「未取走」窗口连来 A、B 两条,B 的写入顶掉 A(**最后写者赢**,锁只保证写不撕破、不仲裁谁赢),**被抹掉的只有基数**(「来了两条」坍缩成「至少一条」);已取走(响铃中)再来事件=写入空槽「存款不是销户」,下轮循环顶部谓词检查接住,完整保留。
- **要点**: ①真覆盖仅存在于 c:81 写入后~c:98-99 取走前的窗口;②时长也被抹仅当 reload 恰落在两写之间改了 active_s(兜底 3 也参与:active_s≤0 时 A=3、热更后 B=10);③修复方向由值语义决定:`+=active_s`=时长累加**一轮加长**而非两轮(且风暴下连响几分钟=自伤),真要「两轮」需计数语义(g_count++);④家族:与 frame_grabber g_jpeg 覆盖同族——丢旧保新丢的从来是「次数」不是「内容」,前提=**真相源另有其处**(事件全记录在 SQLite),报警通道只承诺「别错过正在发生的事」不承诺「数清发生了几次」。
- **不这样会怎样**: 换计数→报警风暴期蜂鸣器疲劳轰炸;换队列→内存与复杂度换精确计数,监控场景不要。
- **源码**: `alarm.c:81`(置数,兜底3)/`98-99`(锁内取走清零)/`101,106`(响铃逐秒可中断)。
- **状态**: 2026-09-15 首次通过(2.3B 段1 Q1;双窗口构造+值语义+g_jpeg 家族迁移独立完成,「存款不是销户」「被抹掉的是基数」为学生原创表述)

### Q: /snap/ 的防线为什么是能力设计,不是过滤设计?

- **要点**: ①两道关=形状解析(c:542)+引用授权(c:547:get 失败或无图→404);`..` 更早在 c:537 strstr 拒(403)属纵深冗余;②**过滤器松了不伤安全**:sscanf 不要求吃完整串,`evt_42.jpg/垃圾` 也解析出 42 放行——但路径构造从头到尾没有 URL 字节参与,闸门漏水淹不到能力边界(反证「安全性质靠结构不靠过滤器严密」);③朴素拼路径 `snprintf(dir/%s)+open` 的攻击面:web.c:872 先 url_decode(path)→`/snap/..%2f..%2f…` 或裸 `/snap/../conf/gateway.conf` 越出快照目录读任意文件,一次 GET 拖走 anthropic_auth_token(conf.h:35 真实键名)整份配置——**读权限即致命**。
- **不这样会怎样**: 过滤式防线(URL 黑名单/逐字符检查)永远追着编码绕过跑;能力式一次设计永久收敛攻击面。
- **源码**: `web.c:537-551`(两道关)/`872`(url_decode);`event_bus.c:262-281`(get)。

### Q: event_t 在两条支路上的「有效期」分别由什么保证?
- **一句话**: 支路1(订阅回调)的 ev 是**借的**——cloud_ai.c:272 栈上局部量,寿命=publish 返回、那层栈帧弹出为止,由「同步调用嵌套」保证(回调 c:176-178 的执行区间嵌在 ev 寿命区间内,return id 在 c:179),const 签名=只借读;支路2(web 查询)的 evs[64] 是**拷的**——该连接线程(web.c:994 client_thread)自己的栈数组,由「锁内拷贝+线程私有」保证:row_to_event 在 g_lock 窗口内逐字段复制,放锁后与库彻底脱钩(冻结快照),每线程一份无共享入口。
- **要点**: ①机制/纪律分层(诚实边界):同步只保证**回调执行期间**安全,不阻止订阅者把指针偷存事后用——这层无机制强制,全靠「快速返回、不滞留指针」契约(c:169 注释),口径「机制保证时序嵌套,纪律保证不留指针」;②支路2 的「过期后没人再碰」不是被防止的,是**结构上不存在别的碰法**;③家族:借用语义第三站(packet→recorder 拷、jpeg→TRANSIENT 绑定、ev→同步嵌套);拷贝=锁(一致性)+拷(冻结脱钩)双保证的独立部署。
- **不这样会怎样**: 订阅者把 ev 入队异步处理→publish 返回即悬垂;evs 若共享/外传→放锁后读写竞争。
- **源码**: `cloud_ai.c:272/277`;`event_bus.c:169-179`;`web.c:473/955-994`;`event_bus.h:18-19`(契约注释)。

### Q: 停机顺序 web→cloud→receiver→alarm→event_bus 为什么这么排?
- **一句话**: **依赖倒序+发布者栅栏**:全项目唯一 publish 调用者=cloud_ai(c:277),cloud_ai_stop 竖旗后 join——在途最后一次 publish 在 join 返回前跑完,join 后该线程不可能再调任何东西,故 event_bus_deinit 执行时「天下已无活发布者」,「deinit 后还有 publish」在真实顺序里不存在;alarm(订阅者)排在 event_bus(被依赖者)前=依赖箭头通则——订阅注册指向总线,**被依赖者最后死**。
- **要点**: ①风险分层:alarm→event_bus 这条边在本代码**无实际 UAF 牙齿**(on_event 只在 publish 内跑,而 publish 已被 join 栅栏封死);真正有牙齿的错序=**deinit 挪到 cloud 前**;②守卫兜底:迟到 publish 撞 c:112 `!g_db` 一票否决 return -1,on_event(流水线最后一站)根本走不到,事件干净蒸发,唯一痕迹=cloud_ai 无条件 LOG 的 id=-1(返回值无人分支);③守卫自身针眼:c:112 检查在锁外(c:117 才 lock)=TOCTOU,只在「检查过→deinit 拿锁关库→publish 拿锁用野句柄」极限交错下失守,真实顺序里窗口从不打开——应然(守卫)/实然(顺序保证)/残余(针眼)三层;④web 排最前另有牙齿:web 后停则 POST /api/config 热更新可**重新创建已停的 AI 线程」(TODO #24)。
