### Q: web.c 的路由键是什么?GET 和 POST 的本质区别?
- **一句话**: 路由键 = method + path 两字段组合——「method 选支路、path 选 handler、query/body 是货」;GET=按 URL 取资源(静态文件是合法资源族,HTTP 生于取文件、API 是嫁接),POST=提交给处理过程。
- **要点**: ①query 在路由前剥掉(web.c:977-978 把 `?` 写成 `\0` 就地截断,剥下的 query 全库唯一消费者=serve_events 过滤);②CL 解析+补读块(983-1011)对 GET 也跑——分发前方法无关,普通 GET 无 CL 天然空转;③GET 大支路 1014(1015 顺带预取 Range 头,梯子末尾只有 serve_file 用)、POST 1040 只有 /api/config 一条路、其余 405(1047);④**读可宽容、写必须白名单(一条路一条命)**——GET 多给几条资源路径无害,POST 多开一条就是多一个改态入口。
- **不这样会怎样**: 写路径不收白名单→任意 POST 触发任意 handler→改态入口失控(对照 #24:web 非最先停时 POST 可热复活已停模块)。
- **源码**: `web.c:964`(handle_client_inner)、`977-978`(query 剥离)、`1014/1040/1047`(三支路)。
- **状态**: 2026-09-17 首次通过(3.1 C1/V1);总验收复述确认(09-20)
- **关联**: 3.1 E7;01 主数据流卡

### Q: POST /api/config 尾部三步为什么必须「落盘→推送→转正」这个顺序?

### Q: MJPEG 的缓存栏三栏模型——产帧、单槽、发送泵各是什么节奏?
- **一句话**: 产帧按 target_fps 节流(frame_grabber)→g_jpeg latest-wins 单槽(只有最新概念)→发送侧 200ms 写死的泵——「**MJPEG 无新帧概念只有最新概念,发送侧是照节拍抽缓存的泵,不是照事件推流的闸**」。
- **要点**: ①三栏各自独立:调产帧率不改发送节拍,调发送节拍不改产帧;②可见帧率上限=min(产帧率, 1/0.2s=5fps);③新鲜度量化:产 25fps 时每次抽到的帧最多 40ms 旧,产 5fps 时最多 200ms 旧——产帧翻 5 倍的唯一收益是延迟略降;④调高 fps 白烧:多出的帧全被单槽覆盖,消费者只抽走一张。
- **不这样会怎样**: 以为调 web_mjpeg_fps 能让浏览器更流畅→实然被 200ms 节拍钳死;以为降产帧率省 CPU 却让画面卡顿→三栏独立才能推对杠杆。
- **源码**: `web.c:213`(200ms 写死)、`197`(get_jpeg);`frame_grabber.c:138-139`(节流现读)。
- **状态**: 2026-09-17 首次通过(3.2 场景二自建三栏);总验收变式 V 量化延伸(09-20)
- **关联**: 04 frame_grabber 节流卡;本文件同值异义卡

### Q: send 的「两个病两个药」——短写和卡死分别怎么治?
- **一句话**: 短写=send 返回正数但小于请求长度(web 无处理,余字节随 free 丢弃→MJPEG 流内错位:CL 声明 sz 实到 n,下个 part 头被当帧数据吞);卡死=对端无 RST 分区时阻塞 send 永不返回——**send_all 治短写不治卡死,卡死药=SO_SNDTIMEO 或非阻塞+epoll**。
- **要点**: ①send 返 sz 只等于字节进了内核 SO_SNDBUF,不上网线;②修法=迁移 rtsp_server.c:190-199 的 send_all(while 推进+EINTR continue+MSG_NOSIGNAL);③SIGPIPE 前提:signal(SIGPIPE,SIG_IGN) 忽略后 send 返 EPIPE 不杀进程,不忽略则写已关闭连接=EPIPE 信号默认终止**整个进程**;④断连三分支:RST 已到→send -1 干净退场/RST 在途→尾包 send 失败被吞、退出推迟一轮(200ms+白做一轮 get_jpeg)/无分区→卡死,靠内核重传放弃(~15.4 分钟,tcp_retries2=15)自愈。
- **不这样会怎样**: 只装 send_all 以为完事→慢客户端照样把线程钉死在 send 里(3.4 睡姿分界的另一例)。
- **源码**: `web.c:209-211`(三笔裸 send)、`rtsp_server.c:190-199`(send_all 参照)。
- **状态**: 2026-09-17 首次通过(3.2 场景三+闭卷);总验收场景一复述(09-20)
- **关联**: 05 rtsp_server;动手池候选(send_all 迁移)

### Q: MJPEG 断流后前端会自己重连吗?流结束靠什么感知?
- **一句话**: 不会——app.js 的 imgFail 只亮 NO SIGNAL 不重连(185-191),恢复靠手动切流;流的结束不在流内容里,在 TCP FIN 里:**从不发 `--framebound--` 终止符**,循环退出→外层 close(cfd, web.c:1061)→内核发 FIN→客户端 read=0。
- **要点**: ①multipart 一帧布局=`\r\n--framebound\r\n`+Content-Type/Content-Length 两行头+空行+N 字节 JPEG+尾 `\r\n`(web.c:205-211);boundary 一帧出现一次(开头),流头只声明一次;②客户端不解析 JPEG 也能分帧——靠 part 头里的 Content-Length 精确读 N 字节(x-mixed-replace 每帧整幅替换);③服务端三条退出路径(空帧超限/send 失败/停机)殊途同归同一个 close——所有权人统一关。
- **不这样会怎样**: 以为浏览器 img 标签断了会自愈→实然画面钉死在最后一帧+NO SIGNAL 徽章,用户必须手动恢复。
- **源码**: `web.c:186-192`(流头)、`205-213`(循环体);`app.js:185-191`。
- **状态**: 2026-09-17 首次通过(3.2 纠偏1);总验收题 3 补 FIN/--framebound-- 复述(09-20)
- **关联**: 本文件路由键卡

### Q: HTTP Range 的两层分界——为什么「智能在客户端,dumb 在服务端」?
- **一句话**: Range 词汇表只有字节偏移,没有时间/帧号/关键帧;播放器拖到 1:30,「1:30→字节偏移」的翻译发生在**客户端**、靠 MP4 容器索引(stts 时间→样本序号→向前找最近同步样本→stco 样本→字节偏移),然后发 `bytes=X-`;web 侧全程只需会:解析两个数字→lseek→read→send。
- **要点**: ①方法论=**先问每层的词汇表**(传输层词汇=字节,容器层才懂时间);②检验一个资源能否 Range 拖动=三个「有没有」:总长知道吗/字节↔内容映射稳定吗/能否回头(重新发一段);③MJPEG multipart 对照=「连接本身即时间轴」(无索引、不能回头),与 Range 是两种流模型。
- **不这样会怎样**: 让服务端懂时间→每加一种容器服务端都要解析内部索引,职责越界;通用性来自把翻译留在懂格式的那一端。
- **源码**: `web.c:398-408`(只有字节词汇)、`434-443`(lseek/read/send)。
- **状态**: 2026-09-18 首次通过(3.3 场景B 独立构造);总验收必对①(09-20)
- **关联**: 03 recorder movflags 卡(fMP4 章首小目录=跳读的另一半)

### Q: Range 越界重置为 0 而非返回 416——这是什么性质的问题?
- **一句话**: `start` 越界被静默改写成 0(web.c:406)、`end` 越界钳到 total-1(407)——合规菜单只有 416(带 `bytes */total`,SHOULD)或 200 两道菜,**「206 换内容」是第三种**:非法输入被静默改写成合法请求而非被拒绝。
- **要点**: ①后果三类:客户端白白下载全文(带宽)/错误不收敛(无 416 纠错信号,播放器无法判断该重新请求什么)/`bytes=abc` 垃圾数字经 strtol 归 0→同样 206 全文;②倒置区间 `bytes=3000-1000`:content_len=-1999 无人拦,while 谓词 0<-1999 假=「压根不进门」,响应三重畸形(206+倒置 Content-Range+负 CL,Chrome ERR_INVALID_RESPONSE);③根因=守卫矩阵三格只铺了两格(有 start/end 各自范围检查,缺 start≤end 关系检查)。
- **不这样会怎样**: 客户端拿到 206 以为拿到了要的那段→进度条行为错乱;好玩家付带宽,坏玩家花屏。
- **源码**: `web.c:405-407`(两行重置)、`411`(content_len)、`437`(谓词)。
- **状态**: 2026-09-18 首次通过(3.3 场景A+闭卷倒置区间);总验收题 4 演算复述(09-20)
- **关联**: 本文件两层分界卡

### Q: lseek 为什么是 O(1)?Range 发送循环怎么保证不多发一字节?
- **一句话**: lseek 只改内核 file description 里的偏移数字,不搬数据——500MB 文件跳 90% 位置与跳 10 字节同价;对照的「读丢弃法」(读到目标位置扔掉)浪费随 seek 位置线性增长(10 倍读放大+SD 带宽与录像写争用)。
- **要点**: ①want 双钳制:`want=content_len-sent`,超过 32KB 缓冲截到 32KB(web.c:438-439)——**CL 诺言不多发一字节**;②三头分工:Content-Length(206)=end-start+1 与实发对齐、Content-Range=start-end/total 由 total 尾巴携带、Accept-Ranges=能力广告;③三出口各对事件:read≤0=文件侧先断/send<0=对端先走/谓词假=唯一正常出口;④read=0 在本项目近乎不可达(段名时间戳不复用+cleanup 是 unlink 非 truncate),c:441 主防 read=-1 介质故障。
- **不这样会怎样**: 丢弃法 seek→大文件回放拖一下,录像写入就被读带宽挤占(边侧 SD 卡共享带宽)。
- **源码**: `web.c:434`(lseek)、`435-443`(循环)、`413-430`(两版头)。
- **状态**: 2026-09-18 首次通过(3.3 段3);总验收题 4 锚点复述(09-20)
- **关联**: 本文件两层分界卡

### Q: web_start 返回 0 为什么不等于端口已监听?
- **一句话**: 返回值的管辖边界=**pthread_create**(web.c:1114 同步等到结果),bind/listen 发生在新线程栈里(1071-1086)——**两条时间线从不相交**,异步侧的失败没有任何通路送回调用方:main.c:161-163 只抓得到线程创建失败,且处理只是 LOG_WRN 继续跑(Web 是旁路,失败不拖主链)。
- **要点**: ①返回 0 语义=「启动指令发起成功」(发车≠挂牌);②变体:web_port=70000 落盘重启→htons 吃 uint16_t 截成 4464→bind 成功,Web 活在没人知道的端口上,1085 日志打 70000=事实性错误日志——「等 bind 报错」等一个永远不会响的铃;③通用修法三向:同步化(阻塞到 bind 出结果)/完成侧回传(线程写共享状态)/完成侧自证(健康检查);④诚实类比:send 返 sz、rename 返 0、web_start 返 0 同族。
- **不这样会怎样**: 现场表现为「服务起不来但进程活着」,唯一错误信号藏在日志一行 WRN 里;更狠的值(截断撞特权端口)连 web_thread 都直接 return NULL,检测路径完全不存在。
- **源码**: `web.c:1105-1114`(web_start)、`1071-1086`(web_thread)、`main.c:161-163`。

### Q: 停机时为什么 shutdown 能唤醒 accept 而 g_running=0 不能?
- **一句话**: accept 睡在监听 socket 的内核等待队列上(一个内核对象),g_running 只是普通内存标志,改它不产生任何内核事件——**旗治走着的,刀治睡着的;shutdown 负责打断,g_running 负责裁决**。
- **要点**: ①shutdown(SHUT_RDWR)(web.c:1127)对 socket 对象动手术,唤醒队列上所有线程,accept 返 -1;②单用 close 不行——只摘 fd 表项,阻塞中的 accept 持内核引用照睡(**拆门牌吵不醒屋里人**);醒后 1091 continue 送回循环头,while(g_running) 谓词裁决退出,join(1128)收工;③bind 早失败的腿:无人睡在队列上,shutdown 回 ENOTCONN 无害、join 秒回——停机顺利掩盖停的是早死的服务。
- **不这样会怎样**: 只清标志→监听线程永远卡在 accept,join 永不返回,main 停机挂死。
- **源码**: `web.c:1090`(accept)、`1127-1128`(刀+收尸)、`1087`(裁决点)。
- **状态**: 2026-09-19 首次通过(3.4 归因钉死);总验收必对②(09-20,分工句新造)
- **关联**: 本文件 web_stop 返回卡;C2 条件变量(唤醒家族)

### Q: cfd 的关闭责任归谁?为什么提前 return 不漏关?
- **一句话**: **收尾责任跟所有权实际归属走**——client_thread(web.c:1057)拆箱拿到所有权,handle_client_inner 只是借用(函数体内不出现 close(cfd)),十几条提前 return 结束的是借用不结束所有权,1061 的 close 在唯一路径上等着;分支互斥:pthread_create 失败(1096)时所有权没交出去,监听线程自己在 1097 close。
- **要点**: ①两个潜在 closer(门卫/服务员)由分支互斥,不会双关不会漏关;③「return 结束的是借用,不结束所有权」;④别混近邻:serve_static 里 close(fd) 关的是文件 fd 不是 cfd——一次请求两种 fd 两本账。
- **不这样会怎样**: handler 里各关各的→提前 return 路径漏一处就泄漏 fd,双关则第二次 close 触发 EBADF/错关复用号。
- **源码**: `web.c:1057-1061`(所有权链)、`1096-1097`(失败分支)。
- **状态**: 2026-09-19 首次通过(3.4 快问);总验收 C1 反向应用(为什么不漏关,09-20)
- **关联**: 04 get_jpeg malloc 家族(所有权同构)

### Q: web_stop 返回为什么不等于所有线程都退场了?
- **一句话**: web_stop 只 join 监听线程 g_tid(1128),客户端线程出生即 detach(1099)、句柄创建后就丢——卡在 send 上的客户端线程 join 收不到,**最终刽子手只有进程退出**(exit_group 连坐);「调用返回的那一刻恰恰是时序差最大的那一刻」。
- **要点**: ①detached 线程终止后资源自动回收,但「终止」本身没人保证;②三类客户端线程命运:轮询者≤一拍退出/send 阻塞者退化睡客(15 分钟级)/单程毫秒级;③「睡姿分界」:分界不在线程身份在睡姿——轮询者碰上不收的对端即退化睡客(3.2 慢客户端与 3.4 accept 卡死统一框架)。
- **不这样会怎样**: 以为 web_stop 返回后端口立即干净→残留 detached 线程还握着 cfd 和堆副本(有界不增长:N 栈+N 副本+N 份 SO_SNDBUF)。
- **源码**: `web.c:1096-1099`(出生)、`1123-1128`(web_stop)。
- **状态**: 2026-09-19 首次通过(3.4 闭卷 C2);总验收场景一 Q4 复述(09-20)
- **关联**: 本文件两个病两个药卡

### Q: 配置原子写四步各防什么?「数据必须先于名字落盘」怎么讲?
- **一句话**: fflush(stdio 缓冲→page cache,防进程崩溃)/fsync(page cache→盘,**唯一对抗掉电**)/fclose(关门不搬数据,须排在 fsync 后因 fd 须存活)/rename(原子改目录项,可见性切换)——前三步保**新的完整**、rename 保**切换原子**、tmp 保**旧的未损**;名字是生效公告,公告前事实必须已在盘上。
- **不这样会怎样**: 原地写+O_TRUNC=落刀那刻本体即刻是半个;跳过 fsync+rename 后掉电=名字到了数据没到(新文件空/截断,旧 inode 已注销无退路)。
- **要点**: ①rename 返 0=可见性≠持久性——目录项元数据还在 ext4 日志里,commit(~5s)前掉电回滚方向指向旧(「原子性没破,破的是持久性」),结局=完整旧本体+新 tmp 孤儿;②缺口修法=fsync 父目录(dirfd);③备案:ext4 ordered 模式提交元数据前先刷数据,现实多一层保底,通用答案不依赖。
- **源码**: `conf.c:282-286`(四步)、`246`(本体只读)、`251`(tmp 创建)、`288`(rename 失败清理对照)。
- **状态**: 2026-09-20 首次通过(3.5 场景一+闭卷);总验收必对③+场景二 Q4 合成句(09-20)
- **关联**: 本文件 conf_save 实然卡;M-010

### Q: 配置热更新三栏表+判定法三腿——字段改完什么时候生效?
- **一句话**: 三栏=立即生效(web_mjpeg_fps:推送 conf.c:301+frame_grabber.c:138 每帧现读)/需重启(ai_fps=cloud_ai.c:302 出生快照拷了白拷;web_port=监听 fd 一次性 bind;rtsp_url=open_input 一次性建立)/名义热更实际致哑(alarm_gpio_led:软件层 158-159 锁内更新下一事件现读,但 export/direction 是 init 对旧编号一次性做的→新编号 sysfs 路径不存在,write 失败静默断链)。
- **要点**: ①判定法三腿:推送了没有/消费端现读还是出生快照/**消费时依赖的资源就绪没有**;②「字段被推送≠字段被消费,**断链永远断在消费端**」(生效时点=消费时点);③ai_fps 精确=线程重启可恢复(不是进程重启);④发送侧 200ms 上限钳死可见帧率(web_mjpeg_fps 的注脚)。
- **不这样会怎样**: 界面上改完以为生效→GPIO 改完下次响铃反而哑了(资源不就绪),用户以为设备坏了。
- **源码**: `conf.c:296-304`;`web.c:1109`(g_port 一次性拷贝)。

### Q: token 掩码回写为什么危险?「不动点」是什么?
- **一句话**: GET 回显掩码形态=`%.8s****`(web.c:614,短值纯 `****`),前端原样回传时现有守卫(775/805 的 `strcmp(buf,"****")`)只拦纯四星、拦不住长形态→真 token 被掩码值覆盖;且掩码函数对污染值再掩码得到自身(f(x)=前8+**** 还原污染值)——**事故自锁稳定且界面不可见**(不动点)。
- **要点**: ①防线设计「按值长什么样拦,不按哪个字段拦」——不是待遇不同,是长得不像暗号的程度不同;②修法选 A(拒绝含 `****` 的凭据值)三理由:不用猜意图/向 mqtt_pass 安全同构看齐/纯功能损失最便宜;③凡已推送必已入库(先存后推)保证运行态不领先持久态。
- **不这样会怎样**: 换 token 悄悄失效→云端 401,排查时 GET 看到的还是「正常的掩码」——界面上永远看不出 token 已经被污染。
- **源码**: `web.c:607-620`(GET 掩码)、`773-777`(token 守卫,新坐标 875-879);`validate_conf` 凭据检查(web.c:815 附近)。
- **状态**: 2026-09-20 首次通过(3.5 场景三全场最佳);总验收场景二迁移(09-20)
- **关联**: M-010;本文件 validate_conf 卡

### Q: validate_conf 为什么放 web 层、放那个位置、用 400?
- **一句话**: 分层信任——conf_load 必须宽容读历史怪值(否则一次坏配置永远起不来),**web 是不可信输入的唯一入口**,校验放入口;位置=全部解析后、conf_save 前(web.c:909),失败 400+字段级 error,栈副本直接废弃——不落盘不热更不转正,天然不部分应用;400=客户端的错(改请求),500=服务器自己的错(改服务),用错则客户端把输入错误当服务故障重试,错误永不收敛。
- **要点**: ①「越界值落盘后无错误信号,重启才爆」的时间差三重危险:反馈错位(200 撒谎)/持久态运行态分裂(带病跑数天)/修复通道失联(暴露时刻写入口至少已事实失联);②**校验的成本是一行 400,延迟暴露的成本是带外救援**;③错误信息不回显字符串原值:防破坏 JSON+防凭据写进日志;④特权端口不硬拦(嵌入式常 root,硬拦拒合法配置)。
- **不这样会怎样**: 等 bind 暴露=等一个永远不会响的铃(htons 截断后 bind 根本不失败,Web 活在 4464 上日志谎报 70000)。
- **源码**: `web.c:730-831`(validate_conf)、`909-915`(调用点);对照 `main.c:161-163`。

### Q: 同样写 0,web_mjpeg_fps 和 ai_fps 的命运为什么完全不同?

- **要点**: ①「防御缺位时的行为不是设计出来的,是碰巧长成那样的」;②白烧清单无解码(参考链必须逐包维护,节流在解码后);③观感几乎无感:200ms 泵节拍不变,唯一变化是新鲜度(40ms vs 200ms 旧)——5 倍 CPU 换延迟略降;④修法=入口统一词汇表:validate_conf 两行 `conf_check_range(fps,1,30)`(web.c:770/772)把 0 挡在门外——「旧固件里 0 是两个消费端各自的方言,新固件里 0 根本进不了门」。
- **不这样会怎样**: 只看配置文件永远想不到同一个 0 在两条链上一个是灾难一个是兜底——语义住在消费端,不在配置里。

### Q: 「每跨一次异步边界,成功语义就降级一次」——怎么用这个框架找静默失败?
- **一句话**: 每个成功信号都有管辖边界,返回值只对边界内同步完成的那一步负责;每跨一次异步边界(建线程/进内核缓冲/交磁盘),成功语义降级一次,跨越处没有新的确认机制,失败就静默——读任何「成功」代码问一句:**返回的那一刻事办到了哪一步?从这步到我关心的一步之间还隔着谁?**
- **要点**: ①家族四实例:web_start 返 0(管辖=线程创建,边界外=bind/listen)/send 返 sz(=进 SO_SNDBUF,外=上网线)/rename 返 0(=目录项可见,外=介质持久)/盘满时 fflush 被忽略(=已接受进 stdio 缓冲,外=盘上数据);②修法三向:同步化/完成侧回传/完成侧自证(健康检查);③与「锁是延迟的唯一传染媒介」「断链永远断在消费端」同格律。
- **不这样会怎样**: 把发起成功当业务完成→现场「进程活着服务死了」,错误信号只藏在日志一行里甚至不存在。
- **源码**: 家族锚点:`web.c:1105-1114`、`209-211`;`conf.c:282-286`。
- **状态**: 2026-09-20 建卡(总验收后学生元问题催生;学生已能自行举例)
- **关联**: 本文件 web_start 卡;M-010 家族

### Q: conf_save 的实然结构是什么?盘满时真的会返回 500 吗?
- **一句话**: conf_save 是「**读旧文件逐行替换值**」结构(fopen 本体 "r" conf.c:246 逐行 fgets,format_value 命中的 key 写新值、注释与未知行原样保留,全部写向 tmp)——不是从内存结构整体序列化;**282-284 的 fflush/fsync/fclose 返回值全部未查**:真实盘满(只要 tmp 创建成功)走不到 500,而是 fprintf 部分写失败被吞→rename 照做→**残缺 tmp 被转正+POST 返 200**,下次启动 fgets 半行照样命中。
- **要点**: ①唯一能到 500 的盘满路径=fopen(tmp,"w") 创建即失败(c:251);②tmp 遗骸无清理但无害(下次 fopen "w" 截断重写);对照 rename 失败分支(288)反而有 unlink;③修法=三步查返回值,任一失败照抄 288 的 `unlink+return -1`;④事故链:盘满→静默成功→半文件转正→重启加载坏值→系统带错配置跑且无信号(缺陷 #26,总验收学生独立发现)。
- **不这样会怎样**: 以为 500 分支兜住了盘满→实然它只兜住「tmp 都建不成」这一种;半文件转正后配置静默错。
- **源码**: `conf.c:242-292`(全函数);`web.c:918`(500 分支)。
- **状态**: 2026-09-20 建卡(总验收场景二实然推翻题设;学生独立断言+tutor 核实)
- **关联**: 本文件原子写卡;#26(动手池);M-010(注释vs代码家族)
