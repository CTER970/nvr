## 1. 使用方法

每张任务卡默认按下列闭环执行,但Tutor可根据用户已有方法论和现场表现压缩步骤、合并等价产出：

```text
AI给最小脚手架
→ 学生按时间盒主动阅读
→ 学生提交最能暴露理解的代表性产出或等价口述
→ AI按源码证据纠偏
→ 必要时做代表性复述/变式追问
→ 通过后更新状态
```

### 学生提交规则

任务卡中的“必交产出”是默认诊断证据池,不是必须全部完成的格式清单。若用户已能独立讲清整体流程、关键状态、代表性失败路径和核心why,可以省略重复图表；若关键因果仍错,即使表格齐全也不能通过。

- 第一次阅读不要求理解所有库 API；先写动作标签和自己的推断。
- 陌生内容分成“阻塞主线”和“暂不阻塞”，避免遇到一个 API 就离开主线。
- 不确定时写“未知/待验证”，不要为了填满答案而猜。
- 回答尽量带源码证据：变量、赋值、条件或函数调用，而不是只复述注释。

### AI纠偏规则

- 先指出哪些判断正确且有源码证据，再纠正错误和未知。
- 只解释阻塞当前任务的 API，不重新逐行讲完学生已经读对的代码。
- 每次收口都要提炼本次使用的通用阅读技巧，并给闭卷题。

### 参考评分维度

| 项目 | 权重 |
| --- | ---: |
| 数据流、函数阶段和控制流 | 30% |
| 输入/输出、关键状态和接口边界 | 25% |
| 数据或资源生命周期 | 20% |
| 失败路径与 why 推导 | 15% |
| 源码证据和独立复述 | 10% |

权重用于Tutor定位短板,不作为固定80%的机械门槛。Tutor可自主判定“通过/部分通过/需纠偏”；通过时必须有独立理解证据且关键误解已纠正。模块完成仍需达到总计划中的L3核心能力。

## 1.6B · fMP4、输出资源与时间戳

状态：**已完成（2026-08-18）**  
源码范围：`recorder.c:49-107, 229-265`；调用证据`stream_receiver.c:151-156`  
建议时间盒：40分钟初读 + 35分钟API/why + 20分钟演算

### 任务目的与意义

- **为什么有这个任务**：1.6A 回答了“什么时候写”（状态机：等关键帧、何时切段），但“怎么写进文件”仍是黑盒——输出资源从哪来、packet 进 MP4 前经历什么变换、文件内部长什么样。1.6B 补齐 recorder 的“写”半边，打通 packet→磁盘文件的完整数据路径。
- **在项目版图中的位置**：recorder 是录像主路中唯一与文件格式打交道的模块。`open/close_segment` 管段的生死，`write_header/interleaved_write_frame` 管数据入容器。学完它，“NVR 录像”三个字才真正落地。fMP4 是本项目“监控级可靠性”的核心选型：24×7 设备断电是常态，它直接决定“录像中断后还能不能看”。
- **面试价值**：三道高频 why 全落在此任务——为什么 fMP4、为什么 1/90000、为什么 rescale_ts。“三类资源 + `goto fail` 统一清理”是 C 资源管理的标准样本；源码还埋着两个审计点（注释与实际 movflags 不一致、write 后 `out->size` 统计可疑），训练“应然 vs 实然”的审查眼力，面试可主动讲。
- **学完能做什么**：闭卷讲清 MP4 段从创建上下文到关闭文件的资源顺序；分别解释三个 movflags 并使用“提高写入中断后的可恢复性”的谨慎表述；手工演算一次时基换算；指出硬编码 1/90000 成立的前提与失配后果。
- **与前后任务衔接**：向上承接 1.6A 的状态机（何时写），向下交给 1.6C 收口磁盘回收与失败边界；`1/90000` 时基认知将在 Phase 1.5 的 RTP 90kHz 时间戳处复用，是同一协议根源的两次正面接触。

### 本遍目标

- 划分`open_segment/close_segment`的资源获取与释放步骤。
- 理解codecpar复制、输出流、文件IO、写头、写Packet、写尾的顺序。
- 解释fragmented MP4配置服务于什么工程目标。
- 手工走一次Packet clone→rescale→write→free。
