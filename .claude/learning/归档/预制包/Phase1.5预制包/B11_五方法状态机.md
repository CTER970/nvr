## 1. 任务目的与意义(四层)

① **为什么存在**:B10 立了"遥控器"总纲,这块把每个按键具体化:每个方法(按键)改了哪个会话状态、客户端凭什么从"连上了"走到"收到画面"。RTSP 是**有状态**协议(对照无状态的 HTTP),状态机就是它的骨架——不掌握状态变迁,读 handle_client 就是一堆 if-else 的乱麻。
② **项目背景**:`client_t` 结构体(c:152–171)就是本项目 RTSP 会话状态机的载体,每个字段在哪一行被谁赋值,就是状态机的全部转移边;`playing` 字段更直接决定 on_packet 是否给这个客户端发流(c:312)——"PLAY 之前不收流"的代码证据。
③ **岗位/面试**:「DESCRIBE/SETUP/PLAY 分别做什么?」是 RTSP 三连问的标准题;"点播像租房"的类比能把三步答成小故事,面试记忆点强。
④ **学完能做**:画方法时序×字段赋值表;说清每步建立的是"描述"还是"传输方式"还是"开始取数";为 B12(报文长什么样)留接口。

## 2. 前置概念声明(铁律21)

本块机制=**请求-响应+会话状态机**:一问一答的文本协议之上,用 Session ID 把多次请求串成一个有状态的会话(同族:HTTP 无状态→cookie 补状态;RTSP 原生就有 Session)。"状态机"读法:字段=状态变量,方法=触发事件,赋值行=转移边。1.6A 的 recorder 状态机(waiting_key)已用过这套读法,此处平移。

## 3. 标识符词源解析(铁律22)

- **OPTIONS**:问服务端支持哪些方法(能力协商第一步)。
- **DESCRIBE**:describe=描述——索取会话描述(SDP,B13)。
- **SETUP**:set up=建立/搭好——为某条流定**传输方式**(TCP interleaved 或 UDP 端口对),服务端在此分配 **Session**(会话 ID,之后每请求必带)。
- **PLAY / TEARDOWN**:开始推流 / 拆除会话。
- **GET_PARAMETER**:get parameter=取参数,工程实用义=**保活心跳**(keep-alive),防止会话超时。
- **CSeq** = Command Sequence(命令序号):请求带上,响应带回,配对用——RTSP 版的"工单号"。

## 4. 类比锚点

**点播像租房**:OPTIONS=问中介"你们能办哪些业务";DESCRIBE=要一份房源说明书(SDP:几室几厅什么配置);SETUP=签合同定交付方式(怎么交房、走哪个门=传输方式,拿到合同号=Session);PLAY=入住开始按月收货(视频帧);GET_PARAMETER=定期跟房东互报平安(防被当跑路清退);TEARDOWN=退租。顺序错了(没签合同先入住)就是协议错序。

## 5. 五件套草稿

- ① 一句话:RTSP 会话生命周期五方法,驱动 `client_t` 状态从 NEW→(SETUP)READY→(PLAY)PLAYING→(TEARDOWN/断开)CLOSED。
- ② 设计动机:分阶段协商(先知格式、再定传输、再取数据),每步可校验可失败;Session 把请求串成会话。
- ③ 结构:方法时序×字段赋值表:OPTIONS(无状态)/DESCRIBE(回 SDP,无会话)/SETUP(session_id←c:426,tr←c:431/445,rtp_channel←c:432–436,udp fd 对←c:451–452,client_rtp_addr←c:465–468)/PLAY(playing=1←c:483,seq=0←c:484,入 g_clients 链表←c:486–489)/GET_PARAMETER(仅回 200,c:496–499)/TEARDOWN(摘链表←c:505–509,断连)。
- ④ 项目落点:上表各行;另:on_packet 里 `!c->playing` 跳过(c:312)——未 PLAY 不收流;`Public:` 头声明支持方法集(c:412)。
- ⑤ 面试变体:「DESCRIBE 和 SETUP 分别建立什么?」「PLAY 改了哪个状态?」

## 6. 字节样例库(2 正常+2 陷阱)

- **正常 1(完整拉流时序,纸笔主操作)**:VLC 拉 `rtsp://IP:8554/ch0`:OPTIONS→DESCRIBE(回 Content-Type: application/sdp + SDP)→SETUP(带 Transport 头;回 Session: xxx;timeout=60 + Transport: ...)→PLAY(回 Range: npt=0.000- + RTP-Info: url=...;seq=0;rtptime=0)→持续 RTP→TEARDOWN。逐步标"本步改了哪个字段"。
- **正常 2(字段变迁表)**:一行一方法,列出 §5-③ 的赋值行——状态机的"转移边"落地成行号。
- **陷阱 1(设计目的:Session 产生点与顺序校验)**:Session 在 **SETUP** 才产生(c:426),DESCRIBE 无会话也照答;协议应然里 PLAY 先于 SETUP 是错序(服务端应拒),本项目 `playing=1` 照样执行(c:483)不校验——**实然宽松**,三层证据意识(应然/实然/工程影响小因为客户端都守序)。
- **陷阱 2(设计目的:声明≠实现)**:SETUP 回 `Session: %u;timeout=60`(c:427)——但服务端**没有任何超时清理逻辑**:不跟踪客户端最后活跃时间,60 秒到了也不会踢会话;GET_PARAMETER 回了 200 却没被用于续命判定。前瞻一句:超时清理正是可选扩展任务(RTSP session 超时清理)的题目,P6/扩展卡再碰。
