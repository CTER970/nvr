## 1. 任务目的（四层）

① 配置链=「加载→热更新→落盘」的闭环，掉电安全与原子替换是嵌入式 TF 卡场景的真命题。② 项目背景：conf_save 逐行替换保留注释/顺序（作者设计取舍）+tmp+rename 原子替换——但目录 fsync 缺口和敏感字段回写是两个可讲的真实缺口。③ 岗位背景：「.tmp+rename 为什么原子」「fsync 保证什么」是存储岗高频；掩码回写是安全意识题。④ 学完交字段生效表，3.6 校验动手任务直接开工。

## 2. 数据流坐标

链路 D 控制面：`conf_load(启动一次) ⇄ g_cfg(各模块副本) ；POST /api/config：json_get_* 覆盖 new_cfg → conf_save(逐行重写+tmp+rename) → conf_apply_hot(五项) → web g_cfg 更新`。

## 3. 锚点（已实测）

- **conf_save 243-293**：逐行 fgets→副本 strip_comment→提取 key→format_value 命中则重写值**保留行尾注释**（c:267-274）→未命中原样写→`fflush→fsync(fileno)→fclose→rename`（c:281-290）。**rename 同文件系统=原子替换**；无目录 fsync。
- **format_value 197-240**：40 key 白名单；**敏感字段实际在内**（token c:218 / mqtt_user c:235 / mqtt_pass c:236）——与 c:195-196 注释相反（1.8 审计，铁律 15 活例）。
- **conf_apply_hot 296-304**：五项（log_level / alarm / cloud_ai / set_target_fps(web_mjpeg_fps) / set_segment_seconds）——**不含** rtsp_url/port/bind/storage_dir。
- **serve_config_get 573-655**：token 显「前 8 位+****」（c:607-621）；mqtt_pass 恒「****」（c:646）。
- **serve_config_post 732-830**：new_cfg=g_cfg 起步（c:745）→逐字段 if-present 覆盖（c:751-811）→**token/mqtt_pass 仅当精确等于 "****" 时跳过**（c:773-777/804-807）→conf_save（c:816）→apply_hot（c:823）→g_cfg=new_cfg（c:826）。
- **parse_log_level 157-164**：只认小写 debug/info/warn/error，未知→LOG_INFO。
- **conf_load 55-155**：默认值表（c:59-87）→逐行覆盖→未知 key 忽略（c:150）。

## 4. 卡内前置（铁律 21/22）

- **.tmp+rename 原子写**（卡内讲）：直接截断原文件写=中途掉电剩半份；写临时文件再 rename=内核保证「要么旧要么新」；fsync 保证数据真落盘（页缓存→介质）。类比：改账本先抄新副本再撕旧换新 vs 直接在原本上划改。
- 词源：`fsync`（file sync，强制刷盘）；`rename`（同名替换=原子）；`mask`（掩码=遮盖显示）。
- 迁移：热更新判定法「消费者重读才算生效」（2.4-V3）；g_cfg 副本模式（1.7A）。

## 5. 引导问题（手册 6 问照用）

1. 为什么先 .tmp 再 rename，不直接截断原文件？（掉电半份/损坏原配置）
2. fflush→fsync(file)→fclose→rename 各保证什么？缺目录 fsync 能宣称「完整掉电安全」吗？（用户态缓冲→文件系统页缓存→介质→名字替换；rename 本身可能掉电后丢——「新文件有了但目录项没刷」窗口）
3. apply_hot 下发哪些？端口/bind/存储目录为何不立即生效？（五项清单；web 线程已绑旧端口、receiver 已连旧 url——无重读点）
4. 判断热更新生效看什么？（消费者重读——2.4 法则在此终验）
5. GET 输出 token=「前8位+****」，POST 只精确特判 "****"——整表单回传会写入什么？（掩码串本身成为新 token——**审计⑩**；mqtt_pass 两边同为 "****" 反而挡得住——不对称性让学生自己比）
6. 前端传大写 "DEBUG"，parse_log_level 结果？（不匹配→默认 LOG_INFO——静默降级，审计⑫）

## 6. 产出与通过标准

落盘流程图（fgets→tmp→fsync→rename→失败分支 unlink tmp c:288）+ 字段三栏表（真热更新五项 / 传值但存疑如 ai_fps(运行线程不重读)/ 需重启如 url/port/bind/storage_dir）+ 掉电安全三层区分口述（原子替换=有 / 数据 fsync=有 / 目录持久=缺）。通过=三栏表（真热 / 拷了但不重读 / 须重启）+ 掩码不对称题。目录 fsync 缺口、并发 conf_save 无锁各一句，不单独出变式场。

## 7. 闭卷与变式（已过深度滤网）

- 闭卷：POST /api/config 五步链+两处掩码特判位置。
- V1：rename 成功后立刻掉电，重启后文件是新的还是旧的？（数据新，但极端时序下可能名字还是旧的=旧文件——目录项未刷；所以「完整掉电安全」要 fsync 目录，一句话）
- V2：conf_save 期间另一线程 POST（并发保存）会怎样？（无锁！两个线程各自 fopen 同一 .tmp 路径交错写——**预制审计**：web 本可多客户端线程并发，serve_config_post 无互斥；一句话结论+动手池）
- V3（对照）：为什么逐行替换而不是「序列化整个结构体重写」？（保留用户注释/顺序/未知行——工程友好性取舍，代价=format_value 白名单维护 40 行）。

## 8. 预制时审计发现（核实后用）

⑩token 掩码不对称回写；⑫log_level 大写静默降级；**conf_save 无并发保护**（V2，web 每连接一线程放大）；目录 fsync 缺口；注释 c:195-196 与代码相反（正面教材）。
