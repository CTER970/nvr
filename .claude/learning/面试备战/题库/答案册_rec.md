### rec-01 参考答案(目标 L3)

**L1 一句话**: IMX6ULL 没有 H.264 硬解 VPU,软转码不可行;remux 只是把压缩数据换容器、重打时间戳,CPU 近乎零成本,且保住原始证据链。
**L2 展开**: 转码 = 解码上下文把 H.264 还原成原始 YUV 帧 →(可选缩放)→ 编码上下文重新压缩,1080p 软解在 Cortex-A7 上单路都吃不满实时,多路监控必死;且重编码有世代损失,监控录像的取证价值要求"源流原样落盘"。remux 的全部工作 = 复制 codecpar(描述怎么解)+ 复制 packet(压缩数据本身)+ rescale_ts(时间戳换容器时基),零像素级运算。若真要省磁盘,正确方向是改端侧编码参数(GOP/码率)而不是边侧重编码。
**L3 项目实证**: 代码 recorder.c:242 movflags 配置的输出流直接复制源 codecpar(没有任何 codec context 创建);256 `av_packet_rescale_ts` 只改时间戳字段;259 `av_interleaved_write_frame` 直接写压缩 packet。
反例(转码的反证): 若是转码,recorder 里必然存在 `avcodec_send_packet/receive_frame`(解码)和 `send_frame/receive_packet`(编码)及 AVFrame——这些在 frame_grabber.c 里有(抽帧链是真解码),recorder.c 里一个没有,结构上就互相印证。
数据: [数据待补 D1:remux 时 CPU 占用 vs 空闲]。
**答题要点**: 先一句结论,再主动给"转码需要什么"的反证(显示懂 API 面),最后补"省磁盘的正确姿势是改编码参数"。防穿帮:别说"remux 会压缩/解压数据"——remux 不碰压缩数据本身。

### rec-02 参考答案(目标 L3)

**L1 一句话**: 24×7 监控设备断电是常态,fMP4 把全局索引(moov)前置+按关键帧切 fragment 落盘,断电最多丢最后未完成 fragment,不丢整文件;但它提高的是可恢复性,不等于零丢失。
**L2 展开**: 对比传统 MP4:moov(全局目录)写在文件尾,写入中断时 moov 未落盘→播放器拿到无目录的 mdat 正文→整文件不可播;fMP4(`+empty_moov`)开头就写空 moov,之后每个关键帧一个 moof+mdat 小节(`+frag_keyframe`),`+default_base_moof` 规范化 fragment 内寻址偏移;`frag_duration=10s` 是兜底(长时间无关键帧也强制切 fragment)。对比 TS 封装:断电兼容性同样好但索引/章节能力弱、存储效率低。
**L3 项目实证**: 代码 recorder.c:242-243:三个 movflags 一句话+frag_duration 兜底;业务切段(segment_seconds,recorder.c:226)与 fragment 边界是**两层不同的切**(文件段给磁盘管理和检索用,fragment 给掉电恢复用,一个业务段内部含多个 fragment)。
边界表述(必考追问):断电瞬间正在写的 fragment(以及最后一段未 close 的)仍可能损坏/缺失——所以话术是"提高中断后已落盘部分的可恢复/可解码性",不承诺"断电后全部完整"。
反例: 若用传统 MP4 且 30 分钟一段,第 29 分钟断电=前 29 分钟全部白录。
数据: [数据待补 D6:断电/强杀后各段可播性实测]。
**答题要点**: 先"两层切"结构(fragment vs 业务段),再三个 movflags 各自解决什么,最后**主动给出"≠零丢失"的边界**——这句谨慎表述本身就是加分项。防穿帮:别把 movflags 当算术值或帧头(它是 muxer 的具名标志串选项)。

### rec-03 参考答案(目标 L3)

**L1 一句话**: 非关键帧(P 帧)的解码依赖前序参考帧,新段以它起头则整段从一开始就缺参考,播放花屏/黑屏——首要问题是解码依赖,不是容器损坏(MP4 结构本身不必然坏)。
**L2 展开**: H.264 里 IDR 是随机接入点,后面帧都直接间接参考它;等价地,"seek 到任意点能播"就要求那一点是 IDR。到时但无关键帧时:**继续写旧段**(等下一个关键帧再切),用延迟换正确性——监控场景段边界差几秒无感知,坏一段不可接受。首段和业务切段是**两套机制一个原则**:首段用显式 `waiting_key` 门控,业务切段用 226 行的组合条件(header_written && is_key && 到时长),组合条件里的 is_key 同时保证"关旧段的位置"和"新段第一帧"都是关键帧(触发切的那个关键帧在 close/open 之后才进公共写路径,属于新段)。
**L3 项目实证**: 代码 recorder.c:215-216 `waiting_key` 时非关键帧直接 `return 0` 丢弃(注意:不是错误,主循环继续);226 切段组合条件;226-231 切段后新段从 waiting_key 状态重建。
反例: 新段以 P 帧开头→该段从第一帧起所有帧都缺参考帧→播放器表现:花屏、黑屏或直接拒解;这正是"用户 seek 后花屏""录像回放开头花屏"类问题的同源机制(客户端拿到非 IDR 起头的流/没拿到 SPS-PPS 也是同族原因,Phase 1.5 proto-02 呼应)。
**答题要点**: 先"解码依赖"这个首要答案(追问里"还是容器损坏?"是陷阱,MP4 容器可以完好而内容不可解),再讲两套机制,最后主动关联"花屏"变体题。防穿帮:别说"非关键帧写进去文件就损坏"——混淆了内容层和容器层。

### rec-04 参考答案(目标 L3)

**L1 一句话**: 时间戳的语义=数值×时基,不同环节时基不同(源流 1/90000、MP4 流时基由 muxer 定、RTP 固定 90kHz),不换算则同一数值在不同容器/协议里代表不同时长;1/90000 沿用的是 RTP/MP4 的 90kHz 传统。
**L2 展开**: 90kHz 的由来:足够细分帧间隔(1/90000s≈11μs)且是常用帧率的整数倍,同时被 RTP(RFC 3550 视频默认)和 MP4 实践沿用,跨环节免二次换算。换算公式:dst = src × src_tb / dst_tb(数值按时基比例伸缩)。90kHz 与毫秒时基差 90 倍——若把 ms 数值当 90kHz 数值用,播放会快/慢 90 倍(1.6B 实测过的变式:数值不变、含义变,呈现节奏错)。
**L3 项目实证**: 代码 recorder.c:256 `av_packet_rescale_ts(out, (AVRational){1,90000}, r->ost->time_base)`——输入时基**写死**;对照 stream_receiver.c:168:`rtsp_server_on_packet(&pkt, &ic->streams[vidx]->time_base)`——转发那路把源时基传下去了,两路对照正是 rec-09 的素材。
反例: 源流若真是 1/1000(ms)时基,数值 4500 的 PTS 实际是 4.5s,按 90000 解读成 0.05s→播放节奏全错(快 90 倍);不是花屏,是时长错乱。
**答题要点**: 先公式(数值×时基),再 90kHz 三个优点,最后主动交底"输入写死了,这是个已知脆弱假设"(衔接 rec-09,显示审计意识)。防穿帮:把时基和时间戳说混(时间戳是数值,时基是单位)。

### rec-05 参考答案(目标 L3)

**L1 一句话**: 文件名内嵌时间戳,scandir+strcmp 排序天然得到时间序,从最旧删起,删前用 strstr 判断跳过正在写的当前段,每删一个重新 statvfs 直到回到阈值之上。
**L2 展开**: 为什么用文件名不用 mtime:文件名由切段时刻生成,稳定且可读(本身就是检索索引);mtime 可能被拷贝/工具触碰扰动。为什么删一个就重查 statvfs:空间是全局动态的(其他写入者、TF 卡预留),逐次重查避免过度删除。策略对比:低水位+高水位双阈值(削峰)比单阈值更平滑,当前实现是单阈值逐次逼近。触发时机由调用点决定(切段时/定期),函数本身只是"清理策略"——策略与触发分离。
**L3 项目实证**: 代码 recorder.c:116-161:118-119 `statvfs` 查空闲比例不足才继续;126 `scandir(dir,&namelist,NULL,name_cmp)`(第三参 NULL=不过滤,过滤在循环里手动做);**136 `if (strstr(r->cur_path, name)) continue;`** 子串匹配跳过当前段;循环内删最旧后重查空间;147-148 两层释放(每个 dirent + namelist 数组本体)。
反例(删了当前段会怎样):①正在写的 fd 还开着,Unix 下 unlink 后 inode 由打开者持有——**磁盘空间并不立刻释放**,清理目标落空;②muxer 继续往已 unlink 的文件写,段最终丢失;③cur_path 语义被破坏,后续切段判断错乱。
联动审计点 I-06:磁盘满时写失败的 err_count 会被"非关键帧 return 0 清零"路径稀释→熔断可能永不触发→表现是停摆重试而非重连(改进方向:按 errno/ENOSPC 分类处理)。
**答题要点**: 流程五步(查→扫→排→跳→删+重查)先背熟,再主动讲"删当前段空间也不释放"这个 Unix 语义细节(高频加分点),最后 I-06 显示审计纵深。防穿帮:别把"跳过当前段"说成按文件大小或后缀——是路径子串匹配。

### rec-09 参考答案(目标 L2)

**L1 一句话**: 1/90000 是对输入源时基的硬编码假设,当前 V821 推的流恰好满足,但接口上没传真实 tb——换源(如 ms 时基的流)录像时长就错;修法是把源 time_base 像转发路一样通过参数传进来。
**L2 展开**: 两种修法对比:①改 recorder_write_packet 签名加 tb 参数(对照 rtsp_server_on_packet 的做法,stream_receiver.c:168 已有现成形态)——一致性好,要动调用方;②在 recorder_create 时把源 stream 的 time_base 存进结构体——改动最小,但热换源后要记得更新。工程上选①,与另一路保持同一约定。
**L3 项目实证**: recorder.c:256 写死 {1,90000};对照 stream_receiver.c:168 传 `&ic->streams[vidx]->time_base`。
反例: 同 rec-04(90 倍速节奏错乱,非花屏)。
**答题要点**: 这题本质是 rec-04 的"审计延伸",答题姿态=发现者+修复方案者。防穿帮:别说"改个宏就行"——问题在接口没暴露时基,不在数值本身。

### rec-10 参考答案(目标 L2)

**L1 一句话**: 六步:准备参数→配置超时/探测上限→`avformat_open_input`→`avformat_find_stream_info` 探测→遍历 streams 选视频流→交付 ic 和流索引;打开成功但无视频流的收场=关闭 ic、返回失败、不写输出参数。
**L2 展开**: `find_stream_info` 的作用:靠头几个包推算流参数(分辨率/时基/码率),不调则 codecpar 字段不可靠,后续复制给输出流是脏数据;探测配超时(5s)和大小上限(10MB)是防劣质源把拉流线程挂死;`opts`(打开选项)和 `ic`(上下文)是两类独立资源,失败路径各自要走释放。对比:本地格式确定的文件可以少探测甚至免探测,网络流必须探测。
**L3 项目实证**: stream_receiver.c:29-83(open_input,1.5A 已闭卷验收):两个输出参数用二级指针交付(`*pic`/`*vstream_idx`);两类失败收场区分——探测失败(中途资源逐级释放)与"打开成功但无视频流"(关闭 ic、返回 -1、输出参数不写,调用者拿 NULL 判断)。
反例: 不设探测上限→坏源挂住拉流线程→录像停摆且 stop 都难(阻塞在 FFmpeg 内部网络 IO);选流不做业务过滤→音频包混进三分发(实际在 146 后按 stream_index 过滤)。
**答题要点**: 六阶段先背顺,亮点放在"两类失败收场不同"和"为什么要限探测"——这是实际踩过网络流才会说的细节。防穿帮:别把 find_stream_info 说成"打开"的一部分——它是独立第二步,可以失败。

### rec-11 参考答案(目标 L2)

**L1 一句话**: 四类资源按序获取:输出上下文→输出流→文件 IO(avio_open)→写头;任何一步失败 `goto fail` 统一逆序释放"已拿到"的部分;goto 的价值是让 N 个资源的所有失败组合共用一个出口,而不是每个失败点复制一份清理代码。
**L2 展开**: 对比"每失败点就地清理":N 个资源有 N+1 种部分失败状态,就地清理路径组合爆炸且漏一处就泄漏;统一 fail 标签(Linux 内核同款风格)把"释放"只写一次。使用 goto 清理的两个前提:资源变量先初始化为 NULL;释放函数容忍 NULL(avio_closep/avformat_free_context 均天然容忍)。
**L3 项目实证**: recorder.c:66-107(open_segment 资源链+goto fail);49-64(close_segment 与 open 对称逆序:closep→free_context,含 header_written 守卫的 write_trailer 和状态复位)。所有权细节(1.6B 闭卷题,独立答对过):`avio_closep` 必须在 `avformat_free_context` **之前**——pb 挂在上下文上,先 free 则 close 访问的是悬垂路径;`AVFMT_NOFILE` 语义=muxer 声明不需要调用者提供文件 IO,mp4 无此标志才走 avio_open,open/close 两侧对称守卫(M-005 纠偏档案,变式:换 rtp muxer 则两侧都跳过、pb 保持 NULL)。
反例: 守卫不对称=对 NULL 的 pb 关闭崩溃,或打开了不关泄漏;不 goto 而每层 return 复制清理——三处失败路径三份代码,改一处漏两处。
**答题要点**: 四资源→统一出口→所有权顺序,三段各 20 秒;"为什么敢用 goto"的标准答法:"资源清理是 goto 的经典合法场景,代价是纪律(变量置 NULL+释放函数容忍 NULL),内核同款"。防穿帮:别说"goto 都该避免"——教条式回答直接暴露没写过资源型 C 代码。
