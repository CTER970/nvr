### arch-01 参考答案(目标 L3)

**L1 一句话**: 算力分层——端侧只做它有硬件加速的(编码),边侧做它 CPU 干得动的(转发/存储/抽帧),云端做边侧算不动的(大模型推理);边侧不转码因为 IMX6ULL 没有 H.264 硬解 VPU。
**L2 展开**: 备选一"端侧做完整 NVR"——V821 的 RISC-V 核要跑录像+Web+AI 不现实,且存储在端侧损坏即丢;备选二"边侧转码降码率省磁盘"——A7 软解 1080p 单路就吃满 CPU,多路必死,且监控录像要求原始证据链,重编码反而降质;备选三"端侧直接上云"——上行带宽是稀缺资源,边侧本地存储+按需抽帧上云才是监控常态。选型核心是"让每种算力只干它有加速器的事"。
**L3 项目实证**: 代码 stream_receiver.c:146-168——拉流线程一次 `av_read_frame` 后同步三分发:157 `recorder_write_packet`(remux 录像主路)、164 `frame_grabber_feed`(抽 JPEG 旁路)、168 `rtsp_server_on_packet`(本地转发旁路)。
反例: 若要转码,链路必须变成 解码上下文→原始 YUV 帧(AVFrame)→编码上下文→新 Packet(1.6A 反证过的完整形态),当前 recorder.c 里一个解码/编码上下文都没有,只有 codecpar 复制和 rescale_ts——这本身就是"没转码"的证据。
数据: [数据待补 D1:remux 时 CPU 占用,证明"近乎零"的断言]。
**答题要点**: 先三层分工(一句),再转码反例(主动亮出"我知道转码要什么"),最后承认边界(无 VPU 是硬件事实,选型是顺应不是妥协)。防穿帮:别把"边侧不做智能"说死——抽帧上云就是边侧在参与智能链路。

### arch-02 参考答案(目标 L3)

**L1 一句话**: 一条主数据流"RTSP 拉流→单线程同步三分发→录像/JPEG/RTP 转发",7 类线程协作,启动按依赖正序、停止 LIFO 逆序。
**L2 展开**: 线程模型取舍:比"每功能一线程"更关键的是**谁拥有数据**——packet 只在拉流线程的栈上被借用消费,不加队列不加引用计数,时序天然确定;对比"多消费者多队列"模型(吞吐好但一致性成本高),监控场景选了简单确定性。
**L3 项目实证**: 线程清单(6 处 pthread_create):receiver(stream_receiver.c:194)、web 监听(web.c:1012)、web 每连接客户端(web.c:994)、rtsp 监听(rtsp_server.c:574)、AI(cloud_ai.c:328)、报警(alarm.c:124)+主线程(main,sigaction 装 SIGINT/SIGTERM,main.c:125-129)。
启动顺序 main.c:140-161:event_bus→alarm→**receiver**→cloud→web(消费者先于/紧邻生产者就绪,录像链最先通)。
停止 main.c:169-178:`while(g_running)` 主循环退出后 web_stop→cloud_ai_stop→stream_receiver_stop→alarm_stop→event_bus_deinit——与启动严格逆序(LIFO),保证生产者先停、消费者后撤,不产生"发给已销毁模块"的窗口。
反例: 停止若不逆序(如先 deinit event_bus 再停 cloud_ai),AI 线程可能向已销毁的总线发事件→use-after-free。
**答题要点**: 先画图(数据流主线+三个旁路标注),再报线程数和归属,**主动说"回调在哪个线程执行"是最常追问点**。防穿帮:别说成"11 个模块 11 个线程"——模块数≠线程数,log/conf/event_bus 无独立线程。

### arch-03 参考答案(目标 L3)

**L1 一句话**: 三个消费者都足够快,同步调用零队列内存、零引用计数管理、顺序确定;慢消费者问题用"旁路降级"而不是队列隔离来解决。
**L2 展开**: 备选一"每消费者一个无界队列+独立线程"——吞吐隔离最好,但内存无上限(慢消费者积压)、packet 引用计数生命周期复杂化、录像顺序不再确定;备选二"有界队列+丢最旧"——折中,但监控场景里录像要的是"不丢不乱",抽帧要的是"最新",转发要的是"实时",三者的正确策略完全不同,统一队列反而都不对。同步分发的本质是**把策略还给各消费者自己**:frame_grabber 自己节流+只留最新(等于零长度队列),recorder 只 remux 必然快,rtsp_server 的慢客户端是已知缺陷(见 arch-04)而非设计目标。
**L3 项目实证**: stream_receiver.c:157-168——三个调用在拉流线程调用栈上顺序执行,packet 是借用,最终由 receiver 统一 unref;写失败保护:158 `if (++err_count > 20) break` 重连,160 成功即清零(注意 I-06:非关键帧 return 0 也会走到清零——审计发现熔断被稀释)。
反例: 若 rtsp_server 持锁阻塞 send(真实缺陷),队列方案只是把内存爆掉换成延迟爆掉;同步方案的代价是"一个消费者阻塞就拖住全部"——所以设计前提写进了每个消费者的实现里(节流、只留最新、错误计数)。
**答题要点**: 先说结论+前提("消费者都快"),再对比队列方案,最后**主动交出已知缺陷**(慢客户端)——抢在面试官追问前展示审计深度。防穿帮:别说"绝对不会有慢消费者问题",会被持锁 send 的追问打死。

### arch-04 参考答案(目标 L3)

**L1 一句话**: 按"影响主路的→影响功能的→健壮性缺口"三级排:慢客户端可能拖住拉流分发、时基假设脆弱在前;RTCP/AVCC/SPS 缺省等协议层缺口居中;短写/越界返回码/目录 fsync 是长尾。
**L2 展开**: 讲改进要带取舍:"为什么还没改"比"改什么"更显工程成熟度——慢客户端改法是把发送移出锁外/每客户端发送队列,代价是内存和复杂度;时基修法是接口传 tb(一行改动,但要动调用链约定);RTCP 补全需要 SR/RR 解析线程,收益是弱网自适应,当前场景(局域网)收益低。
**L3 项目实证**: 清单级证据(定位见骨架文档):①慢客户端(rtsp_server 持锁 send_all);②时基未传(recorder.c:256 写死 {1,90000});③RTCP 仅端口骨架;④AVCC packet 未真正实现(注释声称);⑤SPS/PPS 硬编码缺省;⑥无 PTS 回退恒 0;⑦码率统计恒 0(recorder.c:262);⑧I-05 写头失败后非关键帧可成段首帧;⑨I-06 磁盘满熔断被清零;⑩Web 短写未处理/Range 越界返 200;⑪目录 fsync 缺口;⑫token 掩码回写。
反例: 只说"代码还不够规范"这种泛答案=零分;每条必须能落到"现象→原因→位置→修法"。
**答题要点**: 选 3 条讲透(推荐:慢客户端、时基、码率 bug),其余口头带过"还有约十项,已列清单"。防穿帮:面试官追问"为什么不修"——准备好"学习项目的边界+修法我已想清"的回答。

### arch-05 参考答案(目标 L3)

**L1 一句话**: 读代码时发现码率统计恒为 0 的真实 bug——`av_interleaved_write_frame` 成功会接管并掏空传入 packet,之后读 `out->size` 恒为 0,一路传导到 Web 码率显示。
**L2 展开**: 这类 bug 的普适价值:FFmpeg 的**所有权转移型 API**——write 成功后 packet 被"偷走"(引用归 muxer、buf 置空),任何"调用后还读参数"的代码都是同一类错误;对比 memcpy 型 API(调用后源数据不变)的心智差异。
**L3 项目实证**: 代码 recorder.c:259 `av_interleaved_write_frame(r->ofmt, out)` → 262 `r->bytes_written += out->size`——中间隔着成功分支,packet 已被掏空。
证据链(讲述用):审计动机=1.6B 学 movflags 时追问"write 之后 packet 归谁"→查 FFmpeg 文档确认接管语义→反推 262 行读的是空壳→影响面:bytes_written 恒 0→bitrate_kbps 恒 0→Web"当前段码率"恒 0。
第二例 I-05:写头失败后状态残留,下个非关键帧经补写头路径成为新段首帧→非关键帧起段(违反 rec-03 的原则),是**错误路径与正常路径状态机交叉**的样本。
反例(修复):统计改在读 `out->size` 之前先存局部变量,或用 write 的返回值前记录 size。
数据: [数据待补 D2:修复前后 Web 码率读数对照]。
**答题要点**: 四步故事"动机→证据→影响→修法",每步 20 秒。防穿帮:必须能说清"为什么编译器不报错"(合法读,只是值恒 0)和"为什么测试容易漏"(功能不崩,只有统计错)。

### arch-07 参考答案(目标 L2)

**L1 一句话**: 信号处理函数只置标志,主循环检测到后按启动的逆序 LIFO 逐个 stop(join 等线程退出),再 deinit 资源。
**L2 展开**: 对比 kill -9:进程被内核直接终止→正在写的 fMP4 段没有收尾(但 fMP4 的可恢复性兜底,见 rec-02)→配置/SQLite 可能写到一半;对比在信号处理函数里直接做清理:信号上下文不可重入,printf/malloc 都是雷。stop 内部顺序的通用心法:**先断输入再关处理**(如 web 先 shutdown/close 监听 fd 唤醒阻塞的 accept,再 join)。
**L3 项目实证**: main.c:125-129 `sigaction` 装 SIGINT/SIGTERM→on_signal 置 g_running=0;main.c:169-178 主循环退出后 web_stop→cloud_ai_stop→stream_receiver_stop→alarm_stop→event_bus_deinit(与启动 main.c:140-161 严格逆序)。
反例: 若 stream_receiver_stop 在 web_stop 之前,Web 还可能响应用户请求去查一个已停止的录像状态。
**答题要点**: 主线是"信号=置标志,清理=线程上下文";accept 的阻塞解除(shutdown 监听 fd)是亮点细节。防穿帮:别说"信号函数里 free/printf"——直接暴露不懂异步信号安全。

### arch-08 参考答案(目标 L3)

**L1 一句话**: 重连在拉流线程自己的两层循环里——外层管连接生命周期、内层读包,断流或录像熔断跳出内层后清理输入上下文原地重连;recorder 整体保留,新流恢复写入。
**L2 展开**: 对比备选一"独立重连线程":与拉流线程竞争输入上下文和分发回调,要加锁且引入两线程并发操作 FFmpeg 上下文的风险;备选二"上层进程自愈重启":状态全丢,录像段断、Web/事件全闪断。放在线程内=失败处理与资源所有权在同一线程,天然无竞争。错误三分流:读包失败(源断)→重连;录像写失败累计 21 次(磁盘/下游问题)→也走重连(顺带重开输入,赌源端也异常);stop(g_running=0)→循环条件失效,正常退出不重连。
**L3 项目实证**: 代码 stream_receiver.c:144(每次连接 err_count 清零);146-149(av_read_frame 失败 break 出内层走重连);157-158(`if (++err_count > 20) break` 熔断——联动审计 I-06:非关键帧 return 0 走到 160 清零,磁盘满时熔断被稀释,应按 ENOSPC 分类);循环出口 packet 兜底 unref;关闭输入前先 `g_ic=NULL` 再 close 局部 ic(全局句柄先失效,防他人误用);重连等待**逐秒 sleep 检查 g_running**(stop 响应性)。
recorder 侧联动:g_rec 跨重连保留、当前段继续写——**主动交出的工程边界**:若新源编码参数与旧段不同,旧段仍用旧 codecpar 存在潜在不匹配;实际部署源固定(V821)故安全。新段场景(首段/开段失败)由 waiting_key 门控(recorder.c:215-216)保证恢复后关键帧起头。
反例: 重连放独立线程→并发操作输入上下文;一次 sleep(10)→stop 要等 10 秒才响应;新段场景不等关键帧直接写→接 rec-03 花屏链。
数据: [数据待补 D3:断流→重连→恢复录像实测耗时]。
**答题要点**: 先两层循环骨架(10 秒),再三类错误分流(15 秒),最后把"recorder 跨重连保留"讲成自己发现的边界而非缺陷。防穿帮:别笼统说"重连后会等关键帧再续段"——实然是保留段直接续写、等关键帧的是新段场景,分场景说才不穿。
