## ① 拉流三分发(主口述约 2 分钟)

摄像头只拉一路流。拉流线程每读出一个包——音频包先按流编号过滤掉,只留视频——就在同一个循环里依次交给三家:先录像,再抽帧,最后转发。注意是三次函数调用,不是三个线程,这叫同步扇出。

为什么这么设计?省。要是每个功能自己连摄像头,就是三路 RTSP、三次拉流、各解各的码。现在一路连接、一份解码器:录像和转发根本不解码,压缩字节拿到手直接用;只有抽帧这条腿要解码,解出来归它一家用。

包归谁?归拉流线程自己,三家都是借的。转发只读一读字节往内核一发;抽帧把包喂给解码器,解码器自己记引用,解出的画面是新内存,跟原来的包就没关系了;只有录像要克隆一份——因为写 MP4 的接口会把传进去的包「据为己有」,不隔开就是双重释放。三家当场调用当场返回,循环末尾我统一释放,不用队列不用锁,这就是同步扇出的简单所在。

三条腿三个脾气:录像不能丢(丢包录像就花,兜底是写错二十次断线重连),转发不能慢(延迟最敏感,UDP 发不出去直接丢这帧、慢客户端连续失败超过 3 次就踢【精修#1】),抽帧只要最新(快照仓库只存一张,新图覆盖旧图,谁慢都不反压)。

### 子弹(按被问概率排)

**子弹1|「包给了三家,每家复制一份吗?」**
不是,一借一克隆一借。录像克隆了,但只是引用计数加一不是拷字节,因为 MP4 接口要接管包;抽帧是借用,解码器自己挂引用,解出的 AVFrame 是新内存;转发纯只读,唯一的字节拷贝发生在内核的 send 里。三家同步借还,我循环末尾统一释放,全程无锁。

**子弹2|「节流为什么不放解码前面?解码不是白做了?」**
放不了。H.264 拿前后帧做差,P 帧存的是「跟上一帧比变了啥」,解码器记着前面几帧的状态——跟追剧一样,跳一集后面全看不懂。跳包不解码,后面帧参考的「上一帧」就是错的,画面花屏直到下一个关键帧,一花一个 GOP。所以解码必须全量吃,节流放在解码后、缩放编码前——那两步才是真贵,而且不做不破坏状态。一句话:解码为了对,节流为了省,一个全量一个挑着来,位置就不同。

**子弹3|「出图那一刻拖慢了,处理跟不上生产,延迟不会越叠越多吗?」**
延迟叠加的前提是有地方无限制攒东西,这条链没有。重活每秒只发生 target_fps 次,平均开销低于到达速度,两次重活之间排队包被纯解码快速追平——尖峰不累计。真跟不上,直播系统的答案是丢不是攒:UDP 缓冲满丢包,花屏到下个 I 帧;下游快照只存最新、覆盖旧的,云慢也不排队。用丢旧保新换延迟有界。

**子弹4|「抽帧的缩放编码不是把转发也压住了吗?播放端怎么办?」**
压住了,但项目一行代码没处理,三层现成机制消化:节流保证重活是尖峰不是常态;FFmpeg 内部缓冲加播放器 jitter buffer 把尖峰摊平;真丢了包,播放器自然停在最后一帧等下个 I 帧——「停上一帧」不是故障,是实时视频的标准行为。

**子弹5|「一条腿卡住不全卡住了?」**
认这个代价,但要能点名最重的腿:抽帧(解码+缩放+编码)和录像(写 SD 卡,嵌入式上最不可靠)。兜底三层:抽帧节流、RTSP 客户端失败超限踢掉、录像写错二十次断线重连。单次慢写没超时保护,拿这个代价换不加队列不加锁的简单。

**子弹6|「预览的 RTSP 转发具体怎么转的?」**
网关自己当个局域网小 RTSP 电台,给 VLC 之类播放器用(web 预览走的是另一条 MJPEG 路,别混)。纯 passthrough 不转码:把 H.264 按 00 00 00 01 起始码拆成 NALU,套 12 字节 RTP 头(序号每包加一,靠它查丢包;时间戳从 packet pts 按 90kHz 换算),大 NALU 用 FU-A 分片,帧尾按双条件打 marker【精修#2】;UDP 直接发到握手留的地址,TCP 在原连接里加 '$'+通道+长度前缀。SDP 里带 SPS/PPS,播放器没它解不了码。

**子弹7|「快照是分析前存的还是分析后存的?」**
两个快照别混:分析前的在内存——抽帧腿往货架上摆最新 JPEG,旧的原地覆盖,AI 线程拷走一份就冻结;分析后的在磁盘——云端返回真事件了,才把手里那张写成 evt_<id>.jpg 落盘、路径回填数据库,挂在事件上当证据。内存的会被覆盖,磁盘的按事件 id 命名互不覆盖(旧快照有定期清理)。

**子弹8(暗雷,备着不主动说)|「配置里有子码流地址/ai_max_queue,用了?」**
都是预留位没接。子码流:当前只拉主码流一路,预览靠解码后缩到 640 宽,接了能降解码开销但要多一路连接一份解码器。ai_max_queue:名字像队列,实际没有模块用它,当前走单缓冲覆盖——理由就是丢旧保新、延迟有界。

## ② 旁路软解与所有权(主口述约 60 秒)

主路两条腿全程不碰解码:录像只做 MP4 重封装,转发只做 RTP 打包,压缩字节进、压缩字节出,最省 CPU。软解只发生在抽帧这条旁路上,分两截说清楚:解码是全量的,每个包都得送进解码器,参考链一包不能跳;出图是按需的,到目标帧率那个点才做缩放和 JPEG 编码这两件贵活。

产物不排队:仓库里只有一张图,新的来了直接覆盖旧的,因为下游 AI 要的是「现在」,旧帧没有价值。跨线程交接用最朴素的办法:读者在锁内 malloc 一块、把图深拷贝出来、所有权归自己——这就是「冻结快照」。【精修#3:这里补一句——锁保的是拷贝过程中仓库不被 realloc 搬家(防撕裂);深拷贝保的是拷完之后这块内存和仓库彻底脱钩(防悬垂)。两个保证缺一不可:只锁不拷=悬垂,只拷不锁=撕裂。】写侧换新用同一把锁,三个读者(AI 线程、预览流、抓拍接口)共用这把互斥锁——读者频率低,不值得上读写锁。

### 子弹

**子弹1|「为什么只存一张不建队列?」**
AI 分析要的是当前画面,旧帧分析出来是过时结果,排队等于花钱买延迟。队列还会让内存无界、让云分析的慢反压到上游。单张覆盖:内存恒定、延迟恒定(永远≈最新帧年龄),双达标。

**子弹2|「这是不是背压?」**
不是,是背压的替代。背压是消费者让生产者慢下来等它;拉流线程绝不能等——直播,一等人人就卡。所以反过来:消费慢就丢,生产节奏纹丝不动,两边彻底解耦。实时系统的通用取舍:用丢换不等。

**子弹3|「为什么深拷贝,不用引用计数/读写锁?」**
【精修#4:口径改为】JPEG 就是一块几十 KB 的平字节,为它引入引用计数机制的复杂度不值(FFmpeg 里 AVBufferRef 那套是给跨模块共享帧用的,这里只有一个写者);锁内一次 memcpy 是最简单可靠的做法,代价是持锁拷几十 KB,在目标帧率下【精修#5:删具体数字】可忽略。读写锁同理——写者只有一个、读者频率低,一把互斥锁的简单性值这个开销。

**子弹4|「冻结快照具体指什么?」**
get_jpeg 在锁内 malloc + memcpy,把所有权移交给调用方。从这一刻起,这块内存是调用方私有的,仓库被覆盖、realloc 都碰不到它——所以叫冻结:时间上冻结在这一刻,空间上和仓库彻底脱钩。

## 附块A · 背压与丢弃(必考概念题,①②③的公共追问层)

**判断标准一句话**:消费者变慢后,生产者有没有跟着慢?有=背压,没有只是扔=丢弃。

**两者关系**:同一个问题(生产快于消费)的对立路线,常组合使用(有界队列吸突发=背压,满了丢=兜底)。本项目自带一对活教材:转发腿 TCP 模式阻塞发送,慢客户端反向拖住拉流线程——这就是背压,还是坏的背压(惩罚了无关的腿),所以要踢人止损;UDP 模式 EAGAIN 直接丢——这是丢弃。同一条腿,两条路线都演了。

**流控菜单(按压力去哪分)**:①等它(阻塞队列、TCP 滑窗);②按需拉(request(n)、信用量、拉模式);③扔掉(丢新 Drop / 丢旧留新 Conflate——快照仓库就是 / 丢次要留 I 帧);④合并降频(采样节流);⑤拒绝(429/503、踢客户端);⑥扩容。

**金句**【精修#7:录像腿例外补进去】:「流控本质就问一句——压力去哪?还给生产者是背压,就地消灭是丢弃。直播选丢,因为新帧才有价值。我这个项目旁路和转发全站在丢这边;两个例外——TCP 转发腿的隐式背压(所以设计成失败超限就踢)和录像腿(它不能丢,选阻塞写+写错二十次断线重连)。」

## ③ remux + fMP4(主口述约 60 秒)

录像腿不解码:克隆引用、每包重标时间戳、交 MP4 封装器,最贵的是写 SD 卡。格式选 fMP4 为了掉电:普通 MP4 目录(moov)押在文件尾,没写到全废;fMP4 头部先写静态目录(empty_moov),数据一小段一小段落、每段自带小目录(frag_keyframe)——索引跟着数据走。可恢复≠零丢失,丢有两笔【精修#6:注意场景】:**首段启动或开段失败重试的等待期,非关键包主动扔(设计内丢);掉电瞬间正在写的 fragment 坏(故障丢)。正常业务切段不丢——到时没遇到关键帧就继续写旧段,段长略超设定**。水位清理:文件名=时间戳+段号,名字序就是时间序,按名排序从头删、跳过当前正在写的段。

### 子弹

**子弹1|三旗一兜底**:frag_keyframe(关键帧切段,索引随数据)/empty_moov(空目录先写,不回头)/default_base_moof(偏移相对自己,掐头去尾照样定位)/frag_duration 10s(没关键帧也强切,防膨胀,`recorder.c:243`)。

**子弹2|段首必须等关键帧**:P 帧参考链向前找,段首非 I 帧则整段开头花屏;等关键帧=每段独立可播,代价是等待期的主动丢包。

**子弹3|掉电边界三档**:头没写完=段没影;完整落盘的都能播;正在写的坏。正常切段写 trailer,完整段尾部干净。

**子弹4|时间基真相**【精修#8】:换算每包做,但输入时基假定 1/90000——这是**我审计出的已知边界**(从「600 秒段内部时长只有 6.7 秒」的矛盾反推的),RTSP 源恰好 90kHz 重合所以能跑,换时基的源就播放速度错。修法是把 AVRational 传进 recorder(rtsp 腿传了,recorder 接口没接)。

## 附块B · 字节纸笔卡(④的协议底层,白板可默画)

**fMP4 布局(对比记)**:

```
普通: [ftyp][mdat 全部数据][moov 总目录←最后才写]  掉电=全废
fMP4: [ftyp][moov 静态目录先写][moof₁|mdat₁][moof₂|mdat₂]...
      (编码参数/轨道/时基)      (小目录只管紧跟的小数据)
```

**NALU 头 1 字节**:F(1)|重要性 NRI(2)|类型(5);背 7=SPS、8=PPS、5=IDR、1=P 切片。Annex-B 用 `00 00 00 01` 起始码分隔。

**RTP 头 12 字节**:V=2 / M(帧末置 1)/ PT=96 / 序号每包+1(查丢包)/ 时间戳(90kHz,同帧同值)/ SSRC。

**FU-A 分片**:`[12B RTP头][FU indicator][FU header][分片载荷]`
- indicator = 原头高 3 位照搬 + 类型 28 → `(hdr&0xE0)|28`
- FU header = S 位(头)/E 位(尾)/原类型 5 位
- 重组:见 S 开缓冲、连拼、见 E 收尾,原头由 indicator 高 3 位 + FU header 低 5 位拼回
- 同 NALU 分片:时间戳全同、序号连续、只有最后一片可能带 M

**两个为什么**:需要 FU-A 的几乎总是 I 帧(全量几万字节 vs P 帧差量几百字节);应用层切到 MTU 内而不靠 IP 分片(IP 分片任一片丢=整包废,放大伤害;FU-A 每片独立、丢了知道丢哪)。

11. ❌ MJPEG 分帧「只靠 boundary 低碰撞概率」 → ✅ 双机制:boundary 划界(multipart 语法)+ 每帧小节自带 Content-Length 定长,「二进制靠长度」在本项目是落地事实
12. ❌「裸流不能直接播」 → ✅「缺索引和时长,拖动不可靠、通用性差」(VLC/ffplay 能顺序播)
13. ❌ 源头给「长 GOP 结构」帮助跳解 → ✅ 反了:GOP 越长参考链越长;正确三档=子码流(工程标准)/SVC 时间分层/全 I 帧(GOP=1);口径「跳解合法性来自参考链闭包」

## ④ 双协议出口(主口述约 60 秒;降级口径+边界声明)

三个旁路腿,两个汇总出口。RTSP 出口走转发腿:H.264 原样透传——生成 SDP 给播放器、拆 NALU 套 RTP、超 MTU 的走 FU-A 分片,全程不解码,压缩字节进压缩字节出。HTTP 出口是自研轻量 server:一个监听线程 accept,每来一个连接开一个线程去处理(c:994);处理函数五步——收包、拆请求行和头、按 Content-Length 补读 body、按 URL 分发到十一个端点、回响应。

HTTP 出口上卖两样东西,各来自一条腿:实时预览来自抽帧腿——MJPEG 流,同一条 TCP 连接上 multipart 连续推 JPEG,边界靠 boundary 字符串分隔(二进制里没法靠分隔符,所以用显式 boundary),帧率就是快照仓库的生产速率,预览和 AI 共用一个仓库;历史回放来自录像腿——MP4 文件走 Range 分段,206 加 Content-Range 加 lseek,播放器 seek 时靠 fMP4 的分段索引算出要哪个字节区间、只拉那段。

事件这块,web 是纯拉模式——用户刷新才查库;alarm 是推模式——publish 时同步回调。两者互为镜像,一个出口一个入口。

### 子弹

**子弹1(点睛)|三腿两出口映射表**:RTSP=转发腿/H.264/压缩域/直播;MJPEG=抽帧腿/JPEG/解码后/实时预览;MP4=录像腿/fMP4/落盘/历史回放。被问「出口之间什么关系」就亮这个表。

**子弹2|文本靠分隔符、二进制靠长度**:HTTP 头 \r\n 靠分隔、body 靠 Content-Length、MJPEG 帧靠 boundary、RTP 定长头+序号——四种机制四个例子,一条 TCP 上全齐。

**子弹3|Range 全链**:Range 头 → 解区间 → lseek → 206/Content-Range/Accept-Ranges;接 fMP4:moof 索引算区间、Range 拉区间——存储格式和回放协议的握手点。

**子弹4|帧率一鱼两吃**:web_mjpeg_fps 既是预览帧率又是仓库生产速率(热更五路里直接喂 target_fps),改预览流畅度,AI 的取样率跟着变——这是配置项背后的真实耦合,说出来是深度。

**子弹5(边界话术)|套接字生命周期、锁的细节是主线 3.x 的活,问到就停**:「这块我梳理到函数功能级,逐分支的失败矩阵还没铺完。」——诚实停比编强。

**边界声明**:本条 RTSP 半边概念层+字节卡层(附块B);HTTP 半边函数功能级。实现层(套接字生灭/慢客户端策略/Range 规范边界/各 serve_* 失败矩阵)留主线 3.x。

## ⑤ 云事件 + 热更新(主口述约 90 秒;含实情精修)

云端链路是完全独立的旁路线程,和拉流线程唯一的接触点就是快照仓库:隔一段去取最新一张——注意节奏是「云耗时加间隔」的下限节流,云慢它就慢,不装固定节拍。取到图 base64 塞进 JSON、HTTPS 调多模态接口,拿回结构化事件:是 none 就丢,真事件才走发布——入库、快照落盘、同步回调报警点 GPIO。云超时失败,影响只有一样:**那段时间窗的识别覆盖没了**(丢的是覆盖不是一帧);拉流、录像、预览一点不耽误——生产消费在仓库那儿早就解耦,慢的代价从「延迟」变成「漏看」,而漏看不伤实时性。

热更分两类,能推的五路:日志、报警、云 AI、预览帧率、分段时长——但注意两处实情:**分段时长是下一段才生效**(recorder.c:206 日志原话【精修#10】);云 AI 那路里六个字段命运不同——每次现读的真热了(timeout/prompt/model/base_url,c:223/249),取帧间隔在循环外算死的是半热(ai_fps,c:302),token 干脆不在白名单里【精修#11:enable 另走启停通路】。要重启的一类:监听端口、拉流源。token 为什么不热?不是敏感掩码的事(掩码是 web 侧 UI 防回写,web.c:775/805),是凭证的原子性:地址在白名单里钥匙不在,同时换就是新地址配旧钥匙、401 错配——换钥匙要停机确认,和调参数是两回事。

### 子弹

**子弹1|token 机制**:reload 白名单六字段(c:355-363),token 不在其中(c:354 注释自认保留原值);错配窗口=base_url 热而 token 冷,这就是「半套凭证不可分批生效」的实体。

**子弹2|失败影响粒度**:丢的是时间窗的覆盖,不是一帧;边界=只伤识别,不反压三腿。

**子弹3|五路生效时序**:四路立即,分段时长「下一段生效」(recorder.c:206)。

**子弹4|诚实答案(三命运版)**:被问「热更都真生效吗」——现读的真热(timeout/prompt/model/base_url)、算死的半热(ai_fps,间隔循环外算一次)、凭证的不来(token);frame_grabber 侧 fps 现读、cloud_ai 侧 fps 冻结,两 fps 两命运是它的子集。

**子弹5|报警路径**:publish 锁内拷订阅列表、解锁后同步回调——报警动作借发布者的栈执行,GPIO 灯和蜂鸣器。

**收尾金句**:「云端线程是整条链上唯一敢慢的角色,因为它消费的是快照不是流——慢只会漏看,不会拖慢任何人。热更白名单三命运:现读的真热、算死的半热、凭证的不来——调参数和换钥匙,从来是两件事。」

**边界声明**:本条到函数功能级+热更实情;event_bus 锁内快照 I/O(审计①)、publish 失败路径、cloud_ai_stop 时长等深挖留主线 2.3A/2.4。
