## 四、条目① 零转码录像与掉电可恢复存储【A 档·深挖】

**简历原文**:「录像路径不解码、不转码，只做压缩域重新封装（remux），CPU 开销近零。按关键帧边界切分为多个视频段，每段采用 fragmented MP4，封装索引随各 fragment 就近写入而非集中压在文件尾，已写完的 fragment 在掉电后仍可播放。磁盘剩余低于水位时，按时间顺序删除最旧段，并保留正在写入的段，循环覆盖。」

**提问入口(五个分句=五组问题)**:

| 分句 | 直问 | 变式/陷阱追问 |
|---|---|---|
| 不解码不转码只 remux | 「remux 和转码差在哪?为什么这里能不转码?」 | 「remux 时对码流到底动了什么?真的一个字节没动?」(不是零动作——每包重打时间戳,动的是元数据不是压缩数据) |
| 按关键帧对齐切段 | 「为什么段首必须等关键帧?」 | 「到了设定时长还没等来关键帧,切还是不切?」(继续写旧段,段长略超——精修#6)/「frag_duration 兜底是干嘛的?」(没关键帧也强切,防单 fragment 无限膨胀) |

**① 机制层(60 秒骨架,A 档;选作开场深挖行时扩到 90 秒)**:端侧硬件编码后的 H.264 经 RTSP 到边侧,录像路径拿到码流包后不解码,只换封装容器——裸流装进 MP4,做的仅仅是每包重打时间戳(时基换算);文件按关键帧对齐切段;fMP4 索引随各 fragment 落盘不压文件尾;磁盘低于水位时按文件名(=时间序)排序删最旧、跳过正在写的段。

**② 选型层**:
- remux vs 转码:800MHz 单核无 VPU,软解再编码打满 CPU;源已是 H.264,录像要的只是「装进可拖动的容器」,不需要碰像素——CPU 只花在封装与时间戳上。
- fMP4 vs 普通 MP4:普通 MP4 总目录 moov 压文件尾,7×24 录像永不「写完」,掉电=整文件报废;fMP4 先写静态空目录(empty_moov),数据按 fragment 落、各带小目录 moof——写到哪完整到哪(完整=fragment 粒度且已落盘,⑯;附块B 布局图,白板可默画)。
- 关键帧切段:P 帧参考链向前找,段首非关键帧=开头缺参考帧不可解码;等关键帧=每段独立可播。
- 删最旧+跳当前:见提问入口;额外一层:recorder 段名等宽(`%s_%04d%02d%02d_%02d%02d%02d_%02d.mp4`),所以 alphasort 安全——同一个 scandir+alphasort 套路,event_bus 复刻时把等宽命名丢了才翻车(#21),「复刻套路要复刻不变量」。

**③ 事故层**:
- **C1 码率恒 0**(#1,独立发现):write 接口成功即接管包并置空(FFmpeg 所有权契约),之后才读 out->size 恒 0;修=写前存局部变量。只伤统计不伤数据——影响面先说清显轻重。
- **C3 时基假定**(#2/锚点⑬):输入时基硬编码 1/90000(RTSP 恰好撞对所以能跑),换时基源=变速播放(600s 段内部 6.7s 的矛盾反推);修=把 AVRational 传进 recorder(转发腿传了,recorder 接口没接);归属=审计+注释修正双层都是我的,大方认领。
- **C2 熔断稀释**(#6):盘满开段失败→等待关键帧路径 return 0(语义=「成功」)→调用点清零计数→超 20 永远凑不齐。「返回 0 身兼两职——『写成了』和『我在等关键帧』,灾难场景下第二个含义把第一个的账本冲掉了。」

**④ 陷阱层**:
- 掉电三档(附块B 子弹3):头没写完=段没影;文件头还在的前提下,完整落盘的都能播——播到最后一个完整 fragment 为止;正在写的坏。正常切段写 trailer,段尾干净。
- 两笔丢的场景区分(精修#6):等待期主动丢只发生在首段启动/开段失败重试;**正常业务切段不丢**。
- CPU 数字防线:「CPU 近零?多少?」→ 不编数字,相对论证(不解码不转码,只有封装与元数据级开销)。
- 「裸 H.264 不能直接播吧?」→ 精修#12:VLC/ffplay 能顺序播,缺的是索引和时长,拖动不可靠、通用性差——别说死。

**⑤ 延伸层**:录像段索引顺带落 sidecar/数据库,加速 Web 按时间检索;上位句:压缩域的事在压缩域做,只有需要像素的旁路才付软解的代价。

**弹药定位**:04③+附块B(布局图/三旗一兜底/NALU 头)/ 05 应答卡 C1、C3 / 02 台账 #1、#2、#6 / 锚点⑬⑯ / 八股 03(录像 9 卡)。

## 五、条目② 一次拉流三路分发【A 档·深挖】

**简历原文**:「单拉流线程将同一路码流同步分发给录像、抽帧和转发，全程仅一次拉流。码流包由拉流线程统一消费与释放，下游只借用不持有；抽帧模块持续解码以维持 H.264 参考帧有效，任意时刻只保留最新一帧 JPEG。预览与识别以深拷贝取得该帧并自行释放，最新帧缓存为单写者多读者。」

**提问入口(五个分句=五组问题)**:

| 分句 | 直问 | 变式/陷阱追问 |
|---|---|---|
| 单拉流线程同步分发 | 「录像、抽帧、转发是三条流水线三个线程?」(不——一次取包,同一循环里三次函数调用) | 「为什么不三个线程各拉各的?」(三路连接三份码流,重复成本)/ ⚠️「一条腿卡住,三条全卡?」(认代价+点名最重腿+三层兜底,04① 子弹5) |
| 包由拉流线程使用并归还 | 「包给三家,每家复制一份吗?」(一借一克隆一借:录像克隆引用、抽帧借用喂解码器、转发纯只读) | 「谁负责释放?怎么防双重释放?」(三家当场调用当场返回,循环末统一释放;克隆给录像正因为 MP4 写接口要接管包) |
| 抽帧维持参考链 | 「能不能跳包解码省 CPU?」(不能:P 帧存的是与上一帧的差,跳一包花一个 GOP) | ⚠️「那节流放解码前不就省了?」(#52 误区复发点:解码全量、出图按需——解码为了对,节流为了省,位置就不同) |
| 只保留最新一帧 JPEG | 「为什么不上队列?」(下游要「现在」不要历史,丢旧保新=内存恒定+延迟恒定) | 「这算背压吗?」(不算——丢弃是背压的替代;判断标准一句话:消费者变慢后生产者有没有跟着慢。附块A) |
| 深拷贝+单写者多读者 | 「读者读到一半,写侧覆盖/扩容怎么办?」(双保证:锁防撕裂+拷防悬垂,缺一不可) | 「为什么不用引用计数/读写锁?」(几十 KB 平字节引入 refcount 复杂度不值;写者只有一个、读者低频,互斥锁的简单性值这个开销)/「读到的尺寸和缓冲配套吗?」(#9 曾不配套) |

**① 机制层(60 秒骨架,A 档;选作开场深挖行时扩到 90 秒)**:拉流线程每读出一个视频包,就在同一个循环里依次交给三家:录像(克隆引用——MP4 写接口要接管包)、抽帧(借用——喂解码器,解出的画面是新内存)、转发(纯只读);三家同步借还,循环末统一释放——**码流三路零队列,但锁不零**:JPEG 仓库读写共一把互斥锁(见本层末句),口试别把「零队列」连读成「零队列零锁」。抽帧解码器全量吃包保参考链,到目标帧率才做缩放+JPEG 编码两件贵活;JPEG 仓库只存一张,三个读者(AI 线程/预览流/抓拍接口)锁内 malloc 深拷贝拿走所有权自行释放。

**② 选型层**:
- 同步扇出的「否」:三路独立拉流(三连接三份码流);队列分发(内存无界+延迟累积+多一把锁)。零队列同步扇出的代价=旁路成本回到主路(⑫,见陷阱)。
- 单槽覆盖的「否」:队列(见提问入口);「丢帧本身就是背压的替代」——生产节奏纹丝不动,消费慢就丢。
- 深拷贝的「否」:只锁不拷=悬垂,只拷不锁=撕裂(精修#3 双保证);引用计数(复杂度不值,AVBufferRef 那套是给跨模块共享用的)。
- 三腿三脾气(失败策略分立):录像不能丢(阻塞写+写错 20 次断线重连)/转发不能慢(UDP 发不出丢这帧、TCP 慢客户端连续失败超 3 次踢)/抽帧只要最新(覆盖不反压)。

**③ 事故层**:
- **#9 get_jpeg 锁外重读尺寸**(独立发现):解锁后又读一次 g_jpeg_size,返回值与 buf 不配套=越界读窗口——「单写者多读者」句的正反面教材,正好证明我审计过自己的说法。
- **#15 malloc 契约半闭合**(自读发现):失败路径不写 out_param,押在调用方预初始化上。
- **⑫ 同步扇出反噬**(三方最深 L3,主动说):零队列的代价=软解+缩放+JPEG 编码(frame_grabber.c:172-187)全跑在拉流线程,解码尖峰会推迟下一包取包;改进=旁路限时丢弃/重活移独立线程。

**④ 陷阱层**:
- 「一条腿卡住全卡?」(04① 子弹5):认这个代价,点名最重的腿(抽帧的解码缩放编码+录像的 SD 卡写),兜底三层(节流/踢客户端/熔断重连),单次慢写没超时保护——拿这个代价换不加队列不加锁的简单。
- 「预览和 AI 读的是同一个仓库?」(是;帧率一鱼两吃:web_mjpeg_fps 既是预览帧率又是仓库生产速率——04④ 子弹4)。
- 「配置里有 ai_max_queue,用了?」(暗雷:预留位没接,当前单缓冲覆盖——备着不主动说)。
- 表达层复发监控(#52/#59):「先节流再转 JPEG」「推」口径——这两处口头复发过,本条口述时重点自查。

**⑤ 延伸层**:⑫ 的两个修法;可迁移句:「锁保共享,拷保所有权」+「同步借用、异步必须复制」——判定标准是数据生命周期有没有跨线程边界。

**弹药定位**:04①②+附块A(背压与丢弃,必考概念题)/ 05 应答卡 A1 / 02 台账 #9、#15 / 锚点⑫⑭ / 八股 02、04。
**防线**:「单写者多读者」挂在 JPEG 缓存上(码流三路是同线程顺序消费,非并发读)——被问「码流也是单写者多读者?」要能分清两层(v7.10 假术语规范)。

| 六步 | 内容 |
|---|---|
| 现象 | 潜在越界读窗口,审计发现而非线上炸出来:get_jpeg 返回给调用方的尺寸可能大于它 malloc 出的那块 buf——调用方按返回尺寸读 buf 就是堆越界读。窗口窄(解锁到 return 只隔两行),所以从未实际崩过 |
| **发现过程(单列≈20 秒)** | 审计这个函数时给每个共享变量的每次读写标「锁内/锁外」:g_jpeg_size 被读了两次——malloc 用的那次在锁内(frame_grabber.c:198),return 的那次在锁外(c:206)。同一函数、同一变量、两个读点跨了锁边界,中间写侧可以换帧 |
| 根因 | return g_jpeg_size(frame_grabber.c:206)写在 pthread_mutex_unlock(c:204)之后:一致性快照在锁内取得,返回值却重新去读可能已被写侧更新的共享变量 |
| 机制原理 | 临界区的意义是「一套相关数据一次取齐」;跨出临界区后再碰共享变量,「配套」就重新交给运气。写侧 emit_jpeg_from_frame 在锁内 realloc+更新尺寸(c:159-166),后到的一帧更大时返回值>buf 实际大小,越界读方向成立 |
| 修法 | 锁内把 size 存进局部变量,解锁后 return 局部——一行改,回到「锁内一次取齐」 |
| 归属 | **学生独立发现**(02 台账#9,1.7C 08-22),可大方认领;讲点=「单写者多读者」这句简历话的正反面教材——保证是我讲述的,破口也是我审计出来的 |

**熟场景 1|资源·内存压力(malloc 失败)**:系统内存紧张,抽帧/上云路径的 malloc 失败,会发生什么?

**熟场景 2|时序·停机与业务并发(#12)**:按 Ctrl+C 停机,拉流线程正好阻塞在 av_read_frame 里,停得下来吗?

## 七、条目④ 自研 HTTP 媒体服务【A 档·深挖】

**简历原文**:「一连接一线程，慢客户端只占用自身连接线程。MJPEG 预览由服务端按固定节拍取最新帧，以 multipart 流持续推送，浏览器一次请求即可连续观看。MP4 回放按 HTTP Range 提供文件字节，播放位置由播放器按 MP4 索引换算。」

**提问入口(四个分句=四组问题)**:

| 分句 | 直问 | 变式/陷阱追问 |
|---|---|---|
| 一连接一线程 | 「Web 并发模型?」(监听线程 accept,每连接开一个 detached 线程) | 「连接多了怎么办?」(select/epoll 方向,「知道方向,项目没用」,诚实停)/「MJPEG 长连接占什么?」(一个线程,无上限保护——局域网少量客户端可接受) |
| MJPEG 对内节拍/对外 multipart | ⚠️业务高频:「为什么 Web 预览走 MJPEG 不走 RTSP?」(浏览器原生不播 RTSP;转码不现实;MJPEG 是浏览器直解的最低门槛) | 「两个方向谁在哪条腿?」(M-009:对内拉——轮询缓存;对外推——持续写)/「帧率谁定?」(节拍与 fps 双旋钮,一鱼两吃) |
| MP4 按 Range | 「回放为什么需要 Range?」(大文件分段+拖动 seek) | 「拖进度条时谁把时间换成字节?」(播放器按 MP4 索引算区间再来要;服务器只吐字节)/ ⚠️「Range 起点越界你返回什么?」(实然=静默重置为 0 而非 416——强防守题) |
| 慢客户端只占自身线程 | 「怎么做到慢客户端不拖别人?」(各占各的线程栈+内核发送缓冲) | 「那 RTSP 转发的慢客户端呢?」(⚠️跨行:锁内 send_all 会拖全部分发——正好显出两协议并发模型差异) |

**① 机制层(60 秒骨架,A 档;选作开场深挖行时扩到 90 秒)**:监听线程 accept,每来一个连接开一个线程:收包、拆请求行和头、按 Content-Length 补读 body、按 URL 分发、回响应。MJPEG 两腿:内腿=连接线程按固定节拍从帧缓存拉最新 JPEG;外腿=一次 GET 后以 multipart 持续推帧、连接不断。MP4 回放=Range 请求→206+Content-Range+lseek 给字节段;播放器 seek 时自己按 fMP4 索引算出要哪个字节区间。

**② 选型层**:
- MJPEG vs RTSP 的「否」(见提问入口,业务高频题)。
- 两腿方向 why:对内轮询=拉,对外持续推;预览帧率独立于源帧率,协议节奏固定。
- 一连接一线程 vs 单线程多路复用:简单直接,局域网少量客户端够用;epoll 是知道的方向不是用过的东西。
- Range 的分层:HTTP 字节层≠MP4 索引层——存储格式与回放协议在 seek 处握手(附块B 子弹3 延伸)。
- 分帧双机制:boundary 划界(multipart 语法)+每帧自带 Content-Length 定长——「文本靠分隔符、二进制靠长度」一条 TCP 上四个例子(04④ 子弹2)。

**③ 事故层**:
- **#25 /stream 三处裸 send 短写不处理+尾包不查**:流内错位破图;修复方案=迁 rtsp send_all(学生产出,可当场白板)。
- **token 掩码不对称回写**(GET 侧掩码 web.c:607-614/639-646;POST 侧仅拒纯「****」web.c:865-868/895-898,带前 8 字符的掩码形态靠 validate_conf 的 strstr 拦截兜住 web.c:809-813):GET 掩码防 UI 回写——「掩码是 web 侧 UI 的事」;token 不热更的真因=凭证原子性(见支撑句节)。
- **Range 越界静默重置为 0**(锚点⑨):合规菜单只有 200/416,「206 换内容」是第三种——辩护句:「我把越界起点静默重置为 0 重发,不合 416 的严格读法,但让残缺播放器拿到可用响应」。

**④ 陷阱层**:
- 「MJPEG 怎么不用 Range?」(精修#10:流无总长度,寻址无意义——与 /rec 回放的「无 Range 头=默认区间 0-」两回事)。
- 「分帧只靠 boundary 碰撞概率?」(精修#11:双机制,Content-Length 定长兜底)。

**① 机制层(60 秒骨架,A 档;选作开场深挖行时扩到 90 秒)**:云 AI 线程完全独立,隔一段取最新一张 JPEG,base64 塞进 JSON、HTTPS 调多模态接口;返回 none 就丢,真事件才发布——入库、快照落盘(evt_<id>.jpg 路径回填)、同步回调报警(判定秒回:类型命中+置 pending),GPIO 动作在专职告警线程。云超时失败只丢那段覆盖,拉流录像预览不牵连——控制流层面(单核 CPU 抢占边界见陷阱层⑲)。

**② 选型层**:
- 旁路线程的「否」:主路内联(云不可靠不能挂主路——7×24 设计先列「谁可以挂」清单)。
- 失败丢帧不重试的「否」:重试队列(积压无意义,旧帧分析出过时结果)。
- 回调秒回+专职线程(B2):「等待没有消失,只是被挪到了唯一以等待为业的线程上」;响铃期间新事件命中照样秒回——阻塞永远只在报警线程一侧。
- 事件先入库再告警:入库=事实持久,告警=易失动作,次序体现优先级。
- GPIO 配 -1=禁用该路(配置语义,一句话)。

**③ 事故层**:
- **审计① publish 锁内四盘 I/O**(编号外,贯穿 Phase 2 主菜):INSERT/快照 fwrite/UPDATE 回填/cleanup 全在锁内,web 四条读路径共等同一把 g_lock——「锁是延迟的唯一传染媒介」(原创句);修法=缩临界区(锁内只留 INSERT+拿 id+确定性回填),交换物=long id+jpeg 所有权而非 ev 借用,代价=读者容忍半文件(孤儿取舍再现)。

- **#22 快照清理无 evt_ 前缀过滤**:外来 jpg 会被扫走。
- **⑰...⑲ event_t 借用 vs 拷贝**:修法与②的深拷贝同一思想——跨异步边界,所有权要交割。

**④ 陷阱层**:
- 「publish 不是锁外执行回调吗,怎么还会拖慢 web?」——**亮点+边界同框**(03 审查包结构裁决):回调确实锁外,但 publish 自身的四件盘 I/O 在锁内;主动交代+给修法,别等面试官拆。
