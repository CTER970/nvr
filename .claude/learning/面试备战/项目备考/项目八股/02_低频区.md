## LF-01 · 码流深水:AVCC vs Annex B、avcC

**知识点**:同一份 H.264 两种封装形态:Annex B 用起始码分隔 NALU(裸流/TS);AVCC 用 4 字节长度前缀(MP4/FLV),文件头部带一份 avcC 配置记录(存着 SPS/PPS 与版本信息)。辨认:看 NALU 之间是起始码还是长度。

**口述**:"Annex B 是裸流形态,起始码分隔;MP4 里是 AVCC,每个 NALU 前面是 4 字节长度,头部还有一份 avcC 记录存着 SPS/PPS。给三段字节,看开头是起始码还是长度就能认形态。两形态互转就是起始码和长度的互换——我们项目 parse_nalus 想兼容两者,边界处理不全是登记在案的(#10 偏移差一位)。"

**追问**:"avcC 结构?" → 版本/Profile/兼容/level + SPS/PPS 各带长度前缀;加分层,深挖再放。

## LF-02 · MP4 深水:trun/tfdt

**知识点**:moof 的 traf 三件套:tfhd(默认参数)、tfdt(本 fragment 媒体时间基点)、trun(样本表:每样本 duration/size/offset)。fMP4 随 fragment 走的索引就是它们。

**口述**:"fragment 的索引就是 traf 三件套:tfhd 放默认参数,tfdt 记这个 fragment 的媒体时间起点,trun 是样本表——每个样本多长、多大、偏移多少。fMP4 能边录边播,靠的就是这套索引跟着数据走。"

**追问**:"tfdt 和 PTS 什么关系?" → fragment 基点+样本偏移合成每帧时间;备一词即可。

## LF-03 · faststart

**知识点**:moov 在文件头的 MP4 是后处理产物(ffmpeg `-movflags faststart`):录完把 moov 搬到头部,利于网络点播边下边播。

**口述**:"下载的 MP4 moov 在前面,那是 faststart 后处理——录完把索引搬到文件头,方便点播边下边播。7×24 录像没有'录完'那一刻,做不了这种后处理,所以只能 fMP4,让索引跟着 fragment 走。"

**追问**:无固定追问;被问"moov 为什么常在尾"→ 边写边录无法预知全部索引。

## LF-04 · 字典序删旧陷阱

**知识点**:按文件名排序走 strcmp 字典序:等宽数字串字典序=数值序;不等宽时 "9">"10" 错序→删新留旧。evt_id 自增不补零=跨位数错序缺陷(#21)。

**口述**:"删最旧按文件名排序,而排序是字典序不是数值序——'10'排在'9'前面。录像段名是等宽时间戳,字典序恰好等于时间序,安全;事件快照的 evt_id 是自增不补零,从两位数涨到三位数那天排序就翻车,删掉的是新的——登记在案的缺陷,修法补零。"

**追问**:"等宽为什么就安全?" → 同长度无前导差异,逐字符比较等价数值比较。

## LF-05 · 两票模型与幽灵文件

**知识点**:文件两条链:名字链(目录项→inode)、打开链(fd→inode)。unlink 撤名字票;空间释放要 nlink=0 且最后一个 fd close(两票全撤)。df 看空闲块位图,du 按目录走访名字——两口径在"名字没了 fd 还在"的中间态会打架。

**口述**:"删一个打开着的文件,unlink 只摘名字——名字链断了,但还有进程拿着 fd,inode 两票没全撤,空间不还,df 看着没变;等它 close,空间当场蒸发。这就是 df 和 du 打架的机制根。我们跳过'正在写的段'防的就是这个:删了也白删,磁盘不会多出一字节。"

**追问**:"幽灵文件?" → 名字没了 fd 还在的中间态:ls 看不见、du 找不着、df 不还。

## LF-06 · 位图/TRIM/匿名文件

**知识点**:删除=空闲块位图标回可分配,数据没擦,覆盖才消失;SSD/eMMC 的 TRIM 提前归还块给磨损均衡,误删可恢复打折。匿名文件=open 后立即 unlink:无名,close 自动回收,tmpfile() 惯用法。

**口述**:"rm 毫秒级完成,是因为只改位图不做擦除——数据还在,覆盖才真消失,所以误删有救;但 SSD 有 TRIM,提前把块还给磨损均衡,救回来的概率打折。还有个标准惯用法:先 open 再立刻 unlink,成了匿名文件,没名字、close 自动回收,tmpfile 就是这么造安全临时文件的。"

**追问**:"目标平台受影响吗?" → TF 卡/eMMC 属 TRIM 类,护边一句。

## LF-07 · 协作式取消与优雅停机

**知识点**:线程没有"被杀"这回事(信号杀的是进程);优雅停机靠标志+检查点(协作式取消)。判据:取消延迟有界⟺执行流里存在观察点。观察点三层安插:自己循环/对方库内部(配超时)/进程级 kill(唯一真抢占边界)。pthread_cancel 推迟取消+取消点是同族机制。

**口述**:"优雅停机没有'杀线程'这回事——信号杀的是进程。线程想停得体面,得自己在循环里看标志:协作式取消,标志是通行证,检查点是关卡。麻烦在卡关:线程睡在一个没有检查点的阻塞调用里——比如无超时的网络读——它永远路过不了关卡,join 就被无限期抵押。判据一句话:取消延迟有界,当且仅当执行流里存在观察点;没有就三层安插:自己代码加、给库配超时、最外面进程 kill。"

**追问**:"pthread_cancel 呢?" → 推迟取消+取消点,同族机制,坑多不优先。
"标志位加 volatile 就够了吗?" → 不够。volatile 只阻止编译器把读优化掉,不提供原子性,也不能替代锁。停机仍要在 mutex 里 cond_signal,告警线程才会从 cond_wait 出来(alarm.c:143-145)。

## LF-08 · join/detach/shutdown 机制链【☆】

**知识点**:join=等线程退场并收尸;detach=声明无人收尸,退出即回收;shutdown(fd)=关 socket 读写,能就地唤醒阻塞在该 fd 上的 recv/accept。detached 线程无人 join——停机时在途工作无人等也无人拦。

**口述(材料版)**:"join 是等收尸,detach 是声明弃养——退出即回收,谁也不等。所以停机时 detached 的连接线程在途干什么,没人知道也没人拦:我们 Web 停机只 join accept 线程,在途的 POST 会走完校验、落盘、热更新、回 200 全链——这是我审计推翻旧口径的发现。另一件工具是 shutdown:对监听 fd 调它,能把阻塞在 accept 上的线程就地唤醒,比等标志位快——标志位要等线程自己醒来去查。"

**追问**:"detach 了还能 join 吗?" → 不能,二者互斥;要可等待就别 detach(修法=记 tid 可跟踪)。

## LF-09 · join≠kill、停止延迟双例

**知识点**:join 不中断目标线程,只等它自然跑到退出点;停止延迟=对方最长阻塞时长。安全(数据不损)与快(停得干脆)是两个维度。

**口述**:"join 不是 kill——它不打断对方,只是排队等人家自己跑到退出点。所以停止延迟由对方最坏阻塞决定:告警线程秒级轮询,最坏等一秒;识别线程睡在 HTTPS 上,最坏押一个 30 秒超时。要快就得给阻塞配超时或唤醒,那是另一套活——安全和快是两个维度,分开论证。"

**追问**:"停机顺序谁定的?" → main 里约定序(web 最先、总线最后),是约定不是机制。

## LF-10 · 深拷贝链失败语义

**知识点**:多层拷贝链中途失败:已挂靠到父对象的能被统一释放;挂靠前失败的谁也够不着=泄漏。"挂靠顺序决定可达性"。内存放大:JPEG→b64(×4/3)→data_url→json,约 5 倍。

**口述**:"一条深拷贝链上,每层失败的样子不一样:已经挂到父对象上的,释放父对象能连带清掉;还没挂靠时失败的,谁也够不着它——泄漏。所以排查看挂靠顺序,不是数 malloc。我们那条链四层,内存放大五倍,两处深层小分配的漏点是登记在案的,报号 15 和 16。"

**追问**:"#16 怎么发现的?" → json_object_put 清不到未挂靠的 content——挂靠顺序铁证。

## LF-11 · SQLite 与锁

**知识点**:嵌入式单文件库,无服务进程,零运维;库级写锁(写写互斥);BUSY 默认立即失败,busy_timeout 改排队;serialized 线程模式=全库互斥;WAL=写不堵读(交底:未实操)。

**口述**:"选 SQLite 因为它是嵌入式的——库直接链进进程,单文件零运维,不上 MySQL 那套服务。并发上它是库级写锁,写写互斥,BUSY 默认立刻失败,想排队给 busy_timeout。我们外层自己一把大锁先串行化了,真正到 SQLite 层的并发根本到不了——库锁是备而不用的第二道。WAL 模式写不堵读,我知道概念,没实操过。"

**追问**:"和 MySQL 什么时候换?" → 数据量大/多进程共享/要网络访问时。

## LF-12 · 热更新三栏表

**知识点**:配置字段三分:循环内反复消费的(log 级别/分段秒/抽帧率/告警参数)→改完即热;只在启动消费的(bind/源地址/路径)→须重启;表面热实则不生效的(ai_fps:运行中间隔是启动快照)。判定法:生效时点=消费时点。

**口述**:"哪些配置能热更新,判定法一句话:生效时点等于消费时点——消费者下一次读这个值时,能不能拿到新的。日志级别、分段时长这些,消费点在循环里反复读,改完就热;监听端口、拉流地址,只在启动时消费一次,改了要重启。还有一类看起来热其实不热:ai_fps,运行中的线程启动时把间隔取成了快照,改完纹丝不动,得重启识别线程——这是个审计发现。"

**追问**:"怎么修 ai_fps 这类?" → 每拍锁内重读重算;或开关翻转重启线程。

## LF-13 · token 掩码不动点

**知识点**:GET 响应回显 token 掩码后,若前端把掩码串原样 POST 回来,写路径不区分"掩码"与"新值",真 token 被覆盖。不动点=回显值与存储值共用同一条写路径。

**口述**:"掩码回显的坑在写回:界面拿到的是打码的串,用户不动它直接保存,打码串就被当成新 token 写进配置——真 token 没了。机制根是'回显值'和'存储值'走了同一条写路径,分不开。修法要么前端不回传掩码字段,要么后端识别到值等于掩码就不写。这是登记在案的发现之一。"

**追问**:无固定追问;归属=审计战绩。

## LF-15 · RTSP vs RTMP/HLS/WebRTC【☆】

**知识点**:RTSP/RTP=会话级流协议,低延迟,安防/局域网事实标准;RTMP=TCP 推流协议,直播推流时代标准,渐退;HLS=HTTP 切片(ts+m3u8),穿透与 CDN 最友好,延迟秒级起步;WebRTC=浏览器实时,栈重。

**口述(材料版)**:"安防这个场景 RTSP 是事实标准,播放器生态都是它;RTMP 是直播推流那代标准;HLS 走 HTTP 家族,穿透最好但延迟秒级起步,监控受不了;WebRTC 面向浏览器实时,栈重。我们的选择是轻量 RTSP 子集——够用、可控,不上 live555 这种大家伙。"

**追问**:"为什么不用 live555?" → 轻量需求+可控性,约 600 行子集覆盖当前量级(送分伏笔)。

## LF-16 · 线程 vs 进程选型【☆】

**知识点**:线程共享地址空间:数据共享零成本、切换便宜;代价=崩溃互染(一崩全崩)。进程隔离好,但共享要过 IPC(序列化成本)。本项目单守护进程多线程:帧仓库/事件总线/配置共享密集,嵌入式资源受限。

**口述(材料版)**:"选多线程是因为这条链路的数据共享太密集——帧仓库、事件总线、配置,线程间天天传数据,放进程里全要过 IPC,序列化代价立刻上来。代价是隔离弱:一个线程写崩栈,整个守护进程陪葬。监控网关要的是省资源加共享密,单进程多线程合适;要故障隔离是进程和看门狗那一层的事。"

**⑦ 状态**:☆新建材料版 2026-09-28。

## LF-17 · 线程池/信号 handler/valgrind 三句【☆】

**知识点**:线程池=预建复用,省创建销毁、顺带控上限;按需创建=简单,量小够用。信号 handler 里只能调异步信号安全函数(printf/malloc 都不行)。valgrind/ASan=内存错误运行时检测(泄漏/越界)。

**口述(材料版)**:"线程池省的是反复创建销毁的开销、顺带控上限;我们十几个连接的量级,按需创建的浪费可以忽略,简单就是收益。信号处理函数里只能调异步信号安全的那一小撮函数,printf、malloc 都不能碰——所以停机不走信号,走标志位。内存排查,工具层面 valgrind 查泄漏、AddressSanitizer 查越界是标准答案;我项目里是手工审计的路子,两条深层的漏点就是这么抠出来的。"

## LF-18 · FFmpeg 与发送细节

**知识点**:解码是 avcodec_send_packet / avcodec_receive_frame 两头循环,一包可出多帧(所以收要 while);两侧 EAGAIN 含义不同(send_packet=先收帧,receive_frame=再送包)。另一头是 socket send:正常态拷进内核缓冲、微秒级返回,阻塞只在缓冲满;短写=返回值小于请求量,须循环补。CLOCK_MONOTONIC 单调,不受改墙钟影响。

**口述**:"FFmpeg 解码是两头循环:avcodec_send_packet 送一个包,avcodec_receive_frame 可能吐好几个帧,所以收要 while。两头的 EAGAIN 不一样——send_packet 说输入满了、先收帧,receive_frame 说还没有新帧、再送包。另一头是 socket 的 send:正常态把数据拷进内核缓冲、微秒返回,阻塞只在缓冲满;返回值小于请求量叫短写,得循环补齐。计时一律 CLOCK_MONOTONIC,墙钟会被改,单调钟不会。"

**追问**:"为什么要重打时间戳?" → 跨容器时基不同(→ HF-10)。

## LF-19 · Web 停机族

**知识点**:web_start 返回 0≠已监听(bind/listen 在子线程异步做,失败不回传);shutdown 监听 fd 唤醒阻塞的 accept;cfd 谁创建谁关。MJPEG 断流两死法:上游断流=10s 空仓有界断开(前端亮无信号);慢客户端=无限期冻结(单槽覆盖,丢帧不积压)。

**口述**:"web_start 返回 0 只代表线程派出去了,bind、listen 在子线程里异步做——失败了没人告诉你,这是自研服务常见的坑。停机用 shutdown 戳监听 fd,把睡在 accept 上的线程就地叫醒,比等标志位快。连接 fd 谁创建谁关,提前 return 不漏关靠统一出口。MJPEG 断流分两种死法:上游断流,10 秒空仓有界断开,前端亮无信号;客户端自己慢,那是无限期冻结——旧帧死在仓库的覆盖里,不死在管道的积压里,代价是丢帧不是延迟累积。"

**追问**:"两种定格怎么区分?" → 看上游:空仓超时=上游断;空仓不超时但发送慢=客户端慢。

## LF-20 · 事件族 + 尾包一句

**知识点**:none 过滤是 cloud_ai 发布前的自律,不是 event_bus 对所有发布者的强制规则;事件有效期=借用(同步支路)vs 拷贝(异步落盘)两支各自保证;云端故障六类:连不上/超时/非 200/解析失败/无结果/none。尾包:MQTT 预留未实现;SQLite 索引=查询加速、事务=原子;libcurl easy 四步 init/设参/perform/cleanup;守护进程化=启动脚本层。

**口述**:"'none 不入库'是识别模块发布前自己过滤,不是总线的强制规则——新发布者发 none 照样进库,这个边界要说清。云端故障六类:连不上、超时、状态码不对、解析失败、无结果、none,各走各的下线和日志。libcurl 用的是 easy 同步接口,四步就是 init、设参、perform、cleanup。其余一句:MQTT 预留了没实现;SQLite 索引是查询加速、事务保原子;守护进程化是启动脚本层的事。"
