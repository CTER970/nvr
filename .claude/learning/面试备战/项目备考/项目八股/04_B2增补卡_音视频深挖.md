## 卡 BV-01 · V4L2 三种内存模式与 cache 一致性(高频 · 采集深挖)

**① 知识点是什么**
V4L2 用户态拿缓冲的三种方式:MMAP(驱动申请、映射给应用,最常用)、USERPTR(应用自己 malloc、注册给驱动)、DMA-BUF(跨设备共享同一块物理缓冲,camera→编码器/显示直连,零拷贝的关键)。三者都要遵守同一条纪律:**DQBUF 取出→用完立刻 QBUF 归还**,应用只碰自己那份内存。带 cache 的场景(尤其 DMA-BUF/非 cache-coherent 路径)要处理一致性:CPU 读过要 flush、外设写过后 CPU 读前要 invalidate,否则看到旧数据。

**② 面试官怎么问**(B2 原题)
- 「V4L2 的 MMAP、USERPTR 和 DMA-BUF 三种内存模式有什么区别?」(地平线/星尘系原题)
- 「DMA-BUF 场景中的 cache 一致性如何处理?」
- 「linux 的 v4l2 子系统框架、核心层注册流程(v4l2_device/v4l2_subdev)、media 拓扑、设备树中如何关联(link/pad)」(中兴领军 B2-42——注意:这是驱动层问题,应用岗答到边界即可)
- 「DMA 和 CPU 和 cache 之间的关系?」(富瀚微 B2-44,合辑)
- 「DMA 搬图像的时候 CPU 同时访问那块内存会冲突吗?怎么处理?cache 一致性是怎么回事?」(字节 PICO B2-34)

**③ 口述回答**
"三种模式的差别在'缓冲是谁的'。MMAP 是驱动申请、映射到用户态,我们项目用的就是这种;USERPTR 是应用自己分配、把指针注册给驱动;DMA-BUF 是导出一个句柄让多个设备共享同一块物理内存,camera 直连编码器或显示就走这条路,省掉一次拷贝。共同纪律是 DQBUF 取、QBUF 还,取帧期间驱动不碰这块内存。cache 一致性是另一个问题:外设 DMA 写过的内存,CPU 读之前可能要 invalidate,CPU 写要给外设看的要 flush,否则各看各的 cache 就是数据对不上——非 cache-coherent 路径上必须显式做,coherent 路径硬件保证。"

**④ 高频追问 + 接法**
- "你们项目用的哪种?" → "MMAP。取出后按本帧有效字节拷进应用内存,**随即归还驱动缓冲**,解码、刷屏、上传只用应用内存——这样驱动缓冲永远够用,不会因为消费慢把采集卡死。"(→ BV-05)
- "零拷贝怎么做?" → "要么 USERPTR/DMA-BUF 让上下游共享同一块缓冲,要么像我们项目在应用层做所有权划分:拉流线程统一持有码流包,下游只借用不持有,需要跨线程长期用的才深拷贝。"(→ BV-03)
- "media 拓扑/设备树关联了解吗?"(驱动层追问) → "应用岗我了解到 v4l2_subdev 注册、pad/link 描述拓扑这一层,再往里的 sensor 上电时序和设备树节点是驱动/BSP 的活,我没有一手经验——但我知道应用层看到的是 /dev/video 节点,ioctl 协商格式。"(停在边界,不硬凹)

**⑤ 项目实然锚点(自查用)**
- 采集终端:V4L2 流式采集 mmap 缓冲轮转、poll 等帧就绪、DQBUF/QBUF 配对归还(简历技能行原文);取出即拷入应用内存随即归还(简历「缓冲归还」段)
- NVR:抽帧持续解码维持参考帧(应用层 demux/dec,不经 V4L2)
- 端侧 V821 的 MIPI CSI→ISP→VENC 为原厂链路,项目侧只做 RTSP 收流——答端侧时明确"原厂 SDK 封装,我在边侧"

**⑥ 坑点一句**
别说"DMA-BUF 一定比 MMAP 快"(要看有没有拷贝瓶颈,单消费者场景 MMAP 足够);别说"cache 一致性内核都会自动处理"(非 coherent 路径要应用/驱动显式 sync);被问驱动层细节时别硬凹——应用岗承认边界是加分项。

**⑦ 状态行**
来源=B2-34/B2-42/B2-44/B2-46+星尘系(已剔样本但题为真);预生成首版 2026-10-18;未开始。

## 卡 BV-02 · 一帧图像的完整链路(高频 · 图像岗主深挖)

**① 知识点是什么**
从光子到屏幕的一条主链:**sensor 曝光 → MIPI CSI-2 并口串行化 → CSI 接收 → ISP(去马赛克/3A/降噪/畸变校正) → DDR Buffer → 应用/编码器处理 → 显示(合成→刷屏)**。每一段都有延迟和带宽成本:MIPI 比并口好在 lanes 多、抗 EMI、线束少;ISP 决定画质也是最大延迟段之一;DDR 是必经的总线瓶颈;显示段有合成和 VSync 等待。面试问"经过哪些环节"考的是能不能把 pipeline 画出来、指出每段的代价。

**② 面试官怎么问**(B2 原题)
- 「一帧图像从 sensor 出来到显示出去,中间大概经过哪些环节?」(字节 PICO B2-34 二面)
- 「MIPI 了解吗?跟并口传图像比好在哪?」(字节 PICO B2-34)
- 「Sensor→MIPI CSI-2→CSI→ISP→DMA→DDR Buffer,DMA 完成一帧写入后产生完成事件,驱动如何处理?」(大疆 B2-15 二面数据通路图)
- 「摄像头硬件选型在系统设计的考虑(帧率、曝光)」(地平线 B2-01)

**③ 口述回答**
"一条链:sensor 曝光出 raw 图,MIPI CSI-2 串行化传输(比并口快、抗干扰、线少),CSI 控制器收下来,进 ISP 做去马赛克、3A、降噪,写成 DDR 里的帧缓冲,然后应用或编码器取走处理,最后送显示。我的项目两头都碰过:端侧是 V821 的 MIPI CSI→ISP→VENC H.264 原厂链路,我做边侧收流;板端采集终端是 USB 摄像头→V4L2→应用内存,然后解码、缩放、合成、刷屏,同时另一路上传。延迟上,ISP 和软件 JPEG 解码是两个大头,我们实测过分段耗时。"

**④ 高频追问 + 接法**
- "延迟主要来自哪几段?" → "端到端拆开看:sensor 曝光和 ISP 是固定成本,传输和拷贝是带宽成本,软件解码是 CPU 成本,显示还有 VSync 等待。我们板端实测 1280×720 下软件 JPEG 解码是主耗时,端到端 P95 837ms;换 640×480 MJPG 让摄像头直出 JPEG 后降到 59ms——所以优化点是'别在板端做软件解码'。"(→ BV-07)
- "USB 摄像头和 MIPI 差别?" → "USB 走 USB 协议栈,带宽和延迟都高一个量级,适合 demo/低帧率;MIPI 是并行 lane 直连,监控/相机产品都用 MIPI。我们第二个项目受平台限制用 USB,第一手踩到了它的帧率天花板(约 25fps)。"

**⑤ 项目实然锚点(自查用)**
- 简历项目背景原文:端侧 V821 经 MIPI CSI 采集→H.264 硬编码→Wi-Fi RTSP 推流;边侧 IMX6ULL 拉流
- 采集终端:USB 摄像头→V4L2→应用内存→LCD 显示 + HTTP 上传(简历项目背景+四段)
- P95 分段计时(取帧/拷贝/解码/缩放/合成/刷屏)=简历「像素预算」段原文

**⑥ 坑点一句**
别说"MIPI 一定比 USB 快所以产品都用 MIPI"(成本/距离/驱动复杂度也是选型因素);ISP 段别说太细(3A 算法是算法岗,应用岗知道"ioctl 调参、不写算法"即可)。

**⑦ 状态行**
来源=B2-34/B2-15/B2-01;预生成首版 2026-10-18;未开始。

## 卡 BV-03 · 零拷贝与模块间大数据传输(高频 · 系统设计深挖)

**① 知识点是什么**
"大数据量在模块之间怎么高效传"的标准答案谱系:共享内存(同一块物理页映射两边,零拷贝但要自己做同步)、内存映射文件/mmap、DMA-BUF(设备间零拷贝)、消息传递+引用计数(所有权转移)、以及工程上的中间态——**单次生产、多级借用,只有跨线程长期持有才拷贝**。核心判据:数据量大×帧率高时,每次拷贝都是带宽和延迟;但无脑零拷贝会把生命周期复杂度推给应用,所以真实系统是"关键路径零拷贝,边界深拷贝"。

**② 面试官怎么问**(B2 原题)
- 「图像数据量很大,怎么在模块之间高效传?零拷贝怎么做?」(字节 PICO B2-34)
- 「线程池、进程间通信、零拷贝在项目中对系统的作用」(地平线 B2-01)
- 「穿插八股:IPC 机制、V4L2 实现的底层、Pipeline 流程、modbus 重传机制、**零拷贝实现**」(中兴领军 B2-42)
- 「linux 中数据量比较大推荐哪种数据传输方式?」(TP-Link 联洲 B2-20 三面)

**③ 口述回答**
"分场景。同进程多模块:我们项目的做法是**单次生产、多级借用**——拉流线程统一从 av_read_frame 拿包并负责释放,录像、抽帧、转发三路只借用不持有,码流不建队列、不重复拉流;需要跨线程长期用的(比如给云 AI 的 JPEG)才深拷贝,取出方自己释放。跨进程:共享内存最快但是同步自理,小数据用消息队列/本地套接字。设备间:DMA-BUF。判断标准就一条——拷贝发生在多热的路径上:我们录像路径是 25fps×几 Mbps,一次不落的拷贝 CPU 吃不消,所以关键路径借用;预览帧率低,深拷贝换线程安全。"

**④ 高频追问 + 接法**
- "借用模式下谁保证包还活着?" → "生产者线程统一消费与释放,下游只在这个调用的生命周期内用;抽帧模块持续解码维持 H.264 参考帧有效,任意时刻只保留最新一帧 JPEG,预览和识别以深拷贝取走自行释放——最新帧缓存是单写者多读者结构。"
- "共享内存为什么快?坑是什么?" → "同一块物理内存映射进两个地址空间,不过内核不拷贝;但同步完全应用自理,要配信号量/互斥锁,还要处理一侧崩溃另一端怎么办。"
- "为什么不用消息队列?" → "消息队列要经过内核拷贝,码流这种大数据量每帧拷贝一遍不值得;它适合传控制命令。"

**⑤ 项目实然锚点(自查用)**
- NVR「一次拉流三路分发」段(简历原文):单拉流线程同步分发给录像/抽帧/转发,不重复拉流、不建码流队列;码流包由拉流线程统一消费与释放,下游只借用不持有
- frame_grabber:最新帧缓存单写多读+深拷贝(简历原文)
- 采集终端:两份深拷贝合计 P95 约 1ms(简历「帧所有权」段——深拷贝的成本有一手数字)

**⑥ 坑点一句**
别说"零拷贝就是 mmap 一下"(mmap 只是手段之一,所有权和生命周期才是难点);别把项目说成"全程零拷贝"——frame_grabber 就是深拷贝换安全,那是设计选择不是缺陷。

**⑦ 状态行**
来源=B2-34/B2-01/B2-42/B2-20;预生成首版 2026-10-18;未开始。

## 卡 BV-04 · YUV/RGB、双缓冲与 VSync、画面撕裂(中频 · 图像岗)

**① 知识点是什么**
YUV 亮度和色度分离,利用人眼对色度不敏感做 4:2:0 子采样,数据量比 RGB 小一半左右,所以传输和存储爱用 YUV;RGB 每像素三分量,显示/图像处理直接用它。缓冲策略:单缓冲=生产和显示抢同一块(撕裂);双缓冲=生产写后台、显示读前台,VSwap 交换,可能浪费一次合成;三缓冲=多一个待显队列,掉帧和卡顿更平滑。撕裂来自显示读到一半被写入;VSync 是显示控制器的场同步信号,应用/合成器在 VSync 前后切换缓冲,避免撕裂。

**② 面试官怎么问**(B2 原题)
- 「YUV 和 RGB 的区别?为什么传输和存储爱用 YUV?」(字节 PICO B2-34)
- 「双缓冲和三缓冲是干嘛的?」(字节 PICO B2-34)
- 「画面撕裂是怎么产生的?帧同步是怎么回事?VSync 在里面起什么作用?」(字节 PICO B2-34)

**③ 口述回答**
"YUV 把亮度和色度分开,色度可以子采样到四分之一,数据量小一半,传输和存储都省,所以编码和摄像头输出基本都是 YUV;RGB 每像素三分量,显示和大多数图像处理直接用 RGB,转换在需要的地方做。缓冲上,单缓冲生产和显示抢同一块会撕裂;双缓冲是一块写一块显,VSync 到了交换;三缓冲再多一个待显队列,生产不等显示,掉帧时更平滑。撕裂的本质就是显示扫描读到一半缓冲被换了,VSync 就是给'换缓冲'这个动作定的安全时点。"

**④ 高频追问 + 接法**
- "你们项目显示用的什么缓冲?" → "采集终端是 LCD 直刷,双队列丢旧保证显示线程拿最新帧;没有做三缓冲那么细,平台限制下先保帧率。"(→ BV-05)
- "YUV 有哪些格式?" → "常见 packed 的 YUYV,planar 的 I420/NV12/NV21——NV12/NV21 是 UV 交织,硬件和 GPU 偏好;I420 是三个平面。JPEG 直出走的是压缩域,到应用层先解成其中一种。"(→ HF-12 ☆待补卡现在有 B2 原题支撑了)

**⑤ 项目实然锚点(自查用)**
- 采集终端:摄像头实际输出 1280×720,可选 MJPG 直出(简历「像素预算」段);显示约 6fps→24fps 的优化故事
- NVR:MJPEG 预览是 JPEG 域,不涉及 YUV 显示链路——答时区分两个项目的域

**⑥ 坑点一句**
别说"YUV 一定比 RGB 省一半"(取决于子采样格式,YUV444 不比 RGB 小);双缓冲不等于"不撕裂"(要配合 VSync/同步交换)。

**⑦ 状态行**
来源=B2-34(二面连问三题);预生成首版 2026-10-18;未开始。**附带价值:HF-12(YUV 格式族,原☆待补)现在有 B2 原题+公司实证,建议转正。**

## 卡 BV-05 · 帧缓存策略与丢帧(高频 · 项目深挖直入口)

**① 知识点是什么**
采集/处理速率不匹配时,帧缓冲有三种经典结构:**环形缓冲区(队列)**:每帧都要就存起来,满了要么阻塞生产、要么丢最旧;**单槽覆盖(latest-only)**:只留最新一帧,消费者永远拿最新的,过期帧自然丢弃;**有界队列+丢旧**:固定容量,队满丢最旧保新鲜。选型判据:消费者要不要每一帧(录像/分析→环形队列)、只要最新(预览/识别→单槽)、还是要"最近一批"(检测→有界队列丢旧)。工程红线:丢帧策略必须显式设计,不能默认阻塞——阻塞会把压力倒灌回采集线程甚至驱动缓冲。

**② 面试官怎么问**(B2 原题)
- 「摄像头驱动中,为什么常用环形队列管理帧缓存?如何避免帧丢失?」(影石 B2-40)
- 「如果摄像头采集数据速率过高,导致队列满了,丢帧怎么解决?」(影石 B2-40)
- 「ringbuffer 的水位调整」(商泰 B2-48,合辑)
- 「讲讲线程安全 Ring Buffer」(TCL B2-49)
- 「项目中多线程通信用到了什么同步机制?」(小米 B2-13)

**③ 口述回答**
"三种结构按消费者需求选。要每一帧的——录像、逐帧分析——用环形队列,满了以后是阻塞生产还是丢最旧,看业务:我们采集终端选丢旧保新鲜,因为显示和上传都只要最新状态,队满时采集线程不等、丢掉最旧帧,驱动缓冲归还不受影响,采集节奏不乱。只要最新的——Web 预览和云 AI 识别——用单槽覆盖:任意时刻只保留最新一帧 JPEG,预览和识别深拷贝取走,单写者多读者,省内存。第三种是中间态,固定容量有界队列。环形队列的线程安全靠读写索引+互斥或原子操作,单槽覆盖靠一把写锁。"

**④ 高频追问 + 接法**
- "为什么不用环形队列存预览帧?" → "预览和识别都只要最新帧,环形队列会堆积过期帧白白耗内存,还引入队列深度调优问题;单槽覆盖把'丢帧'变成隐式且免费的——新帧直接覆盖旧的。NVR 是 800MHz 单核,内存和 CPU 都紧。"
- "丢帧不丢关键数据吗?" → "录像走的是码流直写,不经过帧缓冲——抽帧是旁路,丢了只影响当次识别,下一帧补上;显示丢帧人眼不可感知。关键数据(录像)不过丢帧路径,这是设计前提。"
- "单写者多读怎么保证安全?" → "写者整帧替换+深拷贝给读者,读者拿到的是独立内存自行释放;写者只覆盖槽位指针,不做部分写入——不存在读者看到半帧。"

**⑤ 项目实然锚点(自查用)**
- frame_grabber:持续解码维持 H.264 参考帧有效;任意时刻只保留最新一帧 JPEG;预览与识别以深拷贝取得该帧并自行释放;最新帧缓存单写者多读者(简历原文)
- 采集终端:两条固定容量有界队列;采集线程入队不等待,队满丢最旧帧保新帧;实测 1280×720 采集约 25fps/显示约 6fps(简历「双队列丢旧」段原文)
- NVR 录像:remux 直写不过帧队列(区分"关键路径不丢"与"旁路可丢")

**⑥ 坑点一句**
别说"我们为了省内存所以丢帧"(省内存是结果,主因是消费者只要最新+单核 CPU 受限);别把"单槽覆盖"说成"队列深度为 1 的环形队列"(语义不同:覆盖是隐式丢弃,队列是显式缓存)。

**⑦ 状态行**
来源=B2-40/B2-48/B2-49/B2-13;预生成首版 2026-10-18;未开始。**本卡是项目深挖最高频直入口,建议第一批背。**

## 卡 BV-06 · ffmpeg 解码输出与码流结构口述(高频 · 一面直问)

**① 知识点是什么**
面试不要求会写 ffmpeg,要求能口述:输入的是什么(容器/码流)、av_read_frame 出来的是 packet(还是压缩域)、解码后是 frame(YUV/RGB PCM)、容器和码流的分工(MP4/FLV 是容器,H.264/AAC 是码流)。H.264 码流结构:NALU 单元、起始码/长度前缀、SPS/PPS(参数集,解码器初始化的前提)、IDR。H.265 同样有 SPS/PPS,另有 VPS。

**② 面试官怎么问**(B2 原题)
- 「有没有学过音视频开发、有没有自己做过项目?项目中输入的视频是什么格式、ffmpeg 解码之后是什么格式?」(大疆 B2-02)
- 「有没有了解过 h264/h265?h265 的 SPS 是什么?」(大疆 B2-02——注意:答 H.265 时先说"我一手是 H.264,H.265 结构同构")
- 「重载、重写、覆盖的区别;C++ 多态」等基础题之后的音视频延伸(小米 B2-11 相机岗同场)

**③ 口述回答**
"我们项目输入是 RTSP 拉来的 H.264 码流,av_read_frame 拿到的 packet 还是压缩域,没有解过;录像路径就是拿这个 packet 重新打时间戳、封装成 fMP4,不解码不转码。抽帧路径才解码:avcodec_send_packet/receive_frame 出来的是 YUV 帧,再编码成 JPEG 给预览和云 AI。码流结构上,H.264 是 NALU 序列,开头 SPS/PPS 带分辨率和参数集,播放器靠它初始化解码器——我们 RTSP 转发时就把源流 SPS/PPS 嵌在 SDP 里下发。H.265 我是一手 H.264 经验,结构同构也有参数集,细节没有一手踩过。"

**④ 高频追问 + 接法**
- "为什么不转码?" → "平台没有 H.264 硬解 VPU,软解 CPU 满载,而监控场景输入输出都是 H.264,remux 只重打时间戳 CPU 开销近零——这是被平台约束逼出来的设计决策。"(→ HF-04 remux 卡)
- "fMP4 和 MP4 差别?" → "fMP4 把索引拆到每个 fragment 就近写,掉电后已写完的 fragment 还能播,集中式 MP4 索引在文件尾,掉电等于全丢。"(→ HF-09)
- "SPS/PPS 丢了会怎样?" → "播放器初始化解码器失败,花屏或黑屏;所以切段必须等关键帧、转发必须把参数集带给新会话。"

**⑤ 项目实然锚点(自查用)**
- 简历技能行:FFmpeg;H.264 码流结构(SPS/PPS/NALU)与 MP4/fMP4 封装
- NVR:remux/av_packet_rescale_ts/90kHz;SDP 内嵌源流 SPS/PPS(简历 rtsp_server 段原文)
- H.265 无一手经验——答法停在结构同构层,不深入(大疆面试官对"没学过 265 直说"的应对是示范)

**⑥ 坑点一句**
别说"ffmpeg 读出来就是帧"(读出来是 packet,帧在解码后);别把 H.265 讲成一手机验(坦诚边界+结构同构,面试官认)。

**⑦ 状态行**
来源=B2-02/B2-11;预生成首版 2026-10-18;未开始。

## 卡 BV-07 · 端到端延迟分段与实时性(高频 · 深挖分水岭)

**① 知识点是什么**
"延迟"必须能拆段才算懂:sensor 曝光→传输→拷贝→解码→处理→合成→显示/网络,每段性质不同(固定成本/带宽/CPU/同步等待)。实时性分硬实时(超时即失败,如控制循环)和软实时(超时降级,如音视频)。测量方法:单调时钟分段打点、P95 分位数(比平均值抗毛刺)、区分帧内延迟和端到端延迟。优化优先级:先测量定位热点,再按"消掉最贵的一段"动手(换硬件路径比调参数有效)。

**② 面试官怎么问**(B2 原题)
- 「头显对延迟特别敏感,你觉得延迟主要来自哪几段?什么是硬实时软实时?这种场景属于哪种?」(字节 PICO B2-34)
- 「你怎么定义实时性?系统延迟实际多少、怎么测的?中断延迟由哪些部分组成、怎么优化?」(大疆 B2-15)
- 「项目中相机帧率和线程池解析的系统分析:为什么要取具体那几个参数?线程数对多核的考虑?」(字节 B2-35)
- 「如何评估操作系统的实时性?如何测算中断响应时间?」(海康 B2-04 老池同型)

**③ 口述回答**
"延迟拆成段看:曝光和 ISP 是 sensor 侧固定成本,传输和每次拷贝是带宽成本,软件解码是 CPU 成本,显示还有 VSync 等待,上传有网络往返。我有一手实测:板端 1280×720 下软件 JPEG 解码是主耗时,端到端 P95 837ms;改成 640×480 MJPG 让摄像头直出 JPEG、缩放不再触发,采集显示都到 24fps、端到端 P95 降到 59ms——优化逻辑就是'把最贵的一段(软件解码)从板端消掉'。实时性定义上,硬实时超时即系统失败,软实时超时是体验降级;监控预览是软实时,控制循环才是硬实时。测量用 CLOCK_MONOTONIC 分段打点看 P95,不用平均值——平均值会被毛刺掩盖。"

**④ 高频追问 + 接法**
- "P95 和平均值的差别?" → "P95 是 95% 的帧都快过它,反映稳定体验;平均值会被偶发长尾拉高或掩盖。我们上传往返 P95 190ms,其中 PC 推理 140ms——网络只占四分之一,所以优化不该从网络下手。"
- "线程数怎么定?" → "看任务是 CPU 密集还是 IO 密集:采集/上传是 IO 等,解码是 CPU 吃;单核平台线程多不涨吞吐只涨切换,所以我们三线程按'生产者-消费者'切分,不按核数加倍。"
- "中断延迟组成?" → "中断响应(硬件识别+向量跳转)+上下文保存+ISR 本身+退出恢复;优化靠缩短 ISR、把活挪下半部。这是驱动/BSP 侧,我了解到机制层。"

**⑤ 项目实然锚点(自查用)**
- 采集终端「像素预算」段:单调时钟对取帧/拷贝/解码/缩放/合成/刷屏分段统计 P95;1280×720→837ms,640×480 MJPG→59ms;采集显示均约 24fps、显示丢帧 0(简历原文)
- 「上传隔离」段:libcurl 往返 P95 约 190ms(含 PC 推理约 140ms);不能夹在取帧与还帧之间(简历原文)
- NVR:帧率节流用 now_us/CLOCK_MONOTONIC(源码 web/帧节流)

**⑥ 坑点一句**
别说"平均延迟 XXms"(必须带分位数口径);别把"实时"挂在监控预览上(那是软实时,说错了现场翻车);别把平台限制说成设计缺陷("单核 CPU 受限所以这样设计"是加分的约束思维)。

**⑦ 状态行**
来源=B2-34/B2-15/B2-35;预生成首版 2026-10-18;未开始。**本卡是深挖分水岭:有 P95 一手数字,建议第二批背。**

## 卡 BV-08 · 音频链路一句(低频 · 瘦身版)

**① 知识点是什么**
Linux 音频应用链路:ALSA(oss 的继任)→PCM 采样格式/声道/采样率→重采样→混音→(可选)编解码(AAC 等)。嵌入式常见坑:双麦克风采样式冲突(采样时钟不同步)、插拔检测、延迟估算(缓冲区深度×帧长)。

**② 面试官怎么问**(B2 原题)
- 「ALSA 音频链路;双麦克风抢占问题解决方案和问题定位」(富瀚微 B2-44,合辑)
- 「这个音频和视频怎么编码、用什么编码的(H264 和 AAC)」(芯长征老池同型)

**③ 口述回答(两句)**
"应用侧音频是 ALSA 出 PCM,按采样格式/声道/速率配流,要混音或编码再走重采样和 AAC 这类编码器;双麦克风的典型坑是两个声卡的采样时钟不同步导致采集漂移,定位靠比对两路时间戳和缓冲区水位。"

**④ 追问一句**
"写过吗?" → "没有一手音频项目,我一手是视频侧;机制了解到 ALSA/PCM/重采样这一层。"

**⑤ 项目锚点**:无(视频侧项目;音频为机制层了解)。
**⑥ 坑点一句**:别把音频讲成深水区(没有一手就说没有,防追问穿)。
**⑦ 状态行**:来源=B2-44;瘦身版;投 MTK/恒玄/音频向岗位前激活。

## 卡 BV-09 · Android 多媒体框架与数据读取 APP(低频 · 瘦身版)

**① 知识点是什么**
手机/SoC 原厂岗会问应用怎么读摄像头数据:Android 侧 Camera2/CameraX、NDK 侧直接 V4L2 或厂商 SDK;"数据读取 APP"指绕过框架直读 /dev/video 或走 MediaCodec/Surface 通路。核心概念:框架分层(HAL→framework→app)、buffer 通路(Surface/ANativeWindow)、权限与格式协商。

**② 面试官怎么问**(B2 原题)

**③ 口述回答(两句)**
"Android 侧上层走 Camera2/CameraX,底层是 HAL→V4L2;要直读数据可以 NDK 里直接 open /dev/video 走 ioctl,或者厂商 SDK;我一手是纯 Linux 侧 V4L2 用户态全流程,Android 框架层了解到分层和 buffer 通路这一层。"
