## 一、结论先行

### 1. 当前项目八股的方向判断是对的，但频率层级需要重新分工

当前项目八股已经把 EdgeFusion 最有辨识度的内容整理出来了：

- 压缩域录像、remux、fMP4、关键帧切段；
- 一次拉流三路分发、packet 所有权、最新帧单槽；
- RTSP/RTP、SDP、SPS/PPS、NALU、FU-A；
- HTTP/MJPEG/Range；
- 多线程、锁、条件变量、回调上下文、背压；
- 掉电保存、SQLite、慢客户端、停机与失败隔离。

这些内容非常适合**音视频应用岗位和项目深挖**，也是项目简历能够形成差异化的地方。

但是，132 份校招样本显示，面试的实际筛选顺序通常是：

```text
C/C++ 基础
→ 进程/线程/同步
→ 网络基础与 IO 多路复用
→ 内存管理与调试
→ 手撕
→ 项目/音视频专项深挖
```

因此需要明确区分两套资产：

| 资产 | 主要任务 | 当前评价 |
|---|---|---|
| 通用八股副线 | 解决校招一面硬门槛 | 已有频率校准，但部分点仍待补强 |
| EdgeFusion 项目八股 | 把项目讲出深度和音视频辨识度 | 音视频项目点强，但有几项高频应用层题缺卡 |

**本次不建议把所有通用 Linux 内容塞进项目八股目录。** 项目八股应该补“项目真正能挂靠、且音视频岗位会追问”的内容；纯 `volatile`、`static`、结构体对齐、手撕算法等继续放通用八股副线。

### 2. 项目八股真正的主要缺口有五组

按“岗位频率 × 与当前简历相关度 × 项目可承载度”综合排序，建议补强：

1. **FFmpeg 编解码流程与解码后数据链路**；
2. **RTSP/RTMP/HLS/WebRTC 协议选型对比**；
3. **GOP、编码参数、码率控制与花屏/卡顿处理**；
4. **音频基础、音视频同步和音频重采样**；
5. **V4L2 应用层与项目边界、采集缓冲和性能排查**。

另外还应把项目现有素材重新组织成一组“**性能与故障排查场景卡**”，因为调试排查在校招样本中已经达到 27%，而当前项目八股的正常流程卡多、排查卡分散。

### 3. 当前项目八股的重点不应继续无上限扩展 H.264 字节细节

A 类音视频样本中，音视频专项约占 50%，其中应用层约占 7/10，驱动/SoC 层约占 3/10。当前 RTSP/RTP 和 H.264 字节层内容已经很强，继续增加 Annex B/AVCC 边界、RTP 字段等低频细节的收益低于补齐下面这些应用层高频：

- FFmpeg 从输入到解码输出的完整流程；
- 解码后是什么数据、如何转成显示或 JPEG；
- 软解/硬解怎么选；
- GOP 和编码参数如何影响延迟、码率、恢复；
- 丢包、丢帧、花屏、卡顿怎么定位；
- RTSP 与 RTMP/HLS/WebRTC 的选型边界。

### 2. 音视频专项的内部拆分

采集资料给出的关键拆分是：

| 音视频子方向 | 样本情况 | 当前项目覆盖 | 结论 |
|---|---:|---|---|
| H.264/H.265、流媒体协议、封装、FFmpeg、GOP、码控、同步、花屏卡顿 | 音视频专项约 7/10 | 部分强、部分缺卡 | 需要补齐应用层卡片 |

### 3. 频率上不应继续由项目八股承担的内容

以下内容频率很高，但应放在通用八股副线，不应为了“覆盖率”大量复制到项目八股：

- `volatile`、`static`、`const`、`sizeof`、内存对齐；
- 指针、数组、函数指针、`memcpy/memmove`；
- fork/exec/wait、IPC 通用比较；
- 虚拟内存、页表、TLB、COW；
- epoll 的通用 API 和 LT/ET；
- FreeRTOS 任务、队列、信号量、优先级反转；
- 链表、栈队列、Ring Buffer、字符串手撕；
- BootROM/U-Boot/kernel/rootfs 通用启动链；
- I2C/SPI/UART 通用时序。

这些内容可以保留一条项目挂靠句，但不要在项目八股里再建完整答案卡，否则会造成：

```text
通用八股重复建设
→ 项目八股变厚
→ 项目专属高频缺口反而没有时间补
```

## 四、必须补强的项目八股内容

## P0-1：FFmpeg 完整媒体处理链路

### 为什么优先级最高

采样中，音视频应用层高频问题明确出现了：

- FFmpeg 编解码流程；
- 解码后数据是什么；
- 解码后如何处理；
- 软解还是硬解；
- MP4 解封装到 H.264/H.265 再到 YUV/RGB 的流程。

当前只有 `HF-31`“打开流与拉流”和 `HF-04`“remux vs 转码”，中间的解码数据流缺少一张完整卡。这会造成面试官一旦问：

> “你们抽帧从 packet 到 JPEG 中间到底发生了什么？”

只能依靠零散的源码学习记录回答。

### 建议新建卡

**建议文件名**：`04_FFmpeg媒体处理流程.md`  
**建议档位**：高频区 HF-32 或项目八股专项卡

### 必须覆盖的内容

```text
avformat_open_input
→ avformat_find_stream_info
→ av_read_frame 得到 AVPacket
→ avcodec_send_packet
→ avcodec_receive_frame 得到 AVFrame
→ YUV 像素格式/分辨率
→ sws_scale
→ JPEG 编码
→ 最新帧缓存
→ Web/AI 读取拷贝
```

必须讲清：

1. `AVPacket` 是压缩码流包，`AVFrame` 是解码后的原始图像帧；
2. 一个 packet 不保证对应一帧，`receive_frame` 需要循环；
3. `send/receive` 两端的 `EAGAIN` 语义不同；
4. 抽帧不是“拿到一个 packet 直接转 JPEG”，而是持续送解码器维持参考链；
5. YUV 到 JPEG 前为什么需要像素格式和尺寸转换；
6. 录像主路为什么不进入这条解码链；
7. 软解只发生在低频抽帧旁路，边侧没有 H.264 硬解 VPU。

### 项目锚点

- `stream_receiver.c`：packet 三路分发；
- `frame_grabber.c`：解码、缩放、JPEG 编码、最新帧缓存；
- `recorder.c`：remux 路径不解码。

### 通过标准

能在 60 秒内画出 `AVPacket → AVFrame → YUV → JPEG`，并回答为什么录像路不走这条路径。

## P0-2：RTSP / RTMP / HLS / WebRTC 协议选型

### 频率依据

音视频专项补采中，流媒体协议对比出现约 4 次，且是明确的方向 A 网络新钉子户。原题包括：

- RTSP 输入、RTMP 输出为什么这样做；
- RTSP、RTMP、HLS、WebRTC 的区别；
- 低延迟、浏览器兼容、CDN 和实现复杂度的取舍。

当前 `LF-15` 已存在材料，但仍标为新建材料版，应该从低频材料升为**中频应用层卡**。

### 建议修改

将 `LF-15` 改为 `MF-01` 或升入高频区末尾，不必与 FU-A 同等深度，但不能继续放在“被问再说”的低频区。

### 建议口述骨架

| 协议/技术 | 主要定位 | 优势 | 代价/边界 | EdgeFusion 关联 |
|---|---|---|---|---|
| RTSP + RTP | 摄像头/播放器实时会话 | 安防生态成熟、低延迟、可控制传输方式 | 浏览器原生支持差 | 端侧推流、边侧拉流与转发 |
| RTMP | 直播推流 | 基于 TCP、生态和推流工具成熟 | 传统直播协议、低延迟和现代浏览器方向不占优 | 项目未实现，讲通用对比 |
| HLS | HTTP 分片点播/直播 | 浏览器/CDN/穿透友好 | 延迟通常较高，切片和清单带来等待 | 项目未实现 |
| WebRTC | 浏览器实时互动 | 低延迟、浏览器原生、支持互动 | 协议栈和 NAT/媒体协商复杂 | 项目未实现 |
| MJPEG | 简单浏览器预览 | 实现轻、浏览器可直接显示 | 带宽效率低，无现代视频编码优势 | 项目 Web 预览 |

必须明确：

> 这是一张通用选型卡；项目实然只实现 RTSP/RTP 和 MJPEG/HTTP，不声称实现 RTMP、HLS 或 WebRTC。

## P0-3：GOP、编码参数、码率控制与花屏/卡顿

### 频率依据

音视频专项样本明确出现：

- GOP 设置和依据；
- 编码器参数的影响；
- QP/bitrate、CBR/VBR；
- 主码流/子码流；
- 丢包丢帧影响；
- 花屏、拖影和卡顿的原因与处理。

当前已有：

- HF-01~HF-03：I/P/B、GOP、IDR、关键帧切段；
- HF-08：丢包与参考链；
- HF-11：码率估算材料版；
- 简历审计材料中的掉帧和性能内容。

但这些内容还没有组成面试官真正会问的“场景闭环”。

### 建议新建卡

**建议文件名**：`05_GOP码控与花屏卡顿排查.md`  
**建议档位**：中高频场景卡

### 必须覆盖

```text
GOP 长度
  → IDR 间隔
  → 随机接入和丢包恢复
  → 码率与存储
  → 延迟与瞬时码率
```

并建立排查表：

| 现象 | 第一层判断 | 第二层定位方向 | 项目可答内容 |
|---|---|---|---|
| 花屏直到下一个 IDR 才恢复 | 参考链损坏 | RTP 序号、丢包、GOP | HF-08、RTCP 缺失边界 |
| 画面卡顿但没有花屏 | 延迟或帧未及时到达 | TCP 阻塞、处理耗时、队列/单槽 | 慢 TCP 客户端、拉流线程被阻塞 |
| 录像无法从头播放 | 段头不是解码起点或 fragment 未完成 | `waiting_key`、关键帧、掉电窗口 | HF-03、HF-09 |
| 磁盘占满 | 存储回收或码率预算问题 | 水位、当前段、文件排序 | HF-11、cleanup_disk |
| 码率突增 | VBR/场景复杂度/关键帧 | QP、GOP、码率模式 | 通用选型，项目未做编码器控制 |

项目边界要说准：边侧项目主要负责接收、封装、转发和旁路处理，端侧编码器的全部参数并不是边侧实然；涉及端侧参数时说“通用机制”或“端侧配置需核实”。

## P0-4：音频基础、音视频同步和重采样

### 为什么不能继续只保留一句交底

`LF-14` 已经能回答“项目没有音频轨，但知道同步框架”，这对防守有用，但音视频应用岗位的样本出现了：

- 音视频怎么同步；
- 视频线程如何获取音频时间戳；
- 音频重采样的目的；
- 音频帧和音频断续；
- 播放器设计中的音频时钟。

当前简历定位是视频应用，不需要把自己包装成音频开发者，但至少要具备**通用应用层交底能力**。

### 建议修改

将 `LF-14` 升为 `MF-02 音视频同步与音频基础边界卡`，内容控制在一张卡，不扩展音频算法。

### 必须覆盖

- 采样率、采样位深、声道数、PCM、音频帧；
- 音频和视频分别有自己的 PTS；
- 以音频或外部时钟作为 master clock 的基本思想；
- 视频领先时丢帧，视频落后时重复/等待或调整；
- 重采样解决采样率、声道数、采样格式不一致；
- 音频断续可能来自缓冲欠载、生产消费速率不匹配、网络抖动或时钟偏差；
- EdgeFusion 是单视频轨，未实现实际音视频同步和音频重采样。

### 必须使用的边界句

> “我能讲清音视频同步的通用机制和项目没有音频轨这一边界，但 EdgeFusion 当前实然是单视频 NVR，不能把通用音频知识说成项目实现。”

---

## P0-5：V4L2 应用层与 NVR 项目的关系

### 频率依据

V4L2/ISP/MIPI/Sensor 属于音视频专项的驱动/SoC 子类，约占 3/10。你的简历又有一个完整的 V4L2 采集项目，因此这不是纯通用八股，而是可以成为第二个项目的面试挂靠点。

### 建议新建卡

**建议文件名**：`06_V4L2应用层采集与项目边界.md`  
**建议档位**：中频项目挂靠卡

### 必须覆盖

```text
open 设备节点
→ QUERYCAP / 设置格式
→ REQBUFS
→ mmap
→ QBUF
→ STREAMON
→ poll
→ DQBUF
→ 拷贝有效数据
→ QBUF 归还驱动缓冲
→ STREAMOFF / 释放
```

结合你的简历项目讲清：

1. 驱动缓冲和应用缓冲的所有权不同；
2. `DQBUF` 后要尽快 `QBUF`，不能把驱动缓冲占着去做解码、显示和网络上传；
3. 应用内存拷贝后，显示和上传可以在自己的生命周期内使用；
4. 两条有界队列采用“队满丢旧保新”，解决上传/显示落后；
5. 这是一种与 NVR `frame_grabber` 单槽覆盖不同的缓冲策略；
6. NVR 边侧接收 RTSP/H.264，不直接操作 V4L2，端侧负责采集和硬编码。

### 特别要避免的误导

不能把以下内容写成自己的驱动经历：

- Sensor 驱动注册；
- platform probe；
- 设备树匹配；
- vb2 驱动实现；
- MIPI CSI 驱动；
- ISP 内部 pipeline。

正确表述是：

> “我有 V4L2 用户态采集和缓冲管理经验，能理解应用与驱动的交接；没有把自己包装成 V4L2 内核驱动开发者。”

### 建议新建总卡

### 统一五步法

```text
1. 现象定义：影响哪条链路、是否稳定复现、影响范围是什么；
2. 先分层：输入/码流/线程/锁/文件/网络/外部云服务；

4. 沿控制流定位根因：从现象追到具体状态和所有权；
5. 修复并验证：修复后复测性能、失败路径和回归影响。
```

### 建议收录的 6 个案例

| 编号 | 现象 | 根因 | 建议工具/证据 | 当前资产 |
|---|---|---|---|---|
| D-01 | 当前段码率一直为 0 | FFmpeg 写包后 packet 被清空，之后读取 `size` | 统计字段追踪、源码控制流 | C1 缺陷故事 |

| D-04 | 慢客户端导致拉流侧延迟 | RTSP 发送在锁内且 socket 阻塞 | 线程栈、send 阻塞、锁等待 | HF-16/盲区 03 |
| D-05 | Web 启动返回成功但端口不可用 | bind/listen 在线程内异步失败且未回传 | `ss`/日志/启动时序 | LF-19 |
| D-06 | 视频采集端到端延迟过高 | 软件 JPEG 解码、缩放和上传消费慢 | 单调时钟分段、P95、帧号 | 第二个项目简历 |

### 工具层最低要求

- `gdb`：线程栈、断点、变量和 core；

- `valgrind/ASan`：内存越界和泄漏；
- `ss/lsof`：监听端口、fd 和连接状态；
- `perf`：热点和调度问题，知道工具定位即可。

## P1-2：V4L2 项目性能卡与 NVR 单槽卡的对照

这是一个很有价值、但目前尚未被充分利用的跨项目比较：

| 场景 | 数据价值 | 缓冲策略 | 满载行为 |
|---|---|---|---|
| V4L2 视觉终端显示/上传 | 当前帧，处理线程可能暂时落后 | 两条固定容量有界队列 | 丢最旧保最新 |
| NVR frame_grabber | 当前帧，不要求每帧识别 | 单槽最新帧 | 覆盖即丢旧 |
| NVR 录像 | 历史完整性 | 直接写文件/封装 | 不能随意丢包，错误分级 |
| 事件数据库 | 事件可追溯 | SQLite/文件 | 需要明确失败和重试策略 |

面试官问“你们为什么一个用队列，一个不用队列”时，可以用这张表说明：

> 队列不是默认正确答案，缓冲策略由数据的价值函数、处理速率和延迟目标决定。
