## A 组 · 通用元问题(5 张)

### A1 线程全景卡 ★必考

**问:「这个项目开了几个线程?」**

骨架答:常驻五个——拉流、云 AI、报警、RTSP 监听、Web 监听;主线程是一个一秒心跳循环,等信号退出。Web 每来一个连接临时开一个 detached 线程,MJPEG 长连接会一直占着一个。反过来四个模块明确**零线程**:recorder、frame_grabber、event_bus、conf,都是被动库,借调用方的线程干活——「总线只传不攒,攒了才要队列,要队列才要线程」。

- 子弹1|**同步原语盘点**:互斥锁四处(快照仓库一写三读、数据库连接+写入、报警配置、录像统计),条件变量一处(报警线程专职等待),无锁交接两式(冻结快照 malloc+memcpy、同步扇出同线程直调)。一句话:「锁保共享,拷保所有权」。
- 子弹2|**每连接线程的代价**:连接数=线程数,MJPEG 长连接占着不走,没有上限保护——局域网少量客户端可接受;被问「连接多了怎么办」→ 方向是 select/epoll 单线程多路复用,「知道方向,项目没用」,诚实停。
- 子弹3|**谁在哪个线程上下文**(穿防背错):三分发在拉流线程;publish 的回调借云 AI 线程的栈;GPIO 动作在报警线程;事件查询在 Web 的连接线程。
- 锚点:stream_receiver.c:194 / cloud_ai.c:328 / alarm.c:124 / rtsp_server.c:574 / web.c:1012(监听)+994(每连接)/ main.c:169-170(心跳)。

### A2 现成方案对比卡

**问:「为什么不用现成的 NVR / frigate / 直接 ffmpeg 命令行?」**

骨架答:分两层说。工程上,真要快速上线产品,现成方案更合理——集成度高,不用自己碰 RTP 打包。但我做这个项目的目标是把嵌入式音视频链路吃透到字节层:拉流、remux、fMP4、RTP 打包、热更边界,在现成方案里全是黑盒。选它做源码级梳理和审计,是拿广度换深度的自觉选择。

- 子弹1|**被反问「那你这项目的价值」**:价值在能讲清每个选型的 why 和边界——「不这样会怎样」我都能推;外加一份可复现的问题清单,每条从现象到行号。
- 子弹2|**红线**:不贬低现成方案、不说「自研更好」;自研 RTSP/HTTP 是原作者的工作,我的角色是梳理、审计、注释工程化(角色句,第 1 讲已过闸)。

### A3 亮点定位卡

**问:「这个项目哪里最难 / 最能体现水平?」**

骨架答:两问分开答。**项目本身**含金量最高的两处:同步扇出的所有权设计——一份 packet 三条腿,一借一克隆一借,零队列零锁;自研 RTSP/RTP 打包做到字节层(FU-A、双条件 marker)。**我下功夫最深**的是审计链:时基假定、码率恒 0、熔断稀释,都是从异常现象推到根因、对到行号,顺手把误导性注释改成如实描述。

- 子弹1|三腿三脾气一句话:录像不能丢(阻塞写+熔断重连)、转发不能慢(失败超限踢)、抽帧只要最新(覆盖不反压)——展开见 04①。
- 子弹2|归属红线同 A2:谈项目用客观句式,谈自己只认审计/梳理/注释。

### A4 重新设计卡

**问:「如果重新设计,你会改什么?」**

骨架答:三层。第一层修已知缺陷——码率统计、熔断稀释、时基传参,三条都有定位和一句话修法(见 C 组)。第二层架构级:最想改的是慢 TCP 客户端能持锁阻塞 send、拖住整个拉流线程——把发送改成就绪事件驱动或独立发送线程,让「踢人」从事后止损变成事前隔离。第三层功能级:接上预留的 MQTT、云调用失败退避、同类事件去重。

- 子弹1|**被问「为什么还没改」**:投递优先;清单在档,每条张口就来——这题答得好等于把缺陷清单变成加分项。
- 子弹2|红线:对外只讲三条主缺陷+两条备用(见 04/讲义 03),不报「第几项」内部编号。

### A5 性能数字卡(板端闸门)

**问:「CPU 占用多少?能带几路?帧率多少?」**

骨架答:板端数字还没采,不编;可以讲测量方法和预期方向——CPU 用 top -H 分线程看,预期软解腿(解码+缩放+JPEG 编码)是大头、压缩域两腿近零;码率=字节数/时长,统计修复后页面直接可读;丢包看 RTP 序号断号;重连耗时在熔断触发到流重建之间打点。

- 红线:**一个数字都不报**;D1–D6 采集完成(闸门开)之前,口径永远是「联调进行中,我讲机制和测量方法」。

## B 组 · 架构横切(3 张,面试官从任意条滑进来的岔路)

### B1 快照存储选型卡

**问:「事件图片为什么存文件,不塞数据库 BLOB?」**

骨架答:两条反对理由。一是高频小查询给低频大图陪葬——事件列表查询高频、点开看图低频,BLOB 把行撑肥、索引反而变瘦。二是从库里取图等于把大块字节搬进数据库锁的临界区,和「锁内只做快事」直接相撞。现在文件按事件 id 命名、路径回填数据库,Web 直接当静态资源发,存储和查询天然解耦。

- 追问「原子性呢」:先 INSERT 拿 id,再写文件、UPDATE 回填路径——行在图先在的短暂窗口存在,但查询侧拿不到半张图(jpeg_path 空=前端不显示缩略图),降级可接受。
- 锚点:event_bus.c publish 内快照命名 c:147、UPDATE 回填 c:155;web 端 `/api/event/<id>` 取图。

### B2 报警线程卡

**问:「报警为什么不在回调里直接做,要单独一个线程?」**

骨架答:回调是借发布者的栈执行的——发布者是云 AI 线程,它发完布还要回去取下一张图,在回调里做几秒的 GPIO 蜂鸣等于把云线程按住。所以判定放回调(类型命中+置 pending+发信号,秒回),动作放专职线程(等待、拉高、逐秒睡、拉低)。「等待没有消失,只是被挪到了唯一以等待为业的线程上」。

- 子弹|响铃期间新事件命中,回调依然秒回——覆盖刷新 pending,阻塞永远只在报警线程一侧。
- 锚点:alarm.c on_event c:76 / alarm_thread c:89 / 挂订阅 c:129;契约出处 event_bus.h:18(回调 typedef 注释)。

### B3 推拉镜像卡

**问:「Web 页面怎么知道来了新事件?有推送吗?」**

骨架答:没有。整条链只有一处推——publish 到报警是同步回调;Web 从头到尾是拉——用户刷新才查库,事件列表就是一次 SQL 查询拼 JSON 返回。衔接云事件链和 Web 链的只有数据库和磁盘文件,内存里没有通道。「同一条 event_bus,alarm 推、web 拉,两副面孔」。

- 追问「为什么不做成推送」:浏览器侧要 WebSocket/SSE,HTTP 一问一答的模型下刷新粒度够用;真要推送是功能级改进(A4 第三层)。
- 锚点:alarm.c:129(订阅)/ web.c serve_events c:450 → event_bus_query_filtered c:225(锁内查询)。

## C 组 · 缺陷故事三连(从段 7 挪入;每条按「现象→发现→定位→修法」,行号 09-14 复核)

### C1 =骨架⑥ 「Web 当前段码率恒 0」

- **现象**:页面上「当前段码率」永远是 0,录像本身正常。
- **发现**:部署看页面对不上 → 溯源状态接口的分子 bytes_written → 进写帧路径。
- **定位**:写 MP4 的接口 `av_interleaved_write_frame` 会**接管传入的包并把它清空**(等价 av_packet_unref);代码在写完之后才读 `out->size`(recorder.c:262),读到的恒 0——bytes_written 永不增长,码率算式(c:195)分子恒 0。
- **修法**:写之前把 size 记进局部变量,一行的事。
- **追问层**:「为什么 FFmpeg 要掏空包?」——所有权转移,接口把包据为己有,防双释放;递进到三分发里的「克隆」正是为这类接管准备的(见 04①子弹1)。
- **边界**:只伤统计显示,不伤录像数据——影响面先说清,显得懂轻重。

### C2 =骨架⑨ 「磁盘满后熔断失效,录像停摆」

- **现象**:磁盘满后录像停摆——每个关键帧反复重试开段,永远不触发「写错误过多重连」。
- **定位链(五步,讲清就赢)**:①到时长切段(c:226)先 close_segment,它把 waiting_key 置 1(c:62);②磁盘满,open_segment 打开文件失败,write_packet 返回 -1(c:229);③调用点失败计数加一(stream_receiver.c:158);④下一个**非关键**包进来,waiting_key 还是 1,走「等关键帧」分支直接 return 0(c:216)——返回语义是「成功」;⑤调用点一看返回 0,把计数清零(c:160)。计数在 1 和 0 之间振荡,超 20 永远凑不齐,熔断形同虚设。
- **修法**:让等待路径的返回值和「成功」区分(比如等待中返回 1),调用点不清零它。
- **一句话**:「返回 0 身兼两职——『写成了』和『我在等关键帧』——灾难场景下第二个含义把第一个的账本冲掉了。」
- **追问层**:「为什么正常时凑得齐?」——正常运行里 return 0 的窗口只在首段启动那一小段;磁盘满把短暂窗口变成常驻,稀释才显形。

### C3 =骨架⑦ 「输出时基写死 1/90000」

- **现象**:600 秒的段,容器内部时长只有 6.7 秒量级——时间戳按假定时基换算后对不上真实时间;换非 90kHz 时基的源会变速播放。
- **发现**:审计矛盾推演(600s vs 6.7s);加一层——原注释写的是「输出用源流时基 1/90000」,把假定写成事实,我注释工程化时改成了如实描述(recorder.c:236 现行文字)。
- **定位**:输出时基固定写死(c:237),rescale(c:256)把「输入时基=1/90000」当假定真值;recorder 接口从头到尾没接收过 AVRational——对照组:同一个包,转发腿调用点把真实 time_base 传给了 RTSP server(stream_receiver.c:168),录像腿没传。
- **为什么现在能跑**:RTSP H.264 恰好 90kHz,假定撞对了;换时基的源才暴露。
- **修法**:把 AVRational 传进 recorder,两处字面量换成它。
- **归属**:审计和注释修正都是我的活,大方认领——这是三条里唯一「发现+修正文档」双层的。
