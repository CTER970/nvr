## 一、问题本质

深拷贝接力链上的失败语义设计。链上每一层是一次**资源转移(所有权节点)**,设计要能回答固定三问:**会崩吗?会重试吗?失败后数据是什么状态?** 正确形态是:失败以约定的「空值」契约向上传播、传播前自清本层资源、由上层节拍决定重试——所有权链上每个节点对自己的那份负责到底。

⚠️ 注意:上面是**应然**;本项目实然是「大体判空+两处登记在案的破口(#15/#16)」,见下表——讲的时候先讲实然,应然作为 B 路对照。

## 二、实然链路(四层深拷贝 + 各层失败出口,已逐条对源码)

| 层 | 锚点 | 失败动作 | 调用方拿到 | 下一步 |
|---|---|---|---|---|
| get_jpeg 拷出 JPEG | frame_grabber.c:198–200 | 解锁、return 0——**不写 \*out_data** | sz=0;jpeg 靠调用方初始化才是 NULL | usleep 后 continue,下一拍(cloud_ai.c:305–308) |
| b64_encode | cloud_ai.c:29–30 | return NULL | b64=NULL | 判空退场 |
| build_request_body 的 data_url | cloud_ai.c:89–90 | **json_object_put(root);return NULL** | body=NULL | return,外层 free(jpeg) |
| curl 回调 realloc | cloud_ai.c:56–57 | return 0→curl 视为写错误 | resp=NULL | call_cloud 内 free(rbuf) 后返回 NULL |

### ⚠️ 第三层的真相(源码铁证,外部材料在此说反)

失败点时序(cloud_ai.c build_request_body):root 先挂 model/max_tokens → content 数组创建、txt_blk 挂进 **content** → `data_url = malloc(...)` **失败检查在此** → 之后才有 img_blk、content 挂 root。

**失败那一刻 content(含 txt_blk)还没挂到 root——游离。`json_object_put(root)` 只释放 root+model+max_tokens,碰不到 content → content/txt_blk 泄漏 = #16,台账口径正确,「清整棵树」不成立。**

同错误三次换马甲史(防复发):「无泄漏」→「每层失败释放自己已拿到的资源」→「put 清整棵树」——全部是 #16 的应然化。判别法:**讲失败行为前先问「put 的时候它挂上了吗」**。

## 三、三问的答案(实然版)

- **会崩吗?** 不会。每层失败后调用方层层判空提前退场,没有任何一层解引用失败结果——但注意第一层能「判空」的前提是调用方自己预初始化了 jpeg=NULL(契约押在调用方纪律上,#15)。
- **会重试吗?** 不重发本帧。语义是**节拍重试**:本帧识别丢弃,usleep(interval_us) 后从单槽仓库取**最新帧**重走全链——重试拿到的永远是新帧不是旧帧。
- **数据什么状态?** 不全干净,有登记在案的账:第三层**有泄漏**(#16:游离子树);第一层**契约半闭合**(#15:OOM 分支不写 out);其余层干净(b64 free/JSON put/rbuf free)。仓库 g_jpeg 不受影响,写侧继续供帧。

## 四、口径精修:「解耦所以不崩」要拆成两根柱子

- **柱一·解耦**:失败不在模块间传染——云识别挂了,录像、转发、预览照常(共享点只在仓库锁,持锁时间一次 memcpy,有界)。
- **柱二·纪律**:链内不崩——每层判空+退出前自清资源(实然见上:大体做到,#15/#16 是破口)。
- 两者**并列不是因果**;说成「因为解耦所以不崩」会被追问「解耦和不崩有什么关系」。

## 五、追问弹药

- **为什么会紧张——放大系数**:一帧 JPEG 瞬时驻留峰值约 **5 倍**帧大小:jpeg 拷贝 1× + b64 4/3× + data_url 4/3× + json-c 内部 strdup 4/3×(≈1+4=5);序列化再 strdup 整串 ≈2×,追问再放。深拷贝放大本身是 OOM 成因;修法方向:data_url 这层可省(b64 直接拼)、或流式构造。
- **暗坑①(#15 深化口径,源码证实)**:get_jpeg **空仓分支写 \*out_data=NULL、malloc 失败分支不写**——同函数两分支契约不一致;且都 return 0,把「OOM」和「仓库还没帧」混成同一语义。当前靠调用方 jpeg=NULL 初始化兜住,换个不设防的调用方就是野指针。*(建议回填 02 台账 #15,待用户拍板)*
- **再抠一层②**:json-c 内部小分配(json_object_new_string 等)返回值未判空,OOM 极限下行为依赖库实现(实然:连续调用无判空)。
- **A/B 对照讲法**:A 路吞失败留暗坑(return 0 混语义)vs B 路显式传播 NULL+主动清树(清树前提=先挂靠再可能失败)——同一片内存压力,两种契约质量,B 是干净写法的样板。

## 六、一段话面试话术(审计者人设)

「内存紧张时这条链不崩,失败被逐层截住;但不是全链纪律,是**大体判空加两处登记在案的破口**:取帧的 malloc 失败返回成功码、输出参数不写——空仓分支写、OOM 分支不写,契约不一致,靠调用方预初始化兜底;组包失败时 put(root) 清不到还没挂靠的 content 子树,有一处泄漏。后果轻:单次浪费加这一拍没有识别结果,下一节拍取最新帧重来。修法是失败分支补写 out、按挂靠顺序按已创建对象逐个释放。」
