## 卡1 · 「单核上到底隔离了什么?」【一面基础】

隔离的是控制流,不是算力,这两件事在单核上确实要分开说。控制流隔离指:一个线程的阻塞、失败、退场不牵连别人的执行路径——云线程卡在 HTTPS 里十几秒,拉流线程的循环一步不停;它 malloc 失败层层退场,不碰别人的栈。这靠线程边界加单向快照数据流实现,和几个核无关。但算力在单核上是共享的:内核按时间片分时抢占,所有线程瓜分同一个核——[纠偏句,替换原「云线程占着核跑软解」]拉流线程的软解+缩放是全系统最重的 CPU 活,云线程的 CPU 活是 base64 编码和 JSON 拼装解析;单核上两个方向的挤占都成立:云线程编码占核时拉流取包被推迟,拉流线程软解尖峰时云线程/web 全被推迟。反过来要说准:线程阻塞在网络等待上不占 CPU——睡在 recv 或 curl 上时内核把它移出运行队列,核让给别人,占的只有栈和内存;真正占核的是"在跑"的代码。所以真正的算力隔离需要多核绑核、cgroup 配额这类手段;单核上现实的算力管理是限流——把重活的需求压下来,我们的抽帧节流、以及改进位里的子码流,就是单核版的限流。

## 卡2 · 「为什么用 SQLite?并发写怎么回事?」【一面基础】

选型是三个候选比出来的。纯文本方案先否——事件列表要按时间、类型过滤分页,没有结构化查询就是每次全量读全量筛;MySQL 这类也否——要常驻服务进程,边侧多一个要启动、要配置、要防崩的运维负担,不值。SQLite 的位置正好:无服务进程——就是个链进程序的库,随主进程生灭;单文件——拷走文件即备份,掉电即恢复;零运维,还带事务和完整 SQL。事件这种每分钟几条、KB 级的量,正是它的主场。并发写的行为一句话:SQLite 的写锁是库级的——整个数据库文件一把写锁,写写互斥,默认日志模式下写还会挡读;第二个写者碰到锁会拿到 BUSY,默认不等、立即失败,除非设 busy_timeout 让它排队等。不过我们的实际画像更简单:单进程内所有数据库访问都经过事件总线自己那把互斥锁先串行化了,真正的并发写到不了 SQLite 那层——库级锁在我们这甚至是备而不用的第二道。优化方向:WAL 模式可以让读写不再互斥,写写仍串行——我们这个读写同锁的画像下收益有限,没上。
