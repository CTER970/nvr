# 简历驱动分层面试问答：工作流与 Coding AI 执行提示词（通用版）

> 版本：v1.0｜日期：2026-10-23
>
> 编写：ClawsGO Science Agent
>
> 用途：将本文件交给新项目中的 Coding AI，从真实投递简历出发，模拟面试官提问，经质量审查后再核实实现、组织回答、生成追问，并精简为可用的分层面试问答。

## 一、核心思路

**先用面试官能看到的信息决定问什么，再用项目证据决定怎样回答。**

整个流程分开两种角色：

| 角色 | 可用信息 | 负责什么 |
| --- | --- | --- |
| 面试官视角 | 简历投递正文、已知目标岗位，以及候选人在模拟回答中实际说出的内容 | 提出自然的问题，判断哪些说法值得继续追问 |
| 事实核验视角 | 用户授权范围内的源码、配置、测试记录、官方接口资料及既有备考材料 | 检查回答是否符合实际实现，区分原理、实现和验证结果 |

第一层先核实业务流程、职责、选型和关键机制。第二层承接具体首答，进一步询问实现步骤、资源责任、机制因果及方案代价。更深层要根据已有回答继续生长，避免提前批量编造一棵固定追问树。

### 三个重要区分

1. **提问合理，不等于必然会被问。** “优先准备”依据岗位相关性、简历触发强度和基础重要性；没有面经统计时不编命中率。
2. **回答技术上合理，不等于描述了当前实现。** 必须同时检查源码是否这样做、是否还有失败条件。
3. **材料生成完成，不等于用户掌握。** 掌握需要用户独立口述和变式作答，不能由 AI 写完答案代替。

## 二、总体工作流

```text
S0 明确输入、范围与权限
  ↓
S1 盲读投递简历，生成第一层问题
  ↓
S2 审查问题，修订并冻结首问题单
  ↓ 确认题单；明确授权后才能读项目资料
S3 查证实现，生成并核对第一层参考回答
  ↓
S4 根据每份首答生成第二层追问
  ↓
S5 检查衔接、岗位相关性，去重并精简
  ↓
S6 为保留追问补齐答案，逐题核验
  ↓
S7 更新同一文档，检查完整性并交付
```

既有题库对照可以放在 S5，或在用户要求时单独执行。它用来复用证据、识别重复和发现冲突，不能在 S1 前偷偷成为盲出题的来源。

### 阶段与交付物

| 阶段 | 必要输入 | 必须完成的工作 | 交付／通过条件 |
| --- | --- | --- | --- |
| S0 范围 | 投递简历、目标岗位、用户权限 | 确认哪一版正文、哪些条目、是否允许读源码 | 输入清楚；缺失的关键决策向用户确认 |
| S1 盲出首问 | 仅投递正文及岗位信息 | 按条目提取技术承诺，每条约 3～4 个首问 | 问句自然、各有中心，不依赖内部事实 |
| S2 首问审查 | 简历与 S1 草稿 | 逐题检查来源、首问深度、贴岗度、重复 | 修订结果、简短审查说明、稳定编号 |
| S3 首答核验 | 冻结问题、授权资料 | 按问题定向读实现，生成回答及证据边界 | 每题切题，有证据；未知项明确标记 |
| S4 生成追问 | 首问题与实际首答 | 找到触发句，每组生成约 2～3 个下一问 | 不引入面试官未知事实，不预设下一轮回答 |
| S5 精简审查 | 追问草稿、岗位、可选旧材料 | 删除低收益入口，合并重复或相邻机制 | 留主干；保留数量服从内容，不凑配额 |
| S6 第二层回答 | 精简题单、实现及官方契约 | 逐题直接作答，校核流程、边界和选型 | 问题所有子问得到回应，实然与建议清楚 |
| S7 交付 | 完整分层问答 | 核对覆盖、编号、引用、删并映射及索引 | 同一文档完整交付，说明已验证和未验证范围 |

## 三、关键执行规则

### 1. 严格维护“盲看简历”的边界

S1、S2 可以读取简历文件，但只将用户确认的投递正文作为题源。版本记录、个人学习档案、缺陷清单、隐藏备注、内部预案、项目 README 和源码都属于额外信息，不能用于生成首问。

允许识别简历所在路径和读取必要的操作规则，但不要全仓扫描来“先了解项目”。如果提取 PDF／Word 正文，需要使用当地工具准确提取，文字或表格识别不清时先确认。

**AI 已经知道源码时，无法真正恢复未知状态。** 应向用户简短说明该限制，建议用新会话或具备独立上下文的执行者，只提供脱敏后的投递正文、岗位和出题规则。若用户选择继续，则标注“仅按简历视角约束生成”，不宣称是严格盲评。独立执行者只有实际可用且执行过才能声称调用。

### 2. 首问从技术承诺长出来

每条内容可识别：业务能力、关键技术、效果承诺、个人贡献。首问优先覆盖：

- 数据或请求从哪里来、经过什么、到哪里去。
- 用户负责了什么；已有实现、新增开发、分析审计和验证分别是什么。
- 为什么采用该方案，适用的约束是什么。
- 简历明确承诺的关键机制如何工作。

每条约 3～4 题是初始建议，不要求所有条目同量。一个首问围绕一个主要中心，必要时带紧密关联的子问，避免把流程、原理、异常、改造和性能证明一次塞在一句里。

### 3. 审查必须能导致修订

不要只为每题盖“合理”印章。检查后应实际删掉、合并、降级或改写不合格问题，并保留简短理由。

| 审查项 | 判定问题 | 不合格时怎样处理 |
| --- | --- | --- |
| 来源 | 只看投递简历能自然提出吗？ | 删掉内部实现前提；必要时改成询问式 |
| 首问定位 | 是入口问题，还是已经跳到罕见故障或字段细节？ | 后移追问或折叠 |
| 岗位贴合 | 能检验目标岗位需要的能力吗？ | 低贴合题删除或降为可选 |
| 主要中心 | 是一个清晰考点，还是许多不相干问题？ | 拆分或聚焦 |
| 重要性 | 不懂它是否影响对项目主链路的解释？ | 叶子与边缘知识折叠 |
| 表达 | 条件明确、对象唯一、问句自然吗？ | 补足条件，去掉隐晦指代 |
| 重复 | 已有题是否检验同一因果？ | 共用一个主要入口 |

### 4. 查证答案时定向读码

获授权后，根据已经冻结的问题查接口、调用点、关键状态及代表性失败路径，不为答题无目的整读所有模块。

涉及线程和资源时，至少确认：谁调用、在哪个线程、谁创建、谁持有、谁释放、锁保护什么、失败后走哪里。涉及库或协议，源码与官方接口契约分别核对，注释和函数名不能单独证明实现完成。

回答采用三层证据：

| 层次 | 应说明什么 |
| --- | --- |
| 机制／规范 | 一般机制如何工作，API 或协议提供什么保证 |
| 当前实现 | 本项目实际怎样使用，是否有简化、遗漏或缺陷 |
| 工程结论 | 可得出什么结论，仍缺哪些测试或环境证据 |

设计理由可以做有依据的工程分析，但不能虚构“作者当时比较了三套方案”或“我实测后选择了它”。

### 5. 第二层从首答的具体表述继续追

每组先标记一条真实触发句，再生成问题。例如：

> 首答：“读取者在锁内取得一份拷贝，解锁后发送。”
>
> 合理追问：“为什么读线程也要加锁？直接返回共享指针会有什么风险？”
>
> 追问考察：共享数据一致性与使用期间的生命期。

若源码审查发现了锁外读等问题，但候选人的可见回答没有提及，面试官不能直接问“你那个锁外读缺陷怎样修”。可以询问一般的一致性保证，或者仅在候选人主动披露后开启缺陷分支。

**同组的 2～3 个下一问通常是可选分支。** 只有前一问已有真实或明确标注的模拟回答，后续才能依赖其中新事实继续深入。不要把并列分支描述为已经验证的完整对话链。

### 6. 精简按准备收益，避免追求题量

优先保留：

- 简历主动写出的技术与效果承诺。
- 决定主流程、数据正确性、资源责任与失败策略的机制。
- 目标岗位通用且能借本项目解释的原理。
- 紧贴当前方案、能检验取舍的代表性变式。

优先删除或合并：

- 简历未承诺、与岗位联系较弱的额外功能需求。
- 为显得深入而引出的底层算法、协议冷门字段或新技术栈。
- 多次重复同一机制、仅换场景外壳的问题。
- 内部 helper 的命名、行号、局部参数记忆题。
- 已有题能解释的平行方案比较或缺陷清单扩展。

合并必须保持中心一致。若合并后题干变得更杂、更长，应保留一个主问，将其余折叠成答案边界，不能只是减少标题数量。

## 四、可直接交给新项目 AI 的完整执行提示词

以下代码块可以整段复制。也可以直接发送本文件，并说明“执行第四节”。

```text
任务：执行“简历驱动分层面试问答”流程，为当前项目形成可信、贴岗、可演练的面试准备文档。

【参数】
- 投递简历路径或正文：<填写；暂缺则询问>
- 目标项目与条目范围：<填写；默认简历该项目全部技术亮点>
- 目标岗位、级别及可选 JD：<填写；不得自行推断具体雇主偏好>
- 首层题量：每条约 3～4 题，允许按内容减少。
- 第二层草稿：每个首答约 2～3 个下一问，精简后数量服从价值。
- 事实核验资料：<源码根、测试记录等；尚未授权则不读取>
- 旧问答／训练材料：<可选；首问题单冻结前不得作为题源>
- 输出路径：<填写；缺省在用户工作区的备考目录创建“面试拷打问题.md”>
- 模式：分阶段确认，默认。
  如用户明确选择“全流程执行”，也必须先完成并冻结盲首问，
  再进入核验；源码访问仍须有明确授权。

【角色与权限】
你依次承担“只看到简历的面试官”和“核验实现的代码学习助手”。
先按岗位要求和投递正文决定问什么，再按证据决定怎么回答。
遵守当前环境的项目规则与用户权限。只生成或更新本任务的备考文档，
不修改源码，不提交 Git，不运行部署、压力或破坏性测试，除非另有授权。
使用用户语言；代码、路径、标识符保留原样。

S0：输入确认
1. 确认实际投递正文、目标项目条目、岗位、输出位置及读码权限。
2. 只询问会改变下一步的缺失信息，能合理默认的事项自行选择并说明。
3. 如果上下文已经包含源码或内部缺陷，说明严格盲评受限，建议新上下文。
   获用户同意继续后，按“简历视角约束生成”处理，不虚称信息隔离。

S1：盲读简历，生成首问
1. 只阅读投递正文与岗位信息，不读取源码、README、架构说明、缺陷台账、
   学习进度或旧题库。文件中非投递备注不作为题源。
2. 列出各条简历的原文锚点和技术承诺，不把术语自动等同于实现已正确。
3. 每条提出约3～4个自然首问，每题只保留一个主要考察中心。
4. 问题覆盖流程、职责、选型和简历明确强调的机制，避免直接跳罕见细节。
5. 暂不写项目特定答案。输出表：题号｜简历触发点｜首问｜考察意图。

S2：审查并冻结首问题单
1. 逐题检查：面试官信息边界、与岗位关系、入口深度、重要性、
   句意准确、重复和是否过载。
2. 对不合格题实际执行删并改，并写简短理由。
3. 不凭主观编命中率；“优先”只能解释为岗位与简历驱动的准备优先级。
4. 形成稳定编号，例如B01-Q01；冻结首问快照，标明版本。
5. 默认停在这里，请用户确认题单并明确是否授权读项目核答。
   若此前已明确确认与授权，直接继续，无须重复索取同一确认。

S3：查证并生成首答
1. 按冻结题目定向查头文件、调用点、关键状态、线程、所有权与失败路径。
2. 不用源码知识偷偷重写盲首问。确需纠正错误前提时，记录修订原因与版本。
3. 每题给出“参考回答＋依据与边界”：先结论、再因果、最后必要限定。
4. 实现事实提供真实文件路径和当场核实的行号；库或协议疑点查官方资料。
5. 分清规范机制、当前实现、工程结论；建议方案必须写明未实现。
6. 不虚构贡献、调试经历、性能数字、测试或运行效果。
7. 无源码或未获授权时，只给通用机制回答，项目部分写“待核实”，
   不为保持文档完整而编造事实。
8. 检查答案是否回应所有子问，返回首层答案及审查结果。

S4：根据首答生成第二层追问
1. 从每份首答中摘出明确的触发句。
2. 每组生成约2～3个下一问，按需要选机制、流程、所有权、线程、
   选型或失败边界，不机械套齐所有维度。
3. 问句只能使用简历与首答实际披露的信息。
4. 源码审校备注不自动成为候选人的发言；对未披露缺陷只能问一般机制。
5. 标明并列分支或条件分支，不把尚未回答的追问当作新的已知事实。
6. 默认先输出问题、触发点与意图，请用户确认方向。
   已授权全流程时，直接进入S5，同时保留审查记录。

S5：对照、精简与确认
1. 逐组检查衔接、岗位贴合、重要性、重复和深度，删除边缘题、凑数题。
2. 不要求每组同量，不设必须达到的删题比例。
3. 用户提供旧材料时再做对照，区分：直接覆盖、部分覆盖、新展开。
   统计以可复核的问题单位为准，列来源；不能将同主题直接算全文重复。
4. 旧材料有冲突时核实来源与代码，不因“旧稿权威”沿用过时结论。
5. 列删并映射：原题号｜去向｜理由，保持稳定ID，允许跳号。
6. 精简后仍需覆盖简历的核心承诺，避免合并成更难理解的复合大题。

S6：补齐第二层答案并核对
1. 对每个保留问题给完整、自然、可口述的直接回答。
2. 解释机制、关键流程或取舍，必要时给一个短例子，不堆砌术语。
3. 写清当前实现、存在的限制、建议改进和未验证部分。
4. 每题检查：
   a. 是否真正回答了题干及子问？
   b. 名词、单位、协议与库契约是否准确？
   c. 正常流程和代表性失败流程是否一致？
   d. 线程上下文、锁范围、所有权和释放时机是否有依据？
   e. 是否把设计意图当结果，把局部成功当整体成功？
   f. 是否将建议、共同分析或原项目实现冒充个人已完成成果？
5. 发现问题先修改答案，再记录具体审校结论。
6. 没有实际使用独立执行者时，只能称自检或资料交叉核验，
   不称独立审稿、多智能体一致结论。

S7：更新同一文档并交付
1. 将首问、首答、第二层问答按父子关系放在同一文档，便于连续阅读。
2. 保留简短筛选记录和逐题核对结果，避免大段自我表扬占据主体。
3. 核对所有条目覆盖、编号唯一、答案与问题一一对应、删并数量及引用有效。
4. 清理过期的题数、待答标记、目录与版本描述；遵循当地索引规则登记。
5. 不覆盖用户其他改动，文件发生外部变化时重读目标区再修改。
6. 在工具允许时交付文件，说明最终题量、删并取舍及验证局限。
7. 不因文档生成完成而修改用户学习掌握度，不自动启动下一层或真实面试。

【默认文档格式】
# 面试拷打问题
版本、目标岗位、题源、证据及验证范围。

## 简历条目B01：<标题及必要原文>
### B01-Q01：<第一层问题>
- 考察意图：<一句话>
- 首层参考回答：<自然成段>
- 依据与边界：<真实位置、契约或待核实>
#### B01-Q01-A：<第二层问题>
- 承接点：<首答中的具体表述>
- 第二层参考回答：<先直接答，再说明因果>
- 核对要点：<成立条件、当前不足、建议与证据>

后续各题同理。
附：筛选删并表、逐题审校摘要、引用及未验证清单。

【禁止事项】
```

## 五、交给新项目 AI 的启动话术

### 默认分阶段模式

> 请执行附件第四节的流程。简历是 `<简历路径或正文>`，目标岗位是 `<岗位及级别>`，项目范围是 `<条目范围>`。先只看投递正文，不看项目代码、README 或旧题库，完成第一层提问和质量审查后给我确认。确认后再询问或使用我的明确授权，查代码核对答案，随后生成、精简第二层追问并补齐答案。全部整理到 `<输出路径>`。

### 已明确授权的全流程模式

> 请执行附件第四节的全流程。简历是 `<简历>`，岗位是 `<岗位>`，项目代码在 `<代码根>`，输出为 `<文件>`。我授权你在首问题单冻结后读取本项目代码与必要官方资料，并生成问答文档；不授权修改源码、运行部署或提交 Git。先完成仅基于简历的首问并保留版本，再核答、生成追问、精简和补答，最后交付同一文档和核对结果。遇到真实性或事实缺口时明确标记，需要我判断的地方再问。

### 只有简历、没有源码的模式

> 请执行简历驱动出题和审查。没有项目资料时，答案中的一般机制可以给出，项目特定流程、个人贡献和效果一律标待核实。不要为了完整而推测实现。

## 六、成品验收清单

| 检查点 | 通过标准 |
| --- | --- |
| 输入忠实 | 对应用户确认的投递正文与岗位，非内部备忘 |
| 信息隔离 | 首问生成前未用实现信息；已有污染则如实说明 |
| 首问有效 | 每个问题都有正文触发点，适合作为第一次入口 |
| 问答匹配 | 每题答案直接回应问题和紧密关联的子问 |
| 追问连贯 | 每个第二层问题有首答触发点，条件清晰 |
| 岗位集中 | 主体由岗位核心能力与简历承诺组成，边缘入口已删并 |
| 实现真实 | 代码定位真实，接口行为核对，限制没有被抹掉 |
| 贡献真实 | 原项目、个人开发、AI 辅助、分析、验证分别表述 |
| 证据充分 | 规范、实现、工程效果分层，无法验证之处明示 |
| 文档一致 | 覆盖、题号、题数、目录、引用与删并去向一致 |
| 可演练 | 可逐组遮住答案口述，而非只能阅读的知识堆积 |
| 交付完整 | 完成文件交付，未把未来操作写成已经完成 |

## 七、本流程的使用边界

本流程适合从简历建立项目面试准备主干。个人贡献举证、现场调试故事、长稳测试、项目改进动手和真实冷面模拟仍需单独验证；它们可以由首答自然触发，但不能凭模板自动生成经历。

本次实践形成了“初始扩展后删并”的经验。新项目应迁移筛选原则和证据纪律，不迁移原项目的固定题数、模块名、缺陷编号或答案。
