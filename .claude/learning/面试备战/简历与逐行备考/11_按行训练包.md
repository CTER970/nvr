## 一、行② 一次拉流三路分发【A 档】

**开场先送交行①欠件**(两挂接 20s 压缩版,随本行开场交):

- **MP4 box 树 20s**:「MP4 是 box 树:ftyp/moov 是目录,mdat 是数据。普通 MP4 的 moov 压在文件尾,7×24 录像永远写不完,掉电整文件报废;fMP4 先写静态空 moov,数据按 fragment 落、各自带 moof 小目录——索引在文件尾还是随 fragment,决定掉电后能播到哪。」
- **GOP 与 I/P/B 帧 20s**:「GOP=两个关键帧之间的图像组。长 GOP 省 I 帧码率,但恢复粒度粗——丢一个参考要等到下个 IDR 才能恢复。I 帧自含可独立解,P 帧存与前帧的差;IDR 是硬墙、切断历史参考链——段首必须 IDR,这是『按关键帧对齐切段』的通用层依据。监控流通常关 B 帧,主结构 IDR+P。」

### 件1 · 60s 直问【A|滤网:三分发=orchestrator√ 参考链/所有权=主链因果√ 通用线程/内存模型√】

**题干**:用 60 秒讲清——单拉流线程从 av_read_frame 取出一个码流包后(stream_receiver.c:146 起的主循环),这个包在录像、抽帧、转发三路上各经历什么?谁复制、谁借用、谁释放?JPEG 仓库怎么被三个读者安全共享?

**过线要点**(答不全即标塌点):一次取包、同一循环三次函数调用(不是三条流水线三个线程)/三家三种形态:录像克隆引用(av_packet_clone,recorder.c:254;因 MP4 写接口要接管包)、抽帧借用喂解码器、转发纯只读/三家当场调用当场返回,循环末统一释放/抽帧解码器**全量**吃包维持参考链,到目标帧率才做缩放+JPEG 编码两件贵活/JPEG 仓库单槽只存最新一帧,读者(AI/预览/抓拍)锁内 malloc 深拷贝拿走所有权自行释放(frame_grabber.c:198-206)/**码流三路零队列,但锁不零**——JPEG 仓库读写共一把互斥锁(禁说「零队列零锁」)。

### 件2 · 熟场景×2

**熟场景 1|资源·malloc 失败**【A|滤网:失败路径=主链因果√】

- **场景题干**:系统内存紧张:云 AI 线程调用 frame_grabber_get_jpeg,frame_grabber.c:198 的 malloc(g_jpeg_size) 返回 NULL;build_request_body 里 cloud_ai.c:89 的 data_url malloc 也返回 NULL。两条路径各自会发生什么?调用方分别拿到什么?
- **锚点**:frame_grabber.c:198-201;cloud_ai.c:89-91。
- **答要点**:get_jpeg 直接 return 0 且不写 *out_data=#15 out-param 契约半闭合,当前靠调用方预初始化兜底/上云侧只 json_object_put(root),尚未挂靠的 content/txt_blk 子树泄漏=#16/缺陷有号、后果轻,但契约押在调用方纪律上/修法一句:失败分支补写 *out_data=NULL(#15);失败清理按已创建对象逐个释放(#16)。底稿=07②节熟场景 1 表。

**熟场景 2|时序·停机撞上阻塞读**【A|滤网:停机链=阶段边界√】

- **场景题干**:按 Ctrl+C:stream_receiver_stop 已置 g_running=0 并走到 pthread_join(stream_receiver.c:207-208),但拉流线程此刻正阻塞在 av_read_frame 里——open_input 没挂 AVIOInterruptCB、也没配 rtsp 超时(stream_receiver.c:38-42 的 options 只有 transport/analyzeduration/probesize/fflags)。停机能立刻完成吗?最坏等多久?
- **锚点**:stream_receiver.c:207-208、38-42。
- **答要点**:join 要等读自己出错或对端发包,最坏 TCP 级延迟/缺陷#12 登记未修;不损数据,代价=停机时长不可控拉长/修法一句:给 AVFormatContext 挂 interrupt_callback(回调里查停机标志)或设 rtsp 超时。底稿=07②节熟场景 2 表。

### 件3 · 变式+边界

**变式题(#52 复发点,表达层监控)**【A|滤网:解码语义=核心数据√】:

- **题干**:有人提议:把「到目标帧率才做缩放+JPEG 编码」提前成「到目标帧率才把码流包送进解码器」,中间的包直接不解码——更省 CPU 不是吗?这个提议错在哪?(锚点:frame_grabber.c:172-187,frame_grabber_feed 全量送包)
- **接住标准**:解码必须全量维持参考链——P 帧存与前帧的差,跳一包要等一个 GOP 才能恢复;节流位置只能在解码**后**的出图侧。定稿句式:「解码为了对,节流为了省,位置就不同。」(口头自查:禁说「先节流再转 JPEG」。)

**主动边界(⑫ 同步扇出代价)**【A|滤网:代价/兜底=主链因果√】:

- **主动交版本**:「零队列同步扇出有代价:抽帧的软解+缩放+JPEG 编码(frame_grabber.c:172-187)和录像的 SD 卡写,全跑在拉流线程上——一条腿卡,三条全等。我拿这个代价换的是不加队列、不加锁的简单。兜底三层:抽帧侧节流、转发侧连续失败踢慢客户端、录像侧写错误超 20 次熔断重连(stream_receiver.c:158)。单次慢写没有超时保护,这是已登记的改进位。」

### 件4 · 挂接 20s 版×2【A|滤网:两题均通用并发机制√】

- **互斥锁与单写多读 20s**:「简历里『单写者多读者』说的是 JPEG 仓库:写侧只有抽帧路径,读者三个——AI、预览、抓拍。一把互斥锁保证读写不同时(防撕裂);读者在锁内 malloc 深拷贝拿走所有权、出去自己释放(防悬垂)——锁保一致性,拷保所有权,缺一不可。」
- **背压与丢弃 20s**:「只存最新一帧,慢的一方付出的不是延迟、是漏看——丢旧保新,内存和延迟都恒定。判断背压的一句话:消费者变慢后,生产者有没有跟着慢;这里没有,所以丢弃是背压的替代。」

## 二、行⑤ 云端 AI 识别与事件告警【A 档】

### 件1 · 60s 直问【A|滤网:旁路链=orchestrator√ 隔离边界=主链因果√ 线程两层=通用√】

**题干**:用 60 秒讲清——云端识别从「取一张 JPEG」到「GPIO 响铃」的完整链路;以及云端接口超时甚至整个挂掉时,录像和预览为什么不受影响?「不受影响」的准确边界在哪一层?

**过线要点**:AI 线程完全独立,与拉流唯一接触点=快照仓库/节奏=「云耗时+间隔」的下限节流,云慢它就慢,不装固定节拍/返回 none 过滤掉,真事件才发布:入库 INSERT→快照落盘(evt_<id>.jpg 路径回填)→回调秒回(类型命中+置 pending)/GPIO 动作在专职告警线程——「等待被挪到唯一以等待为业的线程上」/超时失败只丢当前帧不重试,丢的是时间窗的识别覆盖/隔离是**控制流层面**——单核上 CPU 仍互相抢占(⑲ 同框,禁升格「完全隔离」)。

### 件2 · 熟场景×2

**熟场景 1|外部·云挂或云慢**【A|滤网:外部故障=主链因果√】

- **场景题干**:云端接口设了整体超时 ai_http_timeout_s、连接超时 10s(cloud_ai.c:223-224);curl 返回 rc!=CURLE_OK(cloud_ai.c:236-240),甚至云端服务整个宕机。录像、预览、转发会受影响吗?「不受影响」的准确边界?
- **锚点**:cloud_ai.c:289-317(线程主循环)、223-224、236-240、313-314(睡满间隔)。
- **答要点**:AI 线程完全独立,超时截断单次调用、丢帧继续循环/节流是下限语义:调用耗时数秒时睡满间隔即取下一张/拉流录像预览只与快照仓库打交道,云的状态传不过去/边界两句:只在控制流层面,单核 CPU 仍互相抢占(⑲);间隔在启动时取一次(cloud_ai.c:302),ai_fps 热更新对间隔不生效。底稿=07⑤节熟场景 1 表。

**熟场景 2|并发·reload 持锁写与无锁读**【A|滤网:竞态=并发主链√】

- **场景题干**:Web 线程执行 POST /api/config→conf_apply_hot(web.c:925):cloud_ai_reload 在 g_cfg_mtx 锁内写 enable/fps/timeout/prompt/model/base_url 六个字段(cloud_ai.c:352-365),alarm_reload 在 g_mtx 锁内写触发词/阈值/时长(alarm.c:157-164);同一瞬间 AI 线程的 call_cloud 正**无锁**读这几个字段拼 URL/鉴权头/取超时(#18),on_event 正无锁读 g_trigger_types/g_min_conf(alarm.c:79 判定行,经 63/65 读)。会发生什么?后果多重?
- **锚点**:web.c:925;cloud_ai.c:352-365;alarm.c:157-164、79;#13/#18。
- **答要点**:撕裂窗口的后果=单次判定用半新半旧配置、单次请求参数不一致/缺陷有号(#13/#18),台账已评后果轻:最多一次判定偏了、一次请求混旧值,下一轮自愈/修法一句:读侧加同一把锁(低频读写最简单),或 reload 改「新结构构建→指针原子切换→旧结构延迟释放」。底稿=07⑤节熟场景 2 表。

### 件3 · 变式+边界

**变式题(B2)**【A|滤网:回调线程上下文=通用√】:

- **题干**:事件发布了,报警的 GPIO 动作为什么不直接写在发布回调里,而要绕一圈交给专职告警线程?(锚点:event_bus 回调同步执行;alarm.c:79-83 判定秒回置 pending,响铃在告警线程)
- **接住标准**:回调借发布者(ai 线程)的栈同步执行——回调里 sleep 响铃,云线程发完布就回不去取下一张图;专职线程=「等待没有消失,只是被挪到了唯一以等待为业的线程上」;响铃期间新事件命中照样秒回置 pending(响铃迟、不丢)。

**主动边界(publish 回调锁外与锁内盘 I/O 同框)**【A|滤网:锁边界=主链因果√】:

- **主动交版本**:「回调确实锁外执行——但 publish 自身的四件盘 I/O(INSERT/快照 fwrite/UPDATE 回填/cleanup,event_bus.c:117-174,lock 在 117、unlock 在 174)在锁内,web 四条读路径共等同一把 g_lock:TF 卡变慢时事件列表查询跟着变卡;录像无感,因为 recorder 用自己的锁(recorder.c:32,只保统计)。修法=缩临界区,交换物=long id+jpeg 所有权。一句话:锁是延迟的唯一传染媒介。」

### 件4 · 挂接 20s 版×2【A|滤网:两题均通用√】

- **线程隔离两层 20s**:「⑤说的隔离是控制流层面:云线程挂了超时了,录像预览照跑,失败不沿调用链传染。但它是单核 CPU——八个线程还是分时抢占同一颗核,解码尖峰照样推迟别人。所以完整的说法是:控制流隔开、算力不隔离;要算力隔离得靠多核或限流。」
- **SQLite 与锁 20s**:「事件入库发生在 event_bus 的 g_lock 临界区里;等这把锁的还有 web 的四条查询路径。锁内做了几件盘 I/O,盘速就变成读侧延迟的一部分——数据库本身很快,慢的是『在谁的锁里做』。这也是我审计的第一条主菜。」

### 件3 · 变式+边界

**变式题(精修#10)**【A|滤网:寻址前提=通用 HTTP√】:

- **题干**:MJPEG 预览这条流为什么不支持 Range?回放的 MP4 就按 Range 给——同一个 Web 服务两种待遇,依据是什么?

**主动边界(Range 越界静默重置)**【A|滤网:协议边界=通用√】:

### 件4 · 挂接 20s 版×2【A|滤网:两题均通用√】

- **200/206 与 Range 20s**:「回放链上 200 和 206 的差别就是『整个文件』和『字节区间』。播放器拖进度条时,自己按 MP4 索引把时间换算成字节区间,再向服务器要——HTTP 这层只认字节,不认时间;存储格式与回放协议在 seek 处握手。」
