## 一、背景

**候选人**:校招,嵌入式 Linux 音视频方向,目标企业为海康威视、大华等安防/音视频公司(此类岗位考察权重:多线程/并发 > 流媒体协议与封装 > codec 与码流处理 > 可靠性设计 > 业务功能)。

**项目**:端边云三层智能监控系统。端侧 V821(RISC-V,带 H.264 硬编码)只做采集与 RTSP 推流;云端为多模态大模型识别 API;系统主体在边侧——运行于 **IMX6ULL(800MHz Cortex-A7 单核、无 H.264 硬解 VPU)** 的 C 多线程守护进程(11 个模块),7×24 无人值守,负责拉流、循环录像、实时预览、MP4 回放、抽帧上云识别、事件告警、RTSP 二次分发与 Web 管理。

**硬约束(亮点故事的共同驱动)**:无 VPU / 800MHz 单核 / 可能掉电 / 磁盘有限 / 云端不可靠 / 慢 TCP 客户端 / 配置需在线生效。

**技术栈**:C、pthread、FFmpeg(libavformat/libavcodec/libswscale)、SQLite、libcurl、手写 HTTP 与 RTSP/RTP(无框架)。

**项目事实清单(供漏项检查对照,均为源码核实过的事实)**:
- 录像:不进解码器,remux 成关键帧对齐分段 fMP4(movflags=+frag_keyframe+empty_moov+default_base_moof),开段/切段等关键帧,索引随 fragment 落盘,掉电只损失末尾 fragment
- 分发:单拉流线程一次 av_read_frame 同步扇出到录像/抽帧/转发三路,零队列单写者;软解+缩放+JPEG 编码与 RTP 锁内发送均跑在拉流线程
- 抽帧:逐包送解码器维持参考链,只缓存最新一帧 JPEG 不建队列;读取接口 malloc 深拷贝交割所有权,调用方 free
- RTSP/RTP:手写 OPTIONS/DESCRIBE/SETUP/PLAY 状态机;codecpar 提 SPS/PPS 生成 SDP;NALU 超 MTU 按 FU-A 分片(S/E 位、marker 打访问单元末包);TCP interleaved($+通道+长度)与 UDP 单播双模式
- Web:手写 HTTP,每连接一线程;MJPEG 对内 200ms 节拍轮询缓存、对外单 GET 持续推;MP4 回放 HTTP Range+lseek O(1),越界 start 静默重置为 0 而非 416
- 事件:publish 锁内冻结订阅者快照、锁外执行回调;publish 自身锁内完成写库/落 JPEG 盘 I/O
- 云 AI:独立线程 HTTPS 调多模态接口,失败只丢当前帧;识别启停/帧率热更新
- 配置:tmp+fflush+fsync+rename 原子保存;仅五项运行参数可热更新,地址/端口需重启
- 其他:磁盘水位循环回收(statvfs+按文件名时间戳删最旧);读失败直接重连、录像写错误分级计数;main 逆序停机链;候选人以三层证据法审计全项目并登记 26 处缺陷(含 FFmpeg 所有权契约违反、盘满残缺配置转正、htons 截断、锁内盘 I/O 延迟传染等)

## 三、五条内容与入选理由

### 第①条 压缩域录像设计

**投递稿文案**:无 VPU 约束下录像不进解码器——H.264 不转码直接 remux 成关键帧对齐的分段 fMP4(movflags=+frag_keyframe+empty_moov+default_base_moof),开段与切段都等关键帧,索引随数据逐 fragment 落盘,异常掉电只损失末尾未完成 fragment;CPU 近零的代价是放弃转码能力,资源约束下的主动取舍。

**入选理由**:
1. **岗位命中**:安防厂问「板上怎么录像」时,要的正是 remux vs 转码、GOP 边界、掉电可恢复,不是「调了 ffmpeg」。两名外部评审均将其列为第一。
2. **稀缺性**:校招生能讲清「主路不解码+切段必须等关键帧+fMP4 三旗各换什么」的极少;「压缩域/像素域边界在哪」是本条独占的叙事。
3. **追问深度**:L1 为什么不转码(无 VPU,软解再编码打满单核)→ L2 三旗各解决什么/为什么非关键帧起段不可播 → L3 掉电恢复到什么程度(已完整 fragment 可播,末 fragment 可能损坏≠零丢失)、时间基 rescale 源时基硬编码 1/90000 是实现假设(候选人可主动交代并给修法)。
4. **组合维度**:架构取舍——五条中唯一「约束→机制→代价」完整闭环的条目,放在第一条立住整个项目的人设。
5. **真实性与掌握**:全部机制经源码核实(recorder.c:242 movflags、waiting_key、rescale);候选人经三个阶段验收,该模块为最深掌握档(含 movflags/faststart/时间基变式追问全部通过)。

### 第②条 单核单源三分发与所有权

**投递稿文案**:单拉流线程一次 av_read_frame 后同步扇出到录像、软解抽帧、RTP 转发三路,零队列单写者,避免重复拉流与多份码流拷贝;packet 同步借用、跨线程数据深拷贝交割所有权(读侧 malloc、调用方 free),读写经拷贝隔离无悬垂读者。

**入选理由**:
1. **岗位命中**:多线程/并发是目标岗位权重最高的考察项;「单写者多读者」是 NVR 类产品的经典骨架。
2. **深度**:同时考数据方向(一包三路怎么走)、所有权(谁释放)、生命周期(同步借用 vs 异步必须复制——这一对照是外部评审公认的好句);L3 可答 realloc 悬垂/读者持锁编码的反事实。
3. **架构叙事**:本条是整机数据流的一句话总纲——面试讲任何一条链路都要回到它。
4. **组合维度**:数据流+并发所有权,与①(录像细节)同源不同层,不重复。
5. **真实性与掌握**:三去向/借用语义/单槽所有权均经源码与两轮阶段验收;候选人讲得最深的一块。

### 第③条 自研 RTSP/RTP 二次分发【标注:实现层回补后启用】

**投递稿文案**:手写 RTSP 会话状态机(OPTIONS/DESCRIBE/SETUP/PLAY/TEARDOWN)与 RTP 打包——从 codecpar 提 SPS/PPS 生成 SDP(sprop-parameter-sets),NALU 超 MTU 按 FU-A 分片(S/E 位、marker 打在访问单元末包),支持 TCP interleaved($+通道+长度帧)与 UDP 单播双传输模式,时间戳经 av_rescale_q 转 90kHz。

**入选理由**:
1. **稀缺性为五条之最**:校招生「用过 live555/FFmpeg 推流」很常见;自己把 NALU→RTP 打出来、能讲 FU-A 的极少。两名外部评审分别排第 3/第 4。
2. **岗位命中**:安防厂日常就是 RTSP/RTP,流媒体权重仅次于并发。
3. **追问深度**:L1 播放器 DESCRIBE 后凭什么解码(SDP 参数集)→ L2 FU-A 的 S/E 位与 marker 语义(marker=访问单元末包≠NALU 末片)→ L3 慢 TCP 客户端的背压链(锁内 send_all 拖全部分发——候选人可答出该缺陷与修法)。
4. **组合维度**:自研协议第一条,与④构成「RTSP+HTTP 双协议手写」的完整故事。
5. **真实性与掌握(诚实标注)**:机制为源码事实;候选人协议概念层已收口(分片时机/SDP 语义/参数集),实现层(609 行,含 parse_nalus 对 Annex B/avcC/AVCC 的边界覆盖)回补后才启用本条——回补前投递版降为背景句,不独立展开。

### 第④条 手写 HTTP 媒体服务(无框架)

**投递稿文案**:每连接一线程,慢客户端只占自身线程栈与内核发送缓冲,不拖累主链路;MJPEG 预览「对内按 200ms 节拍轮询最新帧缓存、对浏览器单 GET 后持续推送」两腿设计,协议节奏不受生产帧率波动影响;MP4 回放 HTTP Range 分段,lseek 改内核文件偏移实现 O(1) seek。

**入选理由**:
1. **岗位命中**:「NVR 为什么 Web 预览走 MJPEG 而不是 RTSP」是业务面试高频题;「拉/推两个方向谁在哪条腿」比「做了个网页看视频」高一量级。
2. **深度**:每连接一线程=并发隔离实例(与②呼应);Range 的「HTTP 字节层≠MP4 索引层」分层理解稀缺;L3 强防守题——越界 Range 被静默重置为 0 而非 416,候选人能给出「合规菜单只有 416/200,'206 换内容'是第三种」的完整辩护。
3. **组合维度**:自研协议第二条+Web 并发模型;MJPEG/Range/线程三块耦合为一条是因版面所限(项目区一页纸容量),拆开则每条变薄。
4. **真实性与掌握**:web 模块经三轮阶段验收,两腿/Range/越界重置均为候选人最深档并有独立闭卷证据。

### 第⑤条 旁路失败隔离

**投递稿文案**:云 AI 识别为独立旁路线程,云端超时或失败仅丢弃当前帧,录像与本地预览不受影响,主链路始终可运行;事件发布锁内冻结订阅者快照、锁外执行回调,订阅者耗时不出现在临界区。

**入选理由**:
1. **岗位命中**:7×24 无人值守设备考的是「谁可以挂、挂了主路还在不在」,不是功能列表。
2. **结构说明(重要,请重点审查本条)**:事件回调锁外执行**不单独成条**——因为同一函数 publish 自身在锁内完成写库/落 JPEG 盘 I/O(候选人自己审计出的缺陷:存储变慢时延迟经锁传染查询接口),单独当亮点会被一层追问打穿(曾有外部评审将其独立成条,被另外两名评审一致判为防守失误)。本条以「失败隔离组件」身份进入,配套边界话术主动交代锁内 I/O 与修法(缩临界区/异步队列)。请审查这种「亮点+边界同框」的结构是否成立。
3. **追问深度**:L1 云慢/挂了录像停不停(不停,旁路线程丢帧)→ L2 隔离的层次(控制流隔离,单核 CPU 层面仍互相抢占)→ L3 锁内盘 I/O 事故链与修法。
4. **组合维度**:可靠性,补齐前四条未覆盖的失败路径维度。
5. **真实性与掌握**:降级链与回调上下文经源码与阶段验收;锁内 I/O 缺陷为候选人独立审计产出。
