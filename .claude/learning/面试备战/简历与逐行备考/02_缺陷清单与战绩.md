## 一、四个代表案（先背这四个，每个都能讲三层：现象→根因→机制→修法）

### 代表案 1 · 码率统计恒 0（#1，学生独立发现）

- **现象**：Web `/api/status` 的"当前段码率"永远显示 0，录像本身正常。
- **根因**：`recorder.c:262` 在 `av_interleaved_write_frame`（c:259）**掏空 packet 之后**才读 `out->size`——FFmpeg 契约是 write 成功即拿走引用并把包置空（doxygen 确证 take ownership + blank），所以每次读到 0，`bytes_written` 恒 0，`bitrate_kbps` 恒 0。
- **机制层**：API 所有权契约——引用被拿走后原对象不可再读；"统计错误不等于功能错误"，录像主链无感。
- **修法**：write 之前先把 `out->size` 存入局部变量再累加（一行改）。
- **归属**：2026-08-18 学生独立推出完整因果链。

### 代表案 2 · 盘满时残缺 tmp 被 rename 转正，500 不可达（#26，学生独立断言）

- **现象**：TF 卡写满时在 Web 保存配置，页面返回 200"成功"；重启后配置文件半行损坏（rtsp_url 被拦腰截断，fgets 照样把半行当合法值加载）。
- **根因**：`conf.c:282-284` 的 `fflush/fsync/fclose` 返回值全部未查——盘满导致的部分写失败被整体吞掉，`rename`（c:286）照常执行，残缺 tmp 顶替本体"转正"。真正能返回 500 的盘满路径只有 `fopen` tmp 创建即失败（c:251）一条。
- **机制层**：原子写四步（fflush→fsync→fclose→rename）每步失败语义不同；「数据必须先于名字落盘」「转正是 commit，宣称不能早于事实」。完整事故链 = 盘满→半文件转正→重启加载坏值→静默错配置。
- **修法**：三步查返回值，任一失败 → `unlink(tmp_path)+return -1`（照抄 c:288 rename 失败分支的既有清理模式）。
- **归属**：2026-09-20 Phase 3 总验收场景二，学生独立断言、tutor 源码核实——**面试可认领**。

### 代表案 3 · htons 截断 70000→4464，服务起在无人知的端口（编号外）

- **现象**：`web_port` 配 70000，Web 实际起在 4464 端口，日志还打印 70000（事实性错误日志），看起来"服务挂了"其实是"地址失联"。
- **根因**：`htons` 参数是 `uint16_t`，70000 mod 65536 = 4464；bind 对 4464 合法所以成功——「等 bind 报错 = 等一个永远不会响的铃」。main.c:161-163 只 LOG_WRN 继续跑 = Web 旁路不拖主链。
- **机制层**：字节序转换函数的宽度收缩是静默的；错误日志本身也会说谎，三层证据要以实然为准。
- **修法**：入口校验拦 0–65535（3.6 的 validate_conf 已落地该规则）。
- **归属**：2026-09-20 总验收场景三"实然推翻题设"第二发，学生+tutor 共同核实。

### 代表案 4 · publish 锁内四盘 I/O，写者盘速决定读者响应（编号外，审计①）

- **现象**：TF 卡极慢时，Web 事件列表查询变卡；录像、预览、转发全程无感。
- **根因**：`event_bus` publish（c:117-174）在锁内串行执行 INSERT / fwrite 快照 / UPDATE 回填 / cleanup 四个盘 I/O；web 四条读路径（query_filtered c:228 等）都在等同一把 `g_lock`。
- **机制层**：「锁是延迟的唯一传染媒介」（学生原创句）——慢只沿锁传染给共锁者；录像无感是因为 recorder 用自己的锁（c:32 只保统计）。
- **修法**：缩临界区——锁内只留 INSERT+拿 id+按确定性规则回填路径（`evt_<id>.jpg` 拿到 id 即已知）；交换物 = `long id` + jpeg 缓冲所有权而非 ev 借用；代价 = 读者容忍半文件（孤儿取舍再现）。
- **归属**：贯穿 Phase 2 的审计主菜；2.5 变式 V-c 学生完整推演（锁链/录像无感/响铃固定晚 2s 不丢）。

## 三、面试讲法建议

1. **主动讲的入口**：「学习过程中我对这个项目做过逐模块源码审计，登记在册的缺陷 26 处，独立首发现至少 5 处」——然后挑代表案讲。推荐顺序：#26（故事最完整：现象离奇→500 为什么不可达→rename 语义→修法）→ 审计①（有原创句）→ #1（FFmpeg 所有权契约，最显 API 功底）。
2. **被问"怎么发现的"**：如实分层——大部分是「三层证据法」（注释声称/代码实然/库契约三方对照）+ 失败路径穷举；独立发现的那几处讲当时的推理过程（如 #26 是推演"盘满时 500 到底可不可达"时撞上的）。
3. **被问"修了吗"**：只修了 validate_conf（3.6 动手，入口校验层）；其余登记未修——理由=不动原始项目文件的纪律 + 修复留给动手任务（send_all 迁移方案已备好可当场白板）。板端跑通后可挑 1–2 个落地，成为"分析并验证"闭环。
4. **防塌方**：#11 已推翻不要讲；审计战绩的前提是归属诚实（原型是开源项目，我的角色=部署/审计/加固）。
