### R01 · const 与 #define 的三大区别（#20）

**当时的问题**：10-25 收口场，那段"三差"对比是照着外部范文念的，你自己当场说"这段我是不会的"——是第一轮唯一一个没变成自己的话就过关的点。

**真实的内容**：

把编译器想成一个加工厂，#define 和 const 走的是完全不同的两条流水线：

1. **#define 是开工前的"查找替换"**。预处理阶段（正式编译开始之前），编译器拿着你的源代码做一遍全局替换：`#define SIZE 10`，代码里所有 `SIZE` 在编译器"看到"代码之前就已经变成了 `10`。所以：
   - **没有类型**：`10` 是什么？int？还是随便什么？没人管。你写 `#define SIZE "10"` 再拿它去乘法，编译器一样照单全收，错到运行时才炸。
   - **调试器搜不到**：符号表里根本没有 `SIZE` 这个名字（早就被替换光了），调试断点、报错信息里只见 `10`，排查时你不知道这个 10 从哪来。
   - **不遵守作用域**：从定义那一行开始，之后的全局生效，写在哪就污染到哪，没有"只在这个函数里有效"一说。

2. **const 是"真的变量，只是被贴了封条"**。它正经走编译流程：
   - **有类型**：`const int size = 10;` 类型是 int，编译期就把关——类型不匹配当场报错。
   - **进符号表**：调试器看得见它，报错信息里叫得出名字。
   - **遵守作用域**：定义在函数里就只在函数里有效，和普通变量一样讲规矩。

3. **选型结论**：常量优先 const；#define 只留本职岗位——条件编译（`#ifdef`）和头文件保护（`#include guard`）。

**面试口条**：「#define 是预处理文本替换：无类型不检查、调试器搜不到、从定义处全局生效；const 是有类型的只读变量：编译期把关、可调试、遵守作用域——常量优先 const，#define 只留条件编译的本职。」

**自测**：①为什么 #define 定义的常量在调试器里看不到名字？②`const void *buf` 这种参数里的 const 是干什么用的？（答：写在类型里的契约——你的缓冲区我只读不写，调用方不用强转，零成本的安全。）

### R03 · mutable：const 函数里的"豁免名额"（P1#40，首次教学）

**当时的问题**：第一轮从没教过——当时说好留到 C++ 专题再讲，一直挂账到现在。

**真实的内容**（C++ 内容，先打比方）：

把类的 const 成员函数想成一份**"承诺书"**：我保证在这个函数里不改对象的任何成员。但有些成员很特殊——改了它们不算"违背承诺"，比如**缓存**、**访问计数**、**锁**。这些成员改了不影响对象的"业务状态"，只影响实现细节。

`mutable` 就是给这类成员发的**"豁免牌"**：挂了 mutable 的成员，即使在 const 函数里也照样能改。

（读不懂下面的 C++ 代码也没关系：`class` 你先当成"**带函数的 struct**"——把数据和操作它的函数打包在一起；函数名后面那个 `const`，就是那份承诺书的书面形式。）

```cpp
class Config {
    mutable int cache_value;        // mutable：缓存，改它不算改状态
    mutable bool cache_valid;       // mutable：缓存有效标志
    int real_value;                 // 普通成员
public:
    int get() const {               // const 承诺：不改业务状态
        if (!cache_valid) {         // 但 mutable 成员随便改
            cache_value = expensive_load();
            cache_valid = true;
        }
        return cache_value;         // real_value = 1; ← 这行会报错，违背承诺
    }
};
```

一句话：**const 管的是"逻辑状态"，mutable 豁免的是"实现细节"**。面试常追问"什么时候用"：答案是缓存、统计计数、线程锁这三类——改了它们，对象对外表现完全没变。

**面试口条**：「mutable 修饰的成员变量在 const 成员函数里也能改——const 承诺的是不改逻辑状态，mutable 豁免的是缓存、计数、锁这类实现细节。」

**自测**：const 成员函数里给普通成员赋值会怎样？给 mutable 成员赋值呢？（前者编译错误，后者合法。）

### R11 · static 与链接：符号进不进"公开电话簿"（#19）

**当时的问题**：10-12 验收时把 undefined reference 那条因果链说反了，隔场重述后转绿。

**真实的内容**：

每个 .c 文件是**单独编译**的，互不见面；最后由**链接器**把所有 .o 拼起来。链接器怎么知道"fileA 里用的函数在 fileB"？靠**全局符号表**——相当于一本"公开电话簿"，每个文件把自己**对外提供**的函数和全局变量登记上去。

- **普通函数/全局变量**：登记进电话簿，全项目都能通过 extern 声明找到它。
- **static 函数/全局变量**：**不登记**（术语叫"内部链接 internal linkage"）——它是你的私人号码，只在本文件可见。

所以那条链是：`extern` 声明只告诉**编译器**"这名字在别处定义"，编译这一关能过；到了**链接**这一关，链接器翻遍公开电话簿都找不到 static 函数 → **undefined reference**。

反向推论也成立：两个文件里各写一个同名 static 函数，互不冲突（都是私人号码，各打各的）；去掉 static 才会撞车。

**面试口条**：「static 的链接含义是符号不进全局符号表——extern 声明只骗过编译器，链接器查不到就 undefined reference；同名 static 函数互不冲突，因为链接认的是符号不是代码。」

**自测**：A.c 定义 `static void helper()`，B.c 里 `extern void helper();` 后调用——编译和链接分别过不过？（编译过、链接挂：undefined reference。）

### R12 · strncpy 的坑：方向别记反（#24）

**当时的问题**：验收时把"源短补零/源长截断"两个方向说反了，当场重述补收。

**真实的内容**：

先记住 strncpy 的性格：**它的任务是"填满 n 个字节"，对 \0 没有执念**。分两种情况：

- **源串 ≥ n（源长）**：只拷前 n 个字符，**一个 \0 都不给**——缓冲区里是一段"有头没尾"的字符串，后面接着什么全看运气。这是最危险的坑：**截断且不保尾**。
- **源串 < n（源短）**：拷完整串，剩下的位置**全部填 \0 填满 n 个**——安全但浪费。

方向记忆法：strncpy 只保证"不越界"，不保证"有结尾"。所以工程铁律：**用它必查结尾**，`buf[n-1] = '\0';` 手动补一刀。

对比着记（这是常考连环问）：
- `strcpy`：只认 \0 不认边界——两头坑（写出界 + 停不下）
- `strncpy`：管住不越界，管不住保尾（源长截断无 \0，源短反而填满）
- `snprintf`：保尾且最多写 size-1（见 R18）
- 码流/二进制数据：一律 `memcpy`——\0 是合法数据，strcpy 家族遇它就断

**面试口条**：「strncpy 源长于 n 时截断且不补 \0，源短时反而填满 n 个零——用它必查结尾；它管得住不越界，管不住保尾。」

**自测**：`strncpy(buf, "ab", 6)` 执行完 buf 里是什么？（"ab" + 4 个 \0。）`strncpy(buf, "abcdef", 3)` 呢？（'a''b''c'，没有 \0。）

### R17 · sizeof 是运算符 + 数组传参退化（#23）

**当时的问题**：「sizeof 是运算符不是函数」这个身份层，10-23 快验时你自报"原来不知道"——之前只知道编译期/运行期的区别。

**真实的内容**：

两件事分开记：

1. **身份**：sizeof 是**运算符**（和 +、* 一个家族），不是库函数。证据有两个：
   - 求值发生在**编译期**——编译器数出类型大小直接换成常量，程序跑起来根本没这一步；
   - 不加括号也能用于变量：`sizeof buf` 合法（函数调用必须带括号）。
   它数的是**类型占几字节**：`sizeof("abc")` = 4（**含 \0**）；而 `strlen("abc")` = 3——strlen 是库函数，运行时一个一个数到第一个 \0 停（不含）。

2. **退化**：数组一传参就退化成指针，大小信息在退化那一刻就丢了：

```c
void f(char buf[100]) { sizeof(buf); }   // = 8（64位指针），不是 100！
```

这就是为什么 `send_all` 这类接口**必须显式传 len**：一退化拿不到大小；二码流里 \0 是合法数据，用 strlen 会截短。

**面试口条**：「sizeof 是运算符不是函数，编译期出结果，数类型占几字节（字符串含 \0）；数组传参即退化成指针，大小信息那一刻就丢——所以接口必须传 len，strlen 遇 \0 会截。」

**自测**：64 位机器上 `char s[100]; sizeof(s)` 和传进函数后 `sizeof(buf)` 各是多少？（100 / 8。）

### R18 · snprintf 的截断细则（#24）

**当时的问题**：10-23 首次学，你自请冷查；当晚复测收了，但只验过一次。

**真实的内容**：

snprintf 的规矩三条，记成"**最多写 size-1，必留一个位置给 \0，返回值是理想长度**"：

1. 缓冲区 size=10，格式化结果理想长度 25 → 实际只写入**前 9 个字符**，并在 `buf[9]` 强制放 \0——**永远保尾**（这就是它比 strncpy 安全的地方）。
2. 剩下的 16 个字符**直接丢弃**。
3. **返回值 = 理想长度 25**（不是实际写的 9）——所以一行就能探测截断：`if (ret >= size) // 被截了`。这个返回值是天然的"截断探测器"。

**面试口条**：「snprintf 理想长度 ≥ size 时只写前 size-1 个字符并强制补 \0，剩余丢弃；返回值是理想长度——ret ≥ size 即知被截断，天然的截断探测器。」

**自测**：`char b[4]; int r = snprintf(b, 4, "abcdef");` —— r 是几？b 里是什么？（r=6；b = 'a''b''c''\0'。）

### R02 · 结构体对齐：末尾填充是给谁垫的（#17）

**当时的问题**：10-21 答到满分，10-25 冷不丁再问又滑了——手算规则都在嘴上，但"末尾填充**为了谁**"这句目的缺席。这个点滑过一次，说明记忆强度不够。

**真实的内容**：

先复习规则（你都熟）：
- 每个成员放在**自己对齐数整数倍**的地址上（int 对齐数 4，就放 4 的倍数处）；
- **结构体自己的对齐数 = 成员里最大的那个对齐数**；
- 总大小要**补成这个对齐数的整数倍**——不够就在末尾填空字节。

关键问题来了：**末尾这块填充，单个结构体看纯属浪费**——最后一个成员都放完了，后面垫的字节谁也不用。那编译器为什么非要填？

答案：**为了数组**。

```c
struct S { char c; int i; };     // sizeof = 8：c 占 0，i 占 4-7，末尾没有填充也正好 8
struct T { char c; int i; char c2; };  // sizeof = 12：c2 在 8，9-11 填充——为什么？
```

因为 C 语言里数组是**紧密排列**的：`struct T arr[10]`，第二个元素从地址 12 开始——如果总大小是 9 而不是 12，那么 arr[1].i 就落在 9+1=10 的位置，**不是 4 的倍数，不对齐了**。所以编译器把每个元素都补成 12，数组里**每个元素的每个成员**才都自然对齐。

一句话钉死：**末尾填充是给数组垫的——单个结构体看是浪费，放进数组才明白。**

**面试口条**：「编译器把结构体总大小补成最大成员对齐数的整数倍——是**为数组**填的：struct a[10] 紧密排列，每个元素的每个成员才都自然对齐；单个结构体看，末尾字节纯属浪费。」+「结构体自己的对齐数 = 成员里最大的那个对齐数。」

**自测**：`struct { char a; short b; char c; }`（32 位机）sizeof 是几？末尾填几个字节、给谁垫？（6；末尾填 1 个，为 short 的数组对齐垫。）

### R15 · 爆栈：MCU 和 Linux 是两套答案（#16/#18）

**当时的问题**：10-19 你拿单片机裸机的模型去答 Linux 的题，被判"层次混淆"后当场分层复述通过。

**真实的内容**：

同一个问题"栈满了会怎样"，两个世界两套答案——面试时**先分世界再作答**，这就是加分点：

**MCU 裸机世界**：栈是启动文件/链接脚本里划死的**固定一块**，没有任何防线。SP 一越界，读写的就是隔壁的变量或外设区——**没有任何第二道防线，直接跑飞**。

**Linux 世界**：栈是**可以自动向下生长的**。内核给每个线程记着一块"栈区户口"（VMA），程序访问栈区下边界再往下一点点，内核发现是栈在扩，**自动补一页新栈**——小超有救。但防线之后还留着一条**保护带**（guard gap）：`char buf[2*1024*1024]` 这种大数组一次把 SP 推过好几页，直接跳过保护带，**没有机会触发扩栈，段错误**。

所以 Linux 上的完整答案：**大局部缓冲上堆、深递归同理**；8MB 默认上限内的小幅自动扩展是内核兜的。

**面试口条**：「Linux 栈能自动向下扩展，但大缓冲一次把栈指针推过保护带就直接段错误——大数组放堆；裸机上栈是固定区域没有防线——先分平台再答。」

**自测**：为什么 `char buf[8*1024*1024]`（≈默认栈上限）在 Linux 上大概率段错误，而递归每层只用 100 字节的深递归反而能扩一阵？（大数组一次跨过保护带触发不了扩栈；逐层下行每页都能触发 VMA 扩展，直到 8MB 上限。）

### R19 · 零页：读白看，写才有真页（#21）

**当时的问题**：10-23 首次学，当晚复测过一次，纠过一个口误（"复制页表"→实际复制的是全零内容到新专属页，页表只改一条指向+权限）。

**真实的内容**：

三步链条：

1. **.bss 不占文件体积**：可执行文件里只"记账"（这一段多大），不存数据——反正全是 0，存它浪费磁盘。
2. **加载时上户口**：内核给整段登记虚拟地址范围（承诺这些地址合法、内容全零），但**一个物理页都不给**——零内存成本。
3. **首次访问才兑现**：
   - **读**：映射到一张全系统共享的**只读零页**——一张全 0 的物理页，所有 bss 变量的读都指向它。还是零成本。
   - **写**：写只读页触发缺页 → 内核**分配一张专属物理页 → 内容清零 → 页表把这一页改成可写、指向新页**。从此这个变量才有自己的真页。

这就是"**承诺全零，兑现延迟到访问**"——malloc 同理：成功≠有内存，只=虚拟地址批下来了。

**面试口条**：「bss 文件只记账不占体积；加载上户口承诺全零；首次访问给页清零兑现——细版：读共享只读零页，写才分配专属页+清零+改可写。」

**自测**：一个 1MB 的未初始化全局数组，程序只读不写，物理内存开销大概多少？（几乎为 0——读全指向那一张共享零页；只有 4KB 零页本身。）

### R20 · 一块内存一个主人：所有权转移（#25）

**当时的问题**：所有权原则句当时过了，但项目落地是当场补空的（get_jpeg 的例子你自己推的）——落地句需要冷验。

**真实的内容**：

C 语言没有垃圾回收，谁负责 free 必须说清楚。工程原则一句话：**一块内存一个主人**——任何时刻，能合法决定这块内存生死的人恰好一个。

项目里的标准做法（frame_grabber_get_jpeg）：模块内部存着最新帧（下一帧来了直接覆盖），调用方要图，模块 **malloc 一份拷贝**返回。这一下完成**所有权转移**：
- 内部那帧还是模块的——模块覆盖它天经地义；
- 拷贝这份是你的——用完你自己 free，谁也不会抢。

反例为什么毒：如果直接返回内部指针——①你还没用完，下一帧一到**数据被覆盖**，拿到的是脏的；②用完后你 free 了它，**模块下一帧写进去就是写已释放内存**——崩溃和悬空两头堵。返回内部指针 = 人为制造多别名 + 说不清该谁 free。

**面试口条**：「一块内存一个主人：get_jpeg 返回 malloc 拷贝——所有权随返回值转移，内部帧归模块、副本归调用方用完自己 free；返回内部指针 = 下一帧覆盖 + free 责任说不清，人为制造悬空。」

**自测**：为什么不返回内部帧指针让调用方"只读不 free"？（只读约定没有强制力，且下一帧覆盖照样读到脏数据；拷贝是唯一同时保数据安全+责任清晰的路。）

### R04 · 网络序大端：谁先上线（#22）

**当时的问题**：方向句缺席三次 + 口误一次（说成"低位到高位"——那是小端的读法），第 4 轮流程演示后才真正自产。这是全册滑得最多的句子之一。

**真实的内容**：

先把两个端说死（用"地址"记）：
- **大端**：高位字节放**低地址**（0x12345678，地址 0 存 0x12）——**网络序就是大端**。
- **小端**：低位字节放低地址（地址 0 存 0x78）——x86 就是小端。

网络上发送是**从低地址开始一个字节一个字节发**。大端低位地址放的是高位字节 → **高位字节先上线**。

记忆钩子：**"大端 = 大头先出门"**（大头=高位字节）。你上次的口误"低位到高位"说的是小端的读法，方向反了。

为什么网络序选了大端（追问预备）：①**决定性信息先到**——长度字段的高位字节先到，接收方能边收边比较判断；高位先到就像报数先报"几万"再报"几千"，量级先有；②ARPANET 历史沿用。

**面试口条**：「网络序大端：高位字节住低地址、低地址先发——高位字节先上线，决定性信息先到。」

**自测**：32 位值 0x000000C8（200）走网络发送，第一个字节是什么？（0x00——高位字节先上线；这也是 htons 截断 bug 的现场：32 位值交给 16 位函数，高 16 位直接没进去。）

### R09 · 确认号：要的是"下一个"（#8）

**当时的问题**：10-11 快筛答反——说成"已收到的最后一个字节"，10-21 修复+手算满分。

**真实的内容**：

一句话本质：**确认号 = 我期望你发的下一个字节**。

为什么这么设计（追问预备）：因为 TCP 是**累积确认**——"我要第 801 个"这个动作本身**隐含承认了 800 及之前全收到**。不用逐个报"1 收到、2 收到"，一句"要下一个"全办了，效率高。

配套三件（面试常连着问）：
- **手算**：seq=1000，发 200 字节 → 最后一个字节编号 1000+200−1=1199 → 确认号 1200。（别记成"从零开始数"——正解是：seq 本身就是**第一个字节**的编号，所以最后一个字节 = seq + 长度 − 1。）
- **SYN/FIN 占序号**：不带数据但各占 1 个序号——握手挥手 x+1 的统一根源。
- **ACK 位 = 确认号字段的生效开关**：SYN 包里 ACK=0，确认号字段无效——因为还没有对方的东西可确认。

**面试口条**：「确认号 = 期望的下一个字节——要下一个的动作就是确认的动作（累积确认）；seq=1000 发 200 字节，确认号 1200；SYN/FIN 不带数据但占一个序号。」

**自测**：收到 seq=2000、长度 500 的段，ACK 里确认号填多少？（2500。）

### R16 · 四次挥手：③不等②（#2）

**当时的问题**：小纠一处——你曾以为第③步（B 发 FIN）要以收到②（A 的 ACK）为前提。

**真实的内容**：

四步各自的身份先摆正（A 主动关）：
- ①A 发 FIN（A 应用调 close）
- ②B 的**内核**收到，**替应用立即回 ACK**——反射动作，不等任何人
- ③B 的**应用**调 close 时才发 FIN——**等的是应用表态，不是②的 ACK**
- ④A 回 ACK

③和②之间隔着 CLOSE_WAIT——B 的应用还没表态的窗口。所以③的触发条件**只有一个：B 应用调 close**。事实上②的 ACK 在路上时 B 应用完全可能已经调了 close，②③可以**合并成一帧**（FIN+ACK）——这时四次变三次，完全合法。

这也是"为什么挥手四次、握手三次"的统一答案（下一点的地基）：**能合并的前提是两件事都是内核行为**；挥手里有一件（③）要等应用，合并不了。

**面试口条**：「③FIN 只等一件事——应用调 close 表态；不等②的 ACK。应用表态快的话②③合并，四次变三次，完全合法。」

**自测**：CLOSE_WAIT 状态卡在哪一步之间？等的是谁？（②和③之间；等应用调 close。）

### R23 · 握手状态名：SENT 和 RCVD 各等什么（#1）

**当时的问题**：状态名当时三轮填空才落地，挂了冷抽。

**真实的内容**：

握手五步三状态，用"**谁在等、等什么**"记：

| 状态 | 谁处于这个状态 | 怎么到的 | 在等什么 |
|---|---|---|---|
| SYN_SENT | **客户端** | 发出 SYN | 等回音（SYN+ACK） |
| SYN_RCVD | **服务端** | 收到 SYN、回了 SYN+ACK | 等最后一次 ACK |
| ESTABLISHED | 双方（客户端先到） | 各自收齐 | — 开工 |

记法钩子：**SENT = 我发出去了在等；RCVD = 我已答复在等**。（谁先进入 ESTABLISHED？——客户端：收到 SYN+ACK 就进；服务端要等第三次 ACK 到了才进，晚一步。）

**面试口条**：「SYN_SENT=客户端发出 SYN 等回音；SYN_RCVD=服务端已回 SYN+ACK 等末次 ACK——SENT 是我发出去在等，RCVD 是我答复了在等。」

**自测**：第一次 ACK 丢了（第三次握手没到服务端），双方各在什么状态？（客户端 ESTABLISHED，服务端 SYN_RCVD；客户端随后发数据时带 ACK 可救活。）

### R24 · 为什么挥手不能像握手那样合并（#2）

**当时的问题**：合并机制当时缺主体（谁在反射、谁在等表态），填空补出后收口——机制句待冷抽。

**真实的内容**：

对比着看，一句话见底：

- **握手三次能合并**：SYN+ACK 是**一个内核动作**——服务端内核一口气把"我同意+我的起始序号"说完。
- **挥手四次难合并**：②和③**分属两个主体**——
  - ②ACK 是 B 的**内核反射**：收到 FIN 立即代答，**马上走**；
  - ③FIN 要等 B 的**应用调 close 表态**——数据可能还没发完（半关闭：②③之间 B 还能继续发数据），内核**不能替应用做主**。

一个马上走、一个等表态，中间隔着不确定的时间窗（CLOSE_WAIT），所以通常合不了。只有 B 应用恰好秒表态，②③才并成一帧。

**面试口条**：「挥手不能合并的根源是主体不同：②ACK 是内核反射马上走，③FIN 等应用调 close 表态——一个马上一个等，中间隔着 CLOSE_WAIT；握手能合并因为 SYN+ACK 都是内核一口气的事。」

**自测**：半关闭区间里 B 还能干什么？（继续发数据——FIN 只关 A 那半边：A 停发不停收。）

### R05 · TIME_WAIT 第二个理由：让旧报文死透（#3/#6）

**当时的问题**：这句被点名 4 次你才自产出来（10-24 你自己都说"这点不会"）——全册最顽固的句子之一。

**真实的内容**：

TIME_WAIT 停 2MSL 有**两个理由**，第一个你熟（最后的 ACK 丢了还能应答对端重发的 FIN），第二个就是这句：

**MSL = 一个报文在网络里的最大生存时间**（TTL 跳数耗尽自然消亡）。等满 2MSL，就是给本连接四元组（源IP+源端口+目的IP+目的端口）相关的**所有在途报文留够时间死透**。

不等的后果（推演一遍就记住了）：立刻用**同样的四元组**建新连接 → 网络里迷路的旧数据正好到达 → 新连接的 TCP 一看序号在窗口内，**当成本连接的合法数据收下** → 脏数据混进来，业务出错还查不到。

一句话：**等旧报文死透，防新连接撞四元组收脏数据。**

**面试口条**：「TIME_WAIT 停 2MSL 双保险：一保最后的 ACK 丢了能应答重发 FIN；二等旧报文死透——防止同样四元组的新连接收到迷路旧数据。」

**自测**：TIME_WAIT 挂在主动方还是被动方？为什么大量 TIME_WAIT 的常见场景是"高频主动关的短连接"？（主动方；每单短连接自己先关，自己进 TIME_WAIT。）

### R06 · TIME_WAIT 的"安全说法"（#3/#6）

**当时的问题**：「等最后一个 ACK 确认到达」这个句式你说过两次——它有个隐藏错误，申诉后判了"表述歧义"，但面试安全版必须固定下来。

**真实的内容**：

危险句式：「我等对方的 ACK 确认到达」。**错在：TCP 没有 ACK 的 ACK**——你发的最后那个 ACK，对方**不会回执**。你在等一个永远不会来的东西，这句话在面试官耳朵里就是概念没通。

安全版一句话：「**我等的不是谁的回音，我等的是『对端重发的 FIN 不来』这件事**——等满 2MSL 没动静，说明我最后的 ACK 他收到了。」

逻辑链：如果对方没收到我的 ACK → 对端内核会**重发 FIN**（它还在 LAST_ACK 里）→ 我这边一动静就重答 ACK。2MSL 内没等到任何重发 → 反推 ACK 到了。守站的是我，重发 FIN 的是对端——主语别放反。

**面试口条**：「我等的不是谁的回音，等的是对端重发的 FIN 不来这件事——等满 2MSL 没动静，说明我最后的 ACK 他收到了。」

**自测**：如果 2MSL 内对端重发了 FIN，TIME_WAIT 方做什么？计时器怎么办？（再答一个 ACK，计时器重置重新等。）

### R07 · 队头阻塞：丢一段，后面全排队（#6）

**当时的问题**：教后滑过 2 次（一次批2问答没带出、一次验收主问没带出），后来你自己造了"数据价值随时间衰减"这句才收口。

**真实的内容**：

TCP 的承诺是**可靠 + 有序**：字节流按序交付给应用。代价在这：

丢了一段 → **后面已经到达的数据也不能交给应用**，全在缓冲区排队等补传 → 补到才能按序放行。队列的头（丢的那段）卡住了整队——这就是"队头阻塞"。

用直播画面看：丢一段 → 后面全停着等补传 → 用户看到的就是**卡顿**。而 UDP 丢旧不堵新：旧帧迟到了没用，扔掉就是，新帧照播——**实时视频要新鲜不要完整**。这就是预览走 UDP 系、回放走 TCP 的选型根源。

（扩展一层，追问预备：HTTP/2 里的"队头阻塞"是另一个层面——TCP 层只有一个字节流，一条逻辑流丢包阻塞全部逻辑流；QUIC/HTTP3 用 UDP 就是为了解这个。知道有这两层即可，别混着说。）

**面试口条**：「TCP 有序交付的代价：丢一段，后到的全排队等补传——队头卡住整队；UDP 丢旧不堵新——实时视频要新鲜不要完整。」

**自测**：为什么说"只用 TCP 传直播"是选型错误？（丢一段后面全卡等补传=用户看到卡顿；直播要的是新鲜度不是完整度。）

### R25 · FU-A 分片 vs IP 分片：发货前装箱 vs 中转站强拆（#7）

**当时的问题**：这两句当时是你超规格自产的（超出了教学深度），但自产过≠冷验过——挂冷抽。

**真实的内容**：

大 NALU（比如一个关键帧几百 KB）怎么塞进 MTU 1500？两个方案，**层次完全不同**：

- **RTP 层 FU-A 分片（项目用的）= 发货前分好箱**：编码后、发送前，把大 NALU 按 RTP 载荷上限切开，**每一片都装进完整的 RTP 包**——每箱都有全套 IP/UDP/RTP 头，是一个**完整的协议单元**。丢一箱，接收端 RTP 层知道缺了哪片，等重传或整帧丢。
- **IP 层分片（尽量避免）= 中转站强拆**：数据报超过链路 MTU 时 IP 层硬拆——可能在发送主机出口，也可能在途中路由器，哪里超了哪里拆。**只有第一片带着 UDP/TCP 头**（端口等信息），后面片没有。IP 层**没有重传机制**：丢任何一片，整个数据报作废——应用层一个字节都收不到，还得靠上层重传整个数据报再赌一次。

所以 MSS=1460（1500−20 IP头−20 TCP头）让 TCP **自己切、丢哪段重传哪段**；UDP 应用（如 RTP）就自己在应用层切（FU-A 就是干这个的），把分片的控制权握在自己手里。

**面试口条**：「FU-A 是发货前分好箱——每箱都有完整 IP/UDP/RTP 头，是完整协议单元；IP 分片是中转站强拆——只有第一片带端口，丢一片整包作废，IP 只管运不管赔。」

**自测**：为什么说"IP 分片的片不是独立协议单元"？（后续片没有传输层头，端口、长度信息只在第一片里——单独到达没法交给上层。）

### R08 · 共享内存：最快，但同步全自理（#28）

**当时的问题**：这句你早就答到过满分，但 10-21 补句场回归滑了一次，重教"三病模型"后收口——满分句回归滑，说明需要冷验钉死。

**真实的内容**：

共享内存为什么最快：两个进程的虚拟地址**映射到同一块物理内存**，数据一次写入两边立即可见——**内核零参与**（对比管道：数据要穿过内核缓冲，两次拷贝）。

但"内核零参与"是双刃剑——内核只提供"同一块内存"这个事实，**秩序一概不管**。三个病全要自己治（三病模型）：

1. **闸门病（互斥）**：两边同时写同一位置 → 数据踩乱。治法：**信号量初值 1 当闸门**（同一时刻只放一个进）。
2. **顺序病（同步）**：A 还没写完 B 就读了。治法：**信号量初值 0 当通知**（A 写完 V 一下，B 的 P 睡到通知才醒）。
3. **存亡病**：一方崩溃/退出，另一方还在读写——读写到已释放的映射。治法：引用计数/心跳，或干脆换本地套接字。

**面试口条**：「共享内存零拷贝最快，但闸门/顺序/存亡三病同步全自理——配信号量：初值 1 当闸门，初值 0 当通知。」+「进程讲通信线程讲同步——隔离借内核，同空间直接锁。」

**自测**：信号量初值 1 和初值 0 分别解决哪个病？（1=互斥闸门；0=先后通知。）

### R10 · volatile：管可见性，不管原子性（#14）

**当时的问题**：快筛期你曾认为 volatile i++ 是原子的——错。10-20 联动收口+CAS 补课。

**真实的内容**：

volatile 只做两件事：①每次访问**强制从内存读**（不许把变量缓存在寄存器里偷懒）；②**禁止编译器把它优化掉或挪动位置**。就这两件——它管的是**可见性**。而且注意边界：它只管编译器这一层，管不住 CPU 自己的乱序执行——所以 volatile 只能做到"看得见"，做不到"排好队"，**多线程同步不能靠它**。

但 `i++` 根本不是"一步"，它是**读→改→写**三条指令。两个线程同时 volatile i++：都读到 5（都从内存读的，可见性没毛病）→ 各自加 1 → 都写回 6。两次自增丢了一次——**可见性没问题，原子性丢了**。

要原子，三条路：①C11 `atomic_int` 原子类型；②平台原子指令（x86 lock 前缀/CAS 比较交换）；③上锁。

volatile 的本职场景（追问预备）：**内存映射寄存器**（硬件寄存器值随时被外设改，编译器不许缓存优化）和**多线程共享的标志位**（只有"一个线程写、其他线程读"的简单场景，无复合操作）。

**面试口条**：「volatile 只管可见性——每次从内存读、禁止优化；i++ 是读改写三步，volatile 管不住中间被人插队——原子要靠 atomic 类型、CAS 指令或锁。」

**自测**：volatile 最本职的用途是什么场景？（内存映射寄存器——硬件随时改，编译器不许把它优化进寄存器。）

### R13 · fork 与 fd：拷的是壳，不是肉（#27）

**当时的问题**：你说反过一处——"父子 fd 号不同"。实际**号相同**、指向同一次打开。

**真实的内容**：

fork 干了什么（一句话）：**拷壳不拷肉**——页表复制一份、物理页先共用，谁写谁分家（COW）；fd 表**照抄**一份，**号一样**，指向内核里**同一个"打开的文件"结构**（同一个 file 结构）。

推论一条条来：
- **偏移共享**：fd 指向同一个 file 结构，里面的文件偏移量只有一份——父写了 100 字节，子接着写在 100 之后，**接着写不覆盖**。
- **号相同 ≠ fd 表同一张**：各自有自己的 fd 表，只是出生时内容一样。fork **之后**各自新开的 fd 互不可见。
- **全局变量**：各写各的互不可见——**地址一样，内存不一样**（COW 分家了）。

**面试口条**：「fork 拷的是壳不是肉——页表复制物理页共用，写了才分家；fd 表照抄号同，指向同一次打开，偏移共享，父子先后写是接着写不覆盖；各写全局互不可见——地址一样内存不一样。」

**自测**：fork 后父子都往同一个 fd 写 10 字节，文件里是 20 字节还是 10 字节被覆盖？（20 字节——偏移共享，接着写。）

### R14 · 管道单向 + 信号量 V 只发许可（#28）

**当时的问题**：两处概念错——「FIFO 是双向」（错，单向）；「V = 读完清空内存」（错，V 不碰数据）。

**真实的内容**：

**管道（无名/有名 FIFO）都是单向的**：一端只写、一端只读，像一根水管。要双向？**两条背靠背**——一条 A→B、一条 B→A。为什么不用一根"双向"的：防止**自读回声**（自己刚写的数据被自己读到）。无名管道靠血缘（fork 继承两端 fd），有名 FIFO 靠文件系统的名字（任意进程可用，但仍单向）。

**信号量的 P/V 各干什么**（停车场模型）：
- 计数器 = **剩余车位数**（资源余量）。
- **P**：车位够（计数>0）→ 减一进去；不够 → 睡在门口排队（阻塞，不是返回错误）。
- **V**：只做两件事——**计数加一 + 叫醒门口一个等待者**。就这两件，**完事**。

V **不碰任何数据**——它只是"发一张许可"。数据本身在双方约定的缓冲区里，靠读写那边的代码搬。V 清空内存？想多了：它连缓冲区在哪都不知道。

**面试口条**：「管道单向不变，双向 = 两条背靠背（防自读回声）；FIFO 只是有名字让无血缘进程找到，仍单向。P 占坑不够就睡，V 只加一 + 叫醒一个——发许可不碰数据，数据靠双方缓冲区约定。」

**自测**：信号量计数是 −3，什么意思？（3 个等待者睡在 P 上——正数=余票，负数=欠条/排队人数。）

### R21 · 条件变量：返回时锁在手 + broadcast 叫错人（#13）

**当时的问题**：两句挂冷抽（你自己自请的）：「wait 返回时锁已回到手里」和「混等两类条件必须 broadcast」。

**真实的内容**：

**第一句：wait 的完整旅程**（三段）：
1. 挂进等待队列（先挂队）；
2. **原子地**放锁 + 入睡（这两步绑死，中间没人能插进来改条件——这就是"检查与入睡原子"）；
3. 被 signal 叫醒 → **重新抢锁，抢到才从 wait 返回**。

所以 wait 返回那一刻，**锁已经回到你手里**——醒来后检查条件自带保护，这就是为什么 while 重判是安全的、必须的（醒来≠条件成立：虚假唤醒 + 多消费者偷条件）。

**第二句：signal 会叫错人**。条件变量不认识"谁在等什么"——signal 只是随便叫醒一个。如果**两类线程混等同一个 cv**（比如有的等"队列非空"、有的等"队列未满"）：signal 叫醒的可能是个"等未满"的——它一看条件不满足，又睡回去了；而真正能干活的（等非空的）还在睡 → **活锁**：大家都醒过，没人干成事。治法：混等场景必须 **broadcast 全叫醒**，配合 while 各自重判——九个白起也只付白起的代价，不出错。

配套边界（追问预备）：条件变量**没有不配锁的用法**（API 绑死）；signal 调用方可以不持锁；无锁干等一个信号 → 用信号量（初值 0 当通知）。

**面试口条**：「wait 一进两段——先挂等待队列，再原子放锁入睡；醒后重新抢锁，抢到才返回——返回时锁已回到手里，while 重判自带保护。」+「混等两类条件必须 broadcast——signal 会叫错人：叫醒的检查完睡回去，能干活的还在睡，活锁。」

**自测**：为什么 signal 的调用方可以不持锁？（signal 只做"叫醒"动作，不动条件本身——条件修改和叫醒之间的窗口由 waiter 的 while 重判兜底。）

### R22 · TLB：页表的高速缓存（#11）

**当时的问题**：10-23 深化场新钉的边界句，挂 TLB 追问冷抽。

**真实的内容**：

每次内存访问都要先做**虚拟地址→物理地址**的翻译，翻译要查**页表**——查页表本身也是内存访问，太慢。TLB（翻译后备缓冲）就是 **MMU 里的页表缓存**：把最近用过的"虚拟页号→物理页框"映射记在芯片内，命中就不用查表。

三个边界点（面试就考这三句）：
1. **每核一份**：CPU 每个核有自己的 TLB——两个核的缓存互不通气。
2. **软件不可单条读写**：程序（包括内核）不能一条指令读/改 TLB 某一项，只能**整批作废**（flush）。
3. **进程切换的隐藏账单**：换进程 = 换页表 → 新进程的虚拟地址和旧映射全对不上 → TLB **整体作废**，接下来一段时间翻译全要慢查页表"重新热身"。**线程切换不换页表 → TLB 保住**——这就是"进程切换比线程贵"的一大来源（另一半是页表本身的切换成本）。

**面试口条**：「TLB 是 MMU 内的地址翻译缓存，每核一份；软件不可单条读写只能整批作废；进程切换换页表 → TLB 全作废重新热身——线程不换页表所以便宜，这是进程/线程切换成本差的大头。」

**自测**：为什么线程切换 TLB 不用作废？（同一进程内的线程共享同一个页表——虚拟→物理映射没变，缓存依然有效。）
