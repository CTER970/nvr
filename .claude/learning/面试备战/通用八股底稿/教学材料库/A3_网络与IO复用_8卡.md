## 卡 1 · #1 三次握手（高频·19 家网络桶·场1 绿保温）

**主轴句**：三次是"双方都确认了对方的收发能力+同步初始序号"的最小次数。

**结构图**：
```
客户端                          服务端
  │ ── SYN, seq=x ──────────────→ │  服务端确认: 客户端能发, 自己能收
  │ ←─ SYN+ACK, seq=y, ack=x+1 ── │  客户端确认: 双方收发全通
  │ ── ACK, ack=y+1 ────────────→ │  服务端确认: 客户端能收, 自己能发  ← 第3次的作用
状态: CLOSED→SYN_SENT→ESTABLISHED   LISTEN→SYN_RCVD→ESTABLISHED
```

**维度表**：

| 次 | 报文 | 完成的确认 |
|---|---|---|
| 1 | SYN | 服务端知道：客户端发✓、自己收✓ |
| 2 | SYN+ACK | 客户端知道：双向全通 |
| 3 | ACK | 服务端知道：客户端收✓、自己发✓（**缺这次服务端只知一半**） |

**机制演示**（两次握手的历史 SYN 场景）：旧连接的滞后 SYN 迟到抵达→两次握手版服务端直接建连、占资源等数据→永远等不到（客户端早已不要）——三次版客户端可拒（回 RST）。这是"为什么不能两次"的经典反例。

**分层答案**：
- **L1**：SYN→SYN+ACK→ACK；三次=确认双方收发+同步 ISN。
- **L2**：①为什么不是两次（历史 SYN+服务端单向确认不全）；②ISN 随机=防新旧连接序号错乱+防猜测注入；③SYN_SENT/SYN_RCVD/ESTABLISHED 三状态位置。
- **L3**：睿联变式"单向通信能否两次握手"——仍不行，服务端仍无法确认自己发的对方收得到；握手卡死 SYN_SENT 排查=网络不通/对端 backlog 满（SYN 洪泛即打这里，syncookies 缓解）。
- **L4**：半连接/全连接队列（accept 从全连接队列取）；SYN 洪泛与 syncookies。

**真题问法**："三次握手过程"（Z-015 大华 B2-06、D-036 MTK B2-39）"为什么是三次不是两次"（Z-031 睿联变体）"单向通信能否两次握手"（Z-031 睿联 B2-51 原题）。

**坑点措辞险**："第三次 ACK 没用"——恰是服务端确认自己发送能力的唯一来源；"SYN 里不能带数据"——TCP Fast Open 可以（一句带过防深挖）。

**边界句**："半连接队列参数调优我了解到 syncookies 机制这层，内核 backlog 实现没读过。"

**联动**：#2（挥手与握手镜像对照）／#8（SYN/ACK 标志位）。

**状态**：**过**（10-22 17点深化场：两次反例+ISN 两因+状态名收口；SYN/ISN 白话补地基，单向两次真题自产闭环；锚句见 02 册）。

## 卡 2 · #2 四次挥手 + #3 TIME_WAIT + #4 CLOSE_WAIT（高频·红点双卡合并教）

**主轴句**：四次=TCP 半关闭（两边独立关）；TIME_WAIT=主动方等 2MSL 保旧报文死透；CLOSE_WAIT 多=本端收到 FIN 却没调 close（代码泄漏）。

**结构图**：
```
主动方                                被动方
  │ ── FIN ─────────────→ │   被动方: ESTABLISHED→CLOSE_WAIT (等应用调 close)
  │ ←─ ACK ────────────── │
  │      (被动方应用继续发剩余数据=半关闭的意义)
  │ ←─ FIN ────────────── │   被动方调 close 后发出
  │ ── ACK ─────────────→ │   被动方→LAST_ACK→CLOSED
主动方: FIN_WAIT_1→FIN_WAIT_2→TIME_WAIT ──2MSL──→ CLOSED
```

**维度表**：

| 状态 | 谁身上 | 含义 | 大量出现= |
|---|---|---|---|
| TIME_WAIT | 主动关闭方 | 等 2MSL（报文最大生存×2） | 高频短连接（正常但占端口） |
| CLOSE_WAIT | 被动关闭方 | 收了 FIN 等 close() | **代码 bug**（忘了关） |

**机制演示**（两个"为什么"推演）：
- 2MSL 第一因：最后的 ACK 丢了，对端重发 FIN，我还能应——立刻关就应不了，对端卡 LAST_ACK；
- 2MSL 第二因：本连接旧报文在网络里最多活 MSL，等 2MSL 让新旧四元组连接不撞上旧包。
- CLOSE_WAIT 排查链：netstat 数连接→定位哪个进程→代码里找"收到对端关闭后没有 close 的路径"（web 慢客户端：连接断了线程没 close）。

**分层答案**：
- **L1**：四步挥手；TIME_WAIT 在主动方等 2MSL；CLOSE_WAIT 在被动方=没调 close。
- **L2**：①为什么四次——TCP 半关闭：被动方 ACK 了 FIN 但可能还有数据要发，自己的 FIN 要等应用调 close，两个方向独立（对比握手：SYN+ACK 可合并所以三次）；②2MSL 两因（重收 FIN+旧报文死透）；③CLOSE_WAIT 多=泄漏不是网络问题——排查找代码。
- **L3**：web 慢客户端场景=连接被对端断/超时，client 线程没 close→fd 泄漏+CLOSE_WAIT 堆积；TIME_WAIT 多=client 高频短连接，端口耗尽风险，方案=连接池/SO_REUSEADDR（服务端重绑）。
- **L4**：MSL 值（Linux 60s 实现值，2MSL=120s）；tcp_tw_reuse 的 timestamps 条件。

**真题问法**："为什么需要 TIME_WAIT"（Z-014 大华 B2-05 原题）"为什么四次"（小米 LX-33 原题）"四次挥手 FIN 后主动方还能收吗"（06 表 #2 抽检变式）。

**变式池**（红点卡必配，10-19 补）：①若 TIME_WAIT 只等 1 个 MSL 而不是 2 个，两个"为什么"各会怎么坏？（对端重 FIN 已应不了 / 旧报文没死透就开新连接）②服务端出现上千条 CLOSE_WAIT，而 netstat 显示对端是同一 IP 高频短连——先查代码还是先查网络？为什么？（CLOSE_WAIT 堆积在本端=本端没收尾，先查代码 close 路径）③反向题：哪一端会进入 FIN_WAIT_2？如果对端一直不调 close，主动方会不会永远停在 FIN_WAIT_2？（会——除非设 fin_timeout 超时，这是四次挥手的另一类"泄漏"）。

**坑点措辞险**："TIME_WAIT 是错误状态要消除"——它是设计保护；"CLOSE_WAIT 等等就好"——代码 bug 不会自愈。

**边界句**："内核 TIME_WAIT 回收定时器实现我没读过，行为层面到 2MSL 这层。"

**联动**：#1（握手对照：为什么握手能合并挥手不能——半关闭）／#8（FIN/ACK 标志）／B 层 web 连接生命周期。

**状态**：**#3#4 双过（10-21 红点教学场：#3 全景图教学+申诉改判第 3 例+范文核验入库；#4 三问自产+排查链落地）**；#2 **过**（10-23 17点深化场：半关闭机制句+衔接句+安全措辞收口）；网络墙红点清零，A3 无红点。

## 卡 3 · #5 粘包与定帧（中高频·条件过欠复述·小米原题）

**主轴句**：TCP 是字节流没有消息边界——"粘包"是应用层概念，边界要应用层自己定（定帧四法）。

**结构图**：
```
发送: write("AB") write("CD") ──字节流──> 接收可能读到 "ABCD"/"ABC"/"CD"...
定帧四法: ①定长 ②分隔符(\r\n) ③长度前缀(Content-Length) ④帧头+长度+校验
UDP: 数据报有边界, sendto 一次= recvfrom 一次 → 天生不粘
```

**维度表**：

| 定帧法 | 适用 | 项目实例 |
|---|---|---|
| 定长 | 固定记录 | 结构化遥测 |
| 分隔符 | 文本协议 | HTTP 头 \r\n\r\n |
| 长度前缀 | 二进制协议 | HTTP body Content-Length；RTSP interleaved $+ch+len(2B) |
| 帧头+校验 | 串口/不可靠 | 丢字节后重找帧头 |

**机制演示**（半包攒缓冲）：读到 100B 但一帧需 150B——不交解析，留缓冲区继续 recv，凑满 150 才处理；串口变式：帧头受损→滑动窗口逐字节重找帧头对齐。

**分层答案**：
- **L1**：TCP 字节流无边界；定帧四法；UDP 数据报有边界不粘。
- **L2**：①根因=流式语义+缓冲合并（Nagle/接收缓冲都只是放大器，根因是"流"本身）；②四法+选型（能定长度用长度前缀，文本用分隔符）；③UDP 为什么不粘（数据报保留边界）——你的欠句。
- **L3**：项目双场景（web POST：头分隔符+body 长度前缀组合拳；RTSP interleaved：$+channel+16 位长度）；串口变式帧头对齐。
- **L4**：Nagle 与延迟确认对"粘"的放大；readv/writev 一句。

**真题问法**："TCP 分包粘包"（Z-078 TPL ST-13 终面）"粘包拆包怎么理解"（D-022 华为 B2-30）"粘包"（小米 LX-33 原题）。

**坑点措辞险**："TCP 协议有 bug 会粘包"——协议没错，是流语义；"设 TCP_NODELAY 就不粘了"——只是减少小包合并，边界问题仍在。


**边界句**（10-19 补）：内核 tcp_read_sock 与用户缓冲的交互细节我没读过，到『TCP 是字节流、定帧是应用层责任』+四法选型层作答，协议实现层到边界。
**联动**：#23（长度信息传递）／B 层 web/rtsp 定帧实然。

**状态**：条件过（10-14：考2 过/考1 缺 UDP 半句/考3 已给标准句未答——均待复述，02 册在案）。

## 卡 4 · #6 TCP vs UDP 选型（高频·场10 过线保温）

**主轴句**：TCP 用延迟和状态换可靠有序字节流；UDP 不保证交付但延迟恒定——选型=数据要完整还是要新鲜。

**结构图**：
```
TCP: 序号+确认+超时重传+滑动窗口 → 可靠有序, 代价: 丢一段→后面全部排队等重传(队头阻塞)
UDP: 尽力而为, 前面丢了后面照走 → 实时流天然匹配: 旧帧迟到无用
```

**维度表**：

| 维度 | TCP | UDP |
|---|---|---|
| 可靠 | 重传保证 | 无 |
| 有序 | 序号保证 | 无 |
| 连接 | 有（状态机） | 无（每次 sendto 独立） |
| 实时 | 队头阻塞劣化 | 延迟恒定 |

**机制演示**（队头阻塞=TCP 可靠的代价）：视频段 3 丢了→段 4-10 已到**但不能交**（要保序）→等段 3 重传→整段画面卡住。UDP：段 3 丢就丢，4-10 照播（旧帧迟到无用）。金句：**数据价值随时间衰减**。

**分层答案**：
- **L1**：可靠有序字节流 vs 尽力数据报。
- **L2**：①TCP 可靠四件套（序号/确认/重传/滑窗）；②队头阻塞=保序的代价（演示）；③UDP 场景=实时音视频/DNS/广播。
- **L3**：rtsp_server 双承载=两者都要：TCP interleaved（穿防火墙+保完整，配置/控制流）与 UDP（低延迟，实时播放）；NVR 转发默认 TCP 因为监控回放要完整。
- **L4**：QUIC 在 UDP 上重建可靠+解决队头阻塞（多流）——一句展示视野。

**真题问法**："TCP 和 UDP 区别"（Z-098 商泰 B2-48、D-019 小米 B2-14）"TCP 网络可靠的原因"（D-010 字节 B2-35）"什么时候用 UDP"（变式）。

**坑点措辞险**："UDP 快"——安全版"延迟恒定+无连接开销"，快是结果不是机制。


**边界句**（10-19 补）：QUIC/UDP 在用户态实现可靠传输的具体机制（0-RTT/连接迁移）我了解概念层，没读过协议细节——TCP/UDP 经典对比是我的主线边界。
**联动**：#1#2（TCP 状态机家族）／B 层 rtsp 双承载。

**状态**：**过**（10-24 17点深化场补句闭环：双承载选型故事+防火墙回程句+只用 TCP 直播卡顿句自产收口；R14b 随场销账；「等 ACK 确认到达」申诉改判第 4 例；锚句见 02 册）。

## 卡 5 · #7 MTU 与 MSS（中低频·降权·场2 绿保温）

**主轴句**：MTU=链路层单帧上限（以太网 1500）；MSS=TCP 单段数据上限（1460=1500−20IP−20TCP）。

**结构图**：
```
IP 包 > MTU → 分片(路由器) → 任一片丢=整包重传(放大!)
TCP: 握手协商 MSS → 段级控制, 不靠 IP 分片
UDP: 无 MSS 概念 → 一次 sendto 3000B = IP 分片 → 丢一片全丢
H.264 NALU > MTU → 应用层分片 = FU-A (RTP 层自己做, 与 IP 分片不同层)
```

**维度表**：

| 概念 | 层 | 值 | 谁负责 |
|---|---|---|---|
| MTU | 链路 | 1500 | 网卡/链路 |
| MSS | TCP | 1460 | TCP 自己（避免 IP 分片） |
| IP 分片 | 网络层 | — | 路由器（丢一片全丢） |
| FU-A | 应用/RTP | — | 发送端（NALU 切片） |

**机制演示**（UDP 3000B 放大）：一次 sendto 3000B→IP 切 2 片→片 1 丢→整包重传 3000B（实际约 2 片全重）——放大效应；TCP 自己按 MSS 1460 切段，丢哪段重哪段。

**分层答案**：
- **L1**：MTU 1500/MSS 1460=减两个头。
- **L2**：①MSS 存在的意义=把分片决策从 IP 层收到 TCP 层（可选择性重传）；②UDP 无 MSS→IP 分片丢一片全丢；③抓包看到的 1460 数据段即 MSS 生效。
- **L3**：FU-A 挂靠——rtsp_server 打包 H.264 时 NALU 超过 MTU 才 FU-A 分片（FU 头 S/E 位标首尾），与应用层缓冲无关。
- **L4**：PMTUD 黑洞一句。

**真题问法**：（变式主流）"UDP 一次 sendto 3000 字节会发生什么"（06 表抽检变式）。

**坑点措辞险**："MSS=MTU"——要减 40 字节头；"分片=TCP 的"——TCP 是分段不分片（IP 才分片）。


**边界句**（10-19 补）：分片重组的内核实现（ip_defrag 队列）与 DF 位的路径 MTU 发现过程我没读过源码，到『MTU 掐第二层、MSS 掐 TCP 层』这层是边界。
**联动**：#6（UDP 的坑）／B 层 FU-A。

**状态**：**过**（10-25 17点深化场补句：MSS 意义句+sendto3000 抽检题随场销+FU-A 层别句三问全过；「只有第一片带端口号」超规格自产；锚句见 02 册）。

## 卡 6 · #8 TCP 头字段（中低频·红点·J8 确认号语义答反）

**主轴句**：四件套字段——序号（本段第一个字节的位置）、确认号（**期望对方发来的下一个字节号**，+1 语义）、窗口（流控通告）、六个标志位。

**结构图**（20 字节定长头）：
```
[0:16 源端口][16:32 目的端口]
[32:64 序号 seq]            ← 本段数据第一个字节的编号
[64:96 确认号 ack]          ← 我已收齐你发来的前 ack-1 字节, 请发第 ack 字节起
[96:112 头长+标志][112:128 窗口 win] ← 我还能收 win 字节(流控)
[校验和+紧急指针]
```

**维度表**：

| 字段 | 语义 | 易错 |
|---|---|---|
| seq | 本段首字节号 | 不是"第几个包" |
| ack | 期望的**下一个**字节号 | **收到 x 号→ack=x+1（J8 旧伤）** |
| win | 接收缓冲剩余 | 0=通知对方停 |
| 标志 | SYN/ACK/FIN/RST/PSH/URG | SYN/FIN 占一个序号（所以握手 ack=x+1） |

**机制演示**（+1 语义推演）：收到 seq=100 len=200 的段（数据 100-199）→我回 ack=200=**下一期望字节**——确认号永远指向"还没来的第一个"。SYN/FIN 虽无数据但占一个序号，故握手 SYN seq=x 回 ack=x+1。

**分层答案**：
- **L1**：四件套名+各自一句。
- **L2**：①**确认号=下一个期望字节序号**（+1 语义，红点修复句）；②窗口=流控通告（端到端），与拥塞控制（对网络）分层；③SYN/FIN 占序号所以握手挥手 ack 都是 x+1。
- **L3**：流控 vs 拥塞控制一句话分清：win=接收方告诉发送方"我还能收"；cwnd=发送方对网络的自律——两者取 min 决定发送速率。
- **L4**：选项字段（MSS/窗口缩放/SACK）一句。

**真题问法**："TCP 报文段的数据格式、包含哪些主要字段"（Z-013 大华 B2-08 原题）"序号确认号作用"（追问式）。

**变式池**（红点卡必配，10-19 补）：①收到 seq=500、len=300 的段，确认号该回多少？如果这个段还带着 SYN 标志呢？（800；带 SYN 则 801——SYN 占一个序号，J8 旧伤直测）②收方通告窗口 win=0 后发送方立即停发，那连接怎么恢复？（收方缓冲排空后发窗口更新；Persist 定时器防更新丢——探活机制一层）③反向题：ack=x+1 出现在哪三种场合？（握手应 SYN、挥手应 FIN、确认数据段末字节+1——同一条 +1 语义三个现场）。

**坑点措辞险**："确认号=已收到的最后一个字节号"——错，是下一个期望（你的 J8 旧伤原话就是答反成这）；安全版"确认号永远指向还没来的第一个字节"。


**边界句**（10-19 补）：选项字段的协商过程（SACK 块格式/窗口缩放因子计算）我知道存在与用途，字节级格式没背过——四件套+交互语义是主线边界。
**联动**：#1#2（+1 语义贯穿握手挥手）／#6（win=cwnd 取 min）。

## 卡 7 · #9 select/poll/epoll 与 LT/ET（高频·海康原题·条件过欠对比句）

**主轴句**：三个都解决"一个线程等多个 fd"，差别在每次调用"把 fd 集合搬运+扫描"的成本——epoll 用红黑树+就绪链表把它降到 O(就绪数)。

**结构图**：
```
select: 每次调用 全量 fd_set 拷入内核 → 内核线性扫描 → 返回后用户再线性扫描 (FD_SETSIZE 1024)
poll:   同 select,fd 数组无硬上限,仍 O(n) 每次拷+扫
epoll:  epoll_create(红黑树注册一次) → epoll_ctl(增删) → epoll_wait(只取就绪链表) O(就绪数)
LT 水平触发: 缓冲区还有数据就一直报 —— 闹钟响到你起床
ET 边缘触发: 无→有的"边沿"只报一次 —— 必须一次读到 EAGAIN, 配非阻塞 fd
```

**维度表**：

| 维度 | select | poll | epoll |
|---|---|---|---|
| fd 上限 | 1024 | 无硬限 | 无硬限 |
| 每次 fd 拷贝 | 全量 | 全量 | 注册一次 |
| 就绪找法 | O(全部) | O(全部) | O(就绪) |
| 触发模式 | LT | LT | LT/ET |

**机制演示**（中断/门铃连环教学遗产）：select/poll=每毫秒挨个问"有信吗"（轮询拷贝）；epoll=内核回调把就绪 fd 挂进就绪链表，wait 只取链表——**登记一次，事件驱动**。ET 为什么必须循环读到 EAGAIN：只报一次，剩下没读的数据不会再提醒——不读完=饿死。

**分层答案**：
- **L1**：三接口名+一句话差（上限/拷贝/扫描）。
- **L2**：①数据结构差（fd_set 位图 vs 数组 vs 红黑树+就绪链表）；②LT/ET 行为差（闹钟 vs 单次提醒）；③ET 必须配非阻塞+读到 EAGAIN。
- **L3**：项目桥：web 为什么一连接一线程不用 epoll——网关连接个位数（MAX_CLIENTS=8），阻塞读最简单可靠；上万连接每线程 8MB 栈才必须 epoll——**这是"按规模选模型"的选型故事**。
- **L4**：红黑树键=fd；epoll 回调挂在 socket 就绪队列（等待队列）上；惊群 EPOLLEXCLUSIVE 一句。

**真题问法**："select/poll/epoll 区别、LT/ET 适用场景"（Z-001 海康 AV-01 原题）"epoll 介绍一下"（D-039 网易 B1-20）"网络模型"（Z-024 星宸 B1-10）。

**坑点措辞险**："epoll 一定比 select 快"——少量连接+高频就绪时优势不明显甚至开销更大（红黑树登记成本）；安全版"epoll 赢在连接多+就绪少的长轮询场景"。

**边界句**："epoll 内核实现我知道到红黑树+就绪链表+回调挂接这层，源码没读过。"

**联动**：#10（ET 配非阻塞）／B 层 web 模型选型。

**状态**：条件过（10-14 场⑤：链路大结构+ET 句自产；LT/ET 对比句+项目桥待复述，02 册在案）。

## 卡 8 · #10 非阻塞与 EAGAIN（中频·条件过欠行为句）

**主轴句**：EAGAIN 不是错误，是"现在没有，待会再来"的状态——非阻塞 IO 拿到它应该去干别的。

**结构图**：
```
阻塞 read: 无数据 → 线程挂起(让出 CPU) → 有数据被唤醒 → 返回数据
非阻塞 read: 无数据 → 立即返回 -1, errno=EAGAIN → 程序自己决定: 轮询?去干别的?
send 同理: 对端窗口满 → EAGAIN (不是对端挂了)
```

**维度表**：

| 场景 | 阻塞行为 | 非阻塞行为 |
|---|---|---|
| read 无数据 | 睡 | -1+EAGAIN |
| send 缓冲满 | 睡 | -1+EAGAIN |
| 适合 | 一连接一线程 | 单线程多路/ET 模式 |

**机制演示**（rtsp_server 实然）：发送侧 send 返回 EAGAIN=对端接收窗口满（慢客户端）→不算失败、丢这帧不计 fail_count；真错误（连接断）→fail_count++>3 踢掉客户端——**EAGAIN 与真错误的分流就是这卡的项目实然**。

**分层答案**：
- **L1**：EAGAIN=资源暂不可用非错误；非阻塞立即返回不挂起。
- **L2**：①行为对比（睡 vs 立即返）；②单线程不可用阻塞（会卡死其他连接）；③ET 模式必须非阻塞+循环读到 EAGAIN（配合卡 7）。
- **L3**：rtsp_server 分流实然（演示段）；web accept 非阻塞避免慢连接卡 accept 循环。
- **L4**：EWOULDBLOCK=EAGAIN（历史两名一值）。

**真题问法**："阻塞与非阻塞 socket 的区别"（Z-014 大华 B2-05）"非阻塞 read 返回什么"（追问式）。

**坑点措辞险**："EAGAIN 是错误要重试到成功"——先做别的，不是原地自旋；"非阻塞更快"——是"不卡住别人"，吞吐未必高。


**边界句**（10-19 补）：EAGAIN/EINTR 在不同 fd 类型（socket vs pipe）上的行为差异我按主线讲，具体驱动层返回值策略没验证——『非阻塞+重试』行为层是边界。
**联动**：#9（ET 黄金搭档）／B 层 rtsp fail_count。

**状态**：条件过（10-14 场⑤：方向全对；行为句+分支句待复述，02 册在案）。
