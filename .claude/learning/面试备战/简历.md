# EdgeFusion 智能 NVR 边侧网关 · 简历项目条目

> v6 定稿(待用户审阅) · 2026-09-20 · 简历完善专场(Phase 0–3 全收口后基于 v5 迭代;新增=审计战绩独立成条、Phase 2/3 证据回填、背景段扩写)

## 项目背景

一套端边云三层智能监控系统。端侧 V821(全志 RISC-V,带 H.264 硬编码引擎)只负责摄像头采集与 RTSP 推流;云端为多模态大模型识别 API;系统主体在边侧——运行于 IMX6ULL(800MHz Cortex-A7 单核、无视频硬解 VPU)的 C 多线程守护进程(11 个模块、7 类线程),负责拉流接入、7×24 循环录像、实时预览、MP4 回放、关键帧上云识别、事件告警入库、RTSP 二次分发与 Web 管理配置。核心工程约束是「无硬解」:主通路全程压缩域,只有抽帧旁路按需软解。

技术栈:C + pthread 多线程;FFmpeg(libavformat 拉流/remux、libavcodec 软解、libswscale 缩放转格式);SQLite 事件存储;libcurl HTTPS 上云;HTTP(含 MJPEG/Range)与 RTSP/RTP 均为手写应用层实现,无框架。

## 核心贡献

完成该网关在 i.MX6ULL 与嵌入式 Linux 上的部署联调与全部 11 个模块的源码级精读,打通拉流、录像、预览、回放、上云识别与二次分发全链路;针对无硬解约束,分析并验证「主通路压缩域、预览与上云按需软解」的分工,使录像转发与预览识别解耦,弱算力下主链路可运行、异常可隔离;逐模块审计累计定位 26 处缺陷与工程隐患,并据此补齐配置样例契约与配置接口输入校验。

## 技术亮点

①**压缩域单源三分发**:单拉流线程一次 `av_read_frame` 后将 H.264 包同步扇出到录像、抽帧、转发三条通路,单写者多读者,避免多会话重复拉流与全解码再编码的 CPU、带宽浪费;读错误分级计数防抖,瞬时坏包不触发重连、持续性故障自动重连,主链自愈。

②**旁路抽帧与跨线程所有权**:抽帧线程逐包软解维护 I/P/B 参考链(解码不能跳帧,缩放与编码才可节流)、按目标帧率出 JPEG,只缓存最新一帧不建队列——下游消费的是「当前画面」,丢帧即天然背压,内存占用恒定;读取接口以 malloc 深拷贝交割所有权,写侧 realloc 扩容不会产生悬垂读者;事件总线以「锁内冻结事件快照、锁外执行订阅回调」隔离订阅者耗时,慢订阅者不拖发布者。

③**无硬解下的录像设计**:H.264 不解码直接 remux 成关键帧对齐的分段碎片化 MP4(`movflags=+frag_keyframe+empty_moov+default_base_moof`),索引随数据逐 fragment 落盘,掉电后已写入片段仍可播放,避开普通 MP4 索引压在文件尾、中断即整文件报废的问题;切段时完成时间基换算保证回放速率正确;磁盘水位反馈式循环回收最旧段。CPU 近零开销的代价是放弃转码能力——无 VPU 平台的主动取舍。

④**手写 HTTP 服务(无框架)**:每连接一线程的并发模型,慢客户端只占满自身线程栈与内核发送缓冲,不拖累主链路;MJPEG 预览「对内按节拍轮询最新帧缓存、对浏览器单次 GET 后持续推流」两腿设计,协议承诺不受生产帧率波动影响;MP4 回放支持 HTTP Range 分段与拖动 seek,定位由 lseek 修改内核文件偏移完成,O(1) 不需重读前置数据。

⑤**云 AI 链路与失败降级**:独立旁路线程经 HTTPS 调用多模态视觉接口,结构化事件入 SQLite 并联动 GPIO 告警;云端超时或失败只降级为该帧识别丢弃,拉流、录像、本地预览保持可运行;识别启停与抽帧率支持运行时热更新,并按「字段被推送≠字段被消费」逐字段厘清生效边界(现读立即生效/出生快照须线程重启/绑定类资源须进程重启)。

⑥**源码级审计与缺陷定位**:以「规范应然—源码实然—工程结论」三层证据法逐模块审计,累计登记 26 处缺陷与工程隐患,均有源码定位与完整事故链推演。代表案:写帧后读已被掏空的 packet 致码率统计恒 0(FFmpeg 所有权契约);配置保存未查 fflush/fsync 返回值,盘满时残缺临时文件被 rename 转正且接口谎报成功;端口值经 htons 截断后服务静默起在错误端口且日志谎报原值;事件发布在锁内完成全部磁盘 I/O,存储变慢时延迟经锁传染给查询接口。

## 1 分钟口述版(2026-09-20 v6 修订)

【定位】我的项目是跑在 IMX6ULL 上的边侧智能 NVR 网关,在端边云架构里守边缘这一层:端侧摄像头硬件编码后 RTSP 推流,我在板上完成 7×24 录像、抽帧识别和报警,只把结构化事件推上云。

【架构】板子 800MHz 单核、没有 H.264 硬解,所以主路走压缩域——录像纯 remux、转发透传,全程不解码;只有 JPEG 抽帧旁路按需软解加节流,把像素域开销压到最小。

【亮点一】录像用 fragmented MP4:按关键帧切 fragment、索引随数据落盘,掉电后已写完的片段依然可播,避开传统 MP4 索引压在文件尾、断电整文件报废的问题。

【亮点二】抽帧通路只存最新一帧、不建队列——下游要的是当前画面不是历史,丢帧本身就是背压;取帧做拷贝并移交所有权,读者线程不会被写侧的 realloc 伤到。

【战绩】我把 11 个模块逐个做了源码审计,登记了 26 处缺陷,最典型的是配置保存不查 fflush/fsync 返回值——盘满时残缺的临时文件被 rename 转正、接口还报成功,整条事故链我推到底,后来据此补了配置接口的输入校验。

【稳定性】云端识别是独立旁路线程,超时失败不传染主链,云端挂了录像预览照跑。

【角色】我负责板端部署联调和全模块源码精读,「我审出来的东西」和「每个选型为什么」我都能展开讲,您感兴趣我可以挑一条链路讲。
