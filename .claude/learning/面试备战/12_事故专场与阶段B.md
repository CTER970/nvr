**触发词**:「最大问题」「讲个最典型的」「配置保存可靠吗」「rename/原子写」。

**口述脚本(分段计时,共约 90 秒;每段一句最严说法,与 02 代表案 2 同口径)**:

| 步 | 秒 | 口述 |
|---|---|---|
| 现象 | 15s | 「TF 卡写满时在 Web 保存配置,页面返回 200『成功』;重启后配置文件半行损坏——rtsp_url 被拦腰截断,fgets 照样把半行当合法值加载,系统带着静默错配置跑起来。」 |
| 发现 | 20s | 「我在推演『盘满时这个接口到底能不能返回 500』——从 fopen 起沿失败路径穷举每一步的返回值检查:fflush/fsync/fclose 三步(conf.c:282-284)返回值全都没查,部分写失败被整体吞掉,rename(conf.c:286)照常执行。方法=失败路径穷举+返回值语义核对:每一步问『这步失败了,下面还走不走』。」 |

| 修法 | 10s | 「三步查返回值,任一失败→unlink(tmp)+return -1——照抄 conf.c:288 rename 失败分支的既有清理模式。」 |

## 卡2 · #6 盘满熔断稀释【完整六步·先读两处代码|A 档|滤网:返回值语义=核心数据√ 熔断路径=主链因果√】

**⚠️ 开场前 5 分钟先读**(逐行读,读时自问「哪一行是『健康等待』,哪一行是『写成功』」):

- recorder.c:216——waiting_key 路径 `if (!is_key) return 0;`(丢弃直到关键帧)
- stream_receiver.c:157-161——调用点:158 `++err_count > 20` 熔断重连、160 `err_count = 0` 清零

**口述六步(每步一句,共约 90 秒;完整底稿=07①节六步表,此处为口试压缩版)**:

| 步 | 口述 |
|---|---|
| 现象 | 「盘满后每个关键帧到来都重试开段、都失败(recorder.c:89-91),录像停在『失败-等关键帧-再失败』里打转——拉流循环不断、预览转发还活着;设计里『写错误超 20 次熔断重连』(stream_receiver.c:158)永远等不来。」 |
| 发现 | 「我旧答案是连续写失败 20 次会熔断重连;审计『盘满后系统走到哪』,逐个数 err_count 的每个清零点——非关键帧在等关键帧路径 return 0(recorder.c:216),调用点把它当『写成功』清零(stream_receiver.c:160)。旧答案被控制流核对推翻。」 |
| 根因 | 「返回值身兼两义:0 既表示『这包写进去了』,也表示『我在等关键帧、丢了但流健康』;盘满时绝大多数包走第二义,却做了只有第一义才有资格做的清零。」 |
| 机制 | 「灾难场景下,清零的合法路径把熔断计数冲掉——++err_count>20 永远凑不齐,系统停摆重试而不是重连。第二个含义把第一个的账本冲掉了。」 |
| 修法 | 「区分语义:等关键帧路径返回『不计入也不清零』的值(或三值协议:写了/丢弃但健康/失败),调用点只在『写了』清零、只在『失败』累计。」 |
| 归属 | 「三层审计修正了我的旧答——如实讲:审计发现,我按修正后的机制当场复述确认,属『共同』层。」 |

**冷面可探**(修法落地细节,未实读,答不上按交位):三值协议改返回值会动哪几个调用点/枚举怎么定义/会不会破坏其他调用方的 `!=0` 判断。

**下一问存款**:

| 收口句 | 下一问 | 档 |
|---|---|---|
| 「绝大多数包走第二义」 | 「正常运行为什么不会触发?」 | 能推(等关键帧 return 0 只在首段启动/开段失败重试出现,窗口短;盘满才让第二义成为常态) |
| 「丢的包」 | 「这些丢包和切段等待期丢包怎么区分?」 | 能指路(①行陷阱层:等待期设计内丢只在首段/开段失败;正常业务切段不丢) |
| 「熔断重连」 | 「重连能解决盘满吗?」 | 能推(不能——重连解决流级故障;盘满靠水位删除,删除挂在成功切段的路径上,属不同层的自愈) |
| 「返回值身兼两义」 | 「为什么当初设计成 return 0 不报错?」 | 能推(等关键帧是设计内常态,报错会引发误熔断——语义过载正源于此) |

### 卡B1 · 码率估算数字题【B 档|滤网:存储规划=通用 NVR 题√ 主链因果(循环覆盖容量)√】

**为什么有这张卡**:NVR 岗必考存储规划数字题;板端实测缺(A5 数字闸门),但闸门禁的是「编实测」、不禁「讲推算」——**估算方法不依赖板端**。讲法纪律:每个数字前先声明「按假设推算,不是板端实测」。

**题干(60–90s 白板)**:「按你的配置:1080P H.264 源、60 秒一段。假设平均码率 4 Mbps——一段大约多大?一天录多少?一张 32GB TF 卡循环覆盖,大约多久全部滚一遍?」

**解法链(换算步步出声,单位用 10 进制)**:

| 步 | 算式 | 结果 |
|---|---|---|
| 码率→字节率 | 4 Mbps ÷ 8 | 0.5 MB/s |
| 一段 | 0.5 MB/s × 60s | ≈30 MB |
| 一天 | 0.5 MB/s × 86400s | ≈43.2 GB |
| 32GB 滚一遍 | 32GB ÷ 0.5 MB/s = 64000s | ≈18 小时 |

**结论句**:「1080P 按 4Mbps 估,32GB 卡不到一天就全程循环覆盖一遍——循环覆盖对 NVR 不是保险,是必需。要拉长保留:降码率/降分辨率/换大卡,这就是存储规划的基本权衡。」(自然接①行:水位删最旧+保留当前段=这套循环的落地。)

**分层加深(被追问)**:①GOP/I 帧占比影响平均码率:长 GOP 省 I 帧开销;监控场景运动量波动→VBR 下段大小不均,「60 秒一段」是时长近似不是大小恒定/②码率从哪读:盒子统计 bitrate_kbps——接 #1:统计坏了(恒 0)存储规划就瞎/③稳态磁盘占用≈水位上限(删除量=写入量)。

**边界交底**:4 Mbps 是估算假设不是实测;板端回来用实测码率重算——「方法不变,数字回填」。

**下一问存款**:「码率怎么选?」→能推(分辨率×帧率×场景运动量,1080P 监控常用 2–8Mbps 量级,常识层)。「换 H.265 呢?」→能指路(同画质约省一半码率,代价=端侧硬编支持与生态兼容——本项目 H.264)。「fMP4 容器开销?」→能推(每 fragment moof 头百字节量级,相对 10s fragment 的 MB 级数据占比可忽略)。

### 卡B2 · 音视频同步交底句【B 档|滤网:PTS/DTS/master clock=音视频岗通用√ 本项目实然单轨=为什么只需交底√】

**为什么有这张卡**:音视频岗高频常识题;本项目实然是**单视频轨**(stream_receiver.c:152 只消费 vidx 视频流),没做过真正的音视频同步——照实交底反而是加分(知道边界在哪),吹「做过同步」会被 PTS/DTS 三问打穿。

**交底句(定稿,约 30 秒)**:「这个项目的码流只有视频轨,没有真正的音视频同步问题——我做过的是视频单轨的时间戳。同步问题的完整形态我知道框架:音视频各自带时间戳,播放端按 PTS 对齐两轨、以一路为 master clock;采集端负责打时间戳,传输和封装透传不引入漂移——边侧 remux 恰好不碰这块。加音频轨,才会进入这个问题域。」

**两层追问预置**:

| 追问 | 档 | 答 |
|---|---|---|
| 「DTS 和 PTS 什么区别?」 | 能推 | PTS=显示时间戳,DTS=解码时间戳;无 B 帧时两者相等,B 帧引入解码序≠显示序的重排——对应本项目解码侧 receive 循环的 0 帧/N 帧现象(B 帧重排等待,八股 04 册有卡) |
| 「口型不同步多少能察觉?」 | 交位+量级 | 人耳对音频超前/滞后敏感度不对称,可察觉窗口量级在几十毫秒、可接受窗口到一百多毫秒(ITU 常引结论);精确数值我记不准——被追问就交位,不编数 |
| (深挖)「remux 双轨会引入同步问题吗?」 | 能推 | 按各轨 DTS 交错写包,双轨时基各自换算(时基⑬ 的通用层);交错器保序不造漂移,前提是每轨时基换算对——⑬ 恰是本项目登记过的脆弱假设 |

**边界交底**:不升格「做过音视频同步」;本项目的相关实绩=视频时基/时间戳(⑬ 的实然与修法)。
