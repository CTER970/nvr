# 04 · 审计① 锁内盘 IO——排队机模型与传染链

> 来源:2026-09-24 行⑤拍③「主动边界」交付,学生原文全收录。tutor 逐行核对通过(记录见文末),护边×2。
> 复述顺序(学生自提,已采纳):**先讲排队、再讲传染**——排队机模型立住,「锁是延迟的唯一传染媒介」才有机理支撑。

---

## 一、缺陷实然

发布事件时抱着锁干完四件事才放手(event_bus.c:117-174):① INSERT 事件行、② 触发帧写成 `evt_<id>.jpg`、③ 路径 UPDATE 回填、④ 清理旧照。后三件全是 SD 卡 IO,且第四件最重——`cleanup_snapshots` 是 statvfs + 目录扫描 + alphasort + unlink 循环,不是"顺手"一个删除。

## 二、传染机制(排队机模型)

- **为什么有人陪等**:云线程和 web 线程素不相识,但都要用**同一个 SQLite 连接 `g_db`**——一个 INSERT 一个 SELECT。一个连接不能两线程并发用(内部有状态:语句对象、游标、错误码),必须串行化,`g_lock` 就是这个资源的排队机。查列表的 `event_bus_query_filtered`(event_bus.c:228)、计数的 `event_bus_count`(event_bus.c:207)全在名单上。
- **等待的本质**:web 不是"在等云线程",是**排队等数据库**,恰好队首是云线程。**等待窗口 = 持锁窗口**——云线程卡在 HTTPS 十几秒时 web 一毫秒不等(没持锁),只在落库+写照片那几百毫秒陪等。
- **因果链三跳**:SD 卡慢 → 持锁时间长 → 同锁排队者等待时间长。不是"盘慢直接拖网页"。

```
云线程:  lock ── INSERT ── 写jpg ── UPDATE ── 扫目录删旧 ── unlock
web线程:        lock(排队……) ─────────────────────────┤ 拿到锁→SELECT→回复
```

## 三、边界(反证)

录像走 recorder 自己的锁、自己的文件(recorder.c:32 一带),不在 g_lock 的排队名单里——盘慢照样慢,但**没有共享锁就没有传染路径**。

## 四、修法

锁内只留快活:锁内只做 INSERT 拿到 id、照片所有权到手,解锁后再写文件、回填、清理——这三件不需要锁保护并发,需要的只是 id 和数据到手。代价:引入「行在、路径未回填」窗口,查询侧容忍空路径或加 pending 标记。另一方向:web 查询用独立连接(读写分离),代价是多连接与 SQLite 并发写行为要重新核对。

## 五、口述版(约 300 字)

> 这是我审计出来的延迟传染缺陷。发布事件时代码抱着锁干完四件事:插记录、写照片、回填路径、清理旧照——后三件全是 SD 卡 IO,清理还是一次目录扫描。而这把锁保护的 SQLite 连接是共享的:网页查事件列表、计数走同一把锁。所以传导链是三跳:盘慢 → 云线程持锁久 → 排同一把锁的网页接口等得久——web 查询自己只读库、不碰照片,它被拖累纯粹因为要用的钥匙被拿去干慢活的人攥着。录像则完全没事:它用 recorder 自己的锁,不在排队名单里。病根不是盘慢——嵌入式盘慢是常态躲不掉;病根是把慢活放进了锁里,**锁的持有时长就是别人的等待上限**。修法:锁内只留 INSERT 拿 id,照片所有权到手就解锁,写文件、回填、清理全在锁外做——它们不需要锁,需要的只是 id 和数据到手。一句话:**锁是延迟的唯一传染媒介**。

**弹药**:①"同一把锁跨度里住着审计①+#21 删序错位+#22 无前缀过滤三个登记项"——缺陷扎堆在边界糊弄处;②修法代价=「行在图未回填」窗口,与快照原子性 B1 同族;③等待窗口=持锁窗口的精确表述——云线程 HTTPS 十几秒 web 不等,只在落库几百毫秒陪等。

## 本次暴露的问题(学生自诊)

1. **互斥锁的排队语义没有打通**(本次主要卡点):把"web 等锁"理解成了"web 等云线程"——等的是**共享资源**不是线程,锁是资源的排队机。这个模型不建立,锁的一切推演都是背的。
2. **"等待窗口 = 持锁窗口"这个等式不在工具箱里**:导致分不清云线程哪些时间 web 在陪等(HTTPS 段不等、落库段才等)——它同时是修法为什么有效的根据(挪出一毫秒,别人上限短一毫秒)。
3. **因果链跳步**:"SD 卡慢所以网页卡"直接跳了三跳链的两跳——审计发现的讲法必须把传导链说全,跳步版本在面试里会被"网页又不碰 SD 卡,卡什么?"一句问塌。

## 护边×2(被追问再滑)

1. **「一个连接不能两线程并发用」**——严格说取决于 SQLite 编译线程模式(serialized 模式下连接内部自带互斥)。本项目不依赖编译选项、自己一把锁,还有更深一层原因:**这把锁罩的不止连接**——还罩订阅数组(169-173 在锁内复制订阅列表,这正是锁要跨到 174 才放的原因)和快照目录一致性(cleanup 与 #21/#22 的交互)。面试安全句:「与其押 SQLite 编译期线程模式,不如自己一把锁把连接、订阅表、快照目录一起看住」。
2. **cleanup 是条件触发**——只在「本条事件带快照」分支跑(145 的 if 与 166 同块),纯事件(无 jpeg)不扫目录。被追「每次发布都扫目录?」答「只在本条写快照时」。
