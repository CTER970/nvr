### 用时校准模型（2026-08-17 系统修订，以真实对话节奏为据）

**锚点（用户确认准确的实际用时）：**
- `1.5A–C` 实际 4h，对原快速口径 2h → **L3 源码任务实测倍率 2.0×**
- `1.6A` 实际 5h，对原 3h → **L3 源码任务实测倍率 1.67×**

**对话证据推出的用时构成**：每个陌生库函数平均引发 2–4 轮追问（原型、所有权、配对、失败路径），加上主动阅读、口述、纠偏和间隔复测，实际用时 ≈ 快速扫读口径的 1.7–2 倍；L1–L2 略读任务因问答密度低，约 1.4–1.7 倍。

**本轮修订内容（对照锚点发现的不一致）：**
- `1.7A–C` 由 6h 上调至 **8h**（2/3.5/2.5）：`frame_grabber` 是三个核心模块中新 FFmpeg API 面最大的（解码 send/receive、swscale、JPEG 编码、AVFrame），比它轻的 `recorder` 按锚点节奏分到 13.5h，原 6h 与锚点倍率矛盾。
- `1.9` 由 2.5h 上调至 **3h**：三模块闭卷 + 8 道 why + 变式追问，按已观察的复测深度（M-004 间隔复测模式）2.5h 偏紧。
- `1.6B/1.6C` 维持 5h/3.5h，`1.8` 维持 2h（机械性动手任务，无新概念密度）。
- Phase 1.5 维持 16.5h（1.74×）、Phase 2 维持 5h（1.67×）、Phase 3 维持 7.5h（1.67×）、Phase 5 维持 3h（1.5×）、Phase 6 维持 15h（1.36×，面试输出非源码精读）：倍率均落在对应深度区间的合理位置，无对话证据支持再调。
- 2026-08-22：应用户要求建立“开卡前前置概念层”机制——Phase 2 增 C1（回调/发布-订阅）+ C2（条件变量），Phase 3 增 C3（socket/TCP 生命周期）+ C4（HTTP 请求/响应模型），各 1.5h；Phase 2 5h→6.5h、Phase 3 7.5h→9h，总路线约 80h→约 83h。机制规则与课程地图见 `Phase2_3前置概念框架.md`（三层分流：迁移复用/前置概念块/卡内铁律21-22声明）。

**滚动校准规则**：每完成一个带实际用时记录的任务，即用其倍率复核同类任务的预算；同类任务实际倍率连续两次落在区间外时，按新均值整类调整。已完成任务一律使用实际用时，不再回改。

这次只调整**学习速度预算**，不恢复已经删除的低收益内容。Phase 2仍从未压缩版本7.5h控制到5h，Phase 3仍从8.5h控制到7.5h；压缩仍体现为学习深度差异：

- 与嵌入式 Linux 音视频直接相关的媒体对象、线程生命周期、socket、MJPEG、MP4 Range 保持 **L3**。
- 可迁移的 Linux 工程能力，如发布者线程回调、条件变量、原子保存和热更新边界保持 **L3**。
- 云 API 参数、base64 细节、JSON 字符串处理、SQLite CRUD、普通 JSON API 和前端实现只要求 **L1–L2**，能定位、复述输入输出并查文档使用即可。
- 节省时间优先回流到 Phase 1 的 packet/time_base/解码-JPEG链、Phase 1.5 的 H.264/RTSP/RTP，以及 Phase 6 的板端运行和性能证据；这些内容更能支撑音视频岗位追问。

## 3. 掌握度等级

| 等级 | 名称 | 验收标准 |
| --- | --- | --- |
| L0 | 未学 | 尚未建立输入、输出和位置概念 |
| L1 | 看懂 | 看着源码能指出主数据流和 public 接口 |
| L2 | 复述 | 不看代码能填输入/输出/状态表，画出调用链 |
| L3 | 推导 | 能回答 why、失败后果、边界和取舍，面对追问不靠背诵 |
| L4 | 验证 | 能做最小修改，完成静态复核，并在 Ubuntu/板端编译运行取得证据 |

模块标记“完成”至少需达到 **L3**。动手任务分“静态完成”和“板端验证”两个状态。

掌握证据采用自适应原则：口述、流程图、表格、源码追踪和变式回答均可等价证明理解。任务卡与百分比是诊断参考,不要求逐项补齐；Tutor可根据表现压缩或合并产出。关键数据流、状态、所有权、失败路径或技术选型因果仍错时不得推进。

#### Phase 1 单模块完成定义（DoD）

下面是模块完成时应覆盖的核心能力维度,不是要求每项都用单独表格重复提交；可由一段完整口述或源码追踪同时证明多项。不能以“AI讲过”或“看完源码”代替：

- 能用一句话说明模块在主数据流中的输入、输出和位置。
- 能闭卷列出主要函数，并指出流程组织函数和阶段边界函数。
- 能画出正常路径、至少一条失败/退出路径。
- 能追踪一个核心数据对象从进入到释放。
- 能指出关键状态由谁读、谁写，是否跨线程。
- 能回答至少 2 道“为什么这样设计 / 不这样会怎样”。
- 能在源码中重新定位支撑上述结论的关键代码行。

## 6. 每次会话的实时更新规则

### 开始时

1. 读 `progress.md`、`学习掌握档案.md` 和本路线。
2. 报告当前 ID、有证据的掌握等级、上次薄弱点和今日预算。
3. 按掌握档案中的复测队列做 1–2 道到期变式题，再开新任务。

### 进行时

1. 先画输入/输出/位置，再读 `.h`，最后读 `.c`。
2. 每个任务最多同时保留 3 个学习问题。
3. 未通过复述时不提高掌握等级。

### 结束时

1. 记录实际用时、最高掌握等级和验收结果。
2. Tutor可自主判定小任务状态；用户要求阶段总结时再执行学习审计，把代表性证据、关键错误和代码心智模型写入`学习掌握档案.md`。
3. 更新薄弱点、why 题状态和下一个任务 ID；`progress.md`只保留摘要，不能替代掌握证据。
4. 重新生成学习看板快照。
5. 代码修改分别标记“静态完成”和“板端验证”，不混为一项。

当用户说“本阶段/任务学习完毕，请结合学习聊天进行总结”或表达等价意图时，使用`nvr-learning-auditor`执行完整阶段审计。聊天中不可见的证据标记为“未验证”，不得依据Tutor讲过的内容自动升级等级。
