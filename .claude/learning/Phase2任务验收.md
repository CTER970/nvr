## 2.1 · AI线程、最新JPEG所有权与吞吐

源码：`frame_grabber.h:27-30`；`frame_grabber.c:155-165,185-202`；`cloud_ai.h:6-23`；`cloud_ai.c:243-330,376-383`；`main.c:136-175`  
时间盒：8分钟接口 + 12分钟对象/线程 + 5分钟纠偏 + 5分钟闭卷

### 最小脚手架

```text
拉流线程更新最新JPEG
→ AI线程取独立拷贝
→ 同步处理一帧并发布事件
→ AI线程free拷贝
```

### 重点与暂略

| 重点 | 暂略 |
| --- | --- |
| `g_jpeg`内部缓存与返回拷贝 | base64位运算 |
| malloc/借用/free责任 | curl选项 |
| 拉流、AI、主线程的边界 | JSON字段 |
| 生产节流、AI采样、云耗时 | SQLite/GPIO |

### 引导问题

1. `frame_grabber_get_jpeg(&jpeg)`返回内部指针还是独立拷贝？谁free？
2. `process_one_frame()`是所有JPEG还是借用JPEG？
3. 云请求耗时5s、`ai_fps=1`时，为什么实际周期不是1s？
4. 慢云请求会阻塞哪个线程？为什么不直接阻塞录像？
5. 当前有无AI任务队列？`ai_max_queue`是否真正被消费？
6. `web_mjpeg_fps`和`ai_fps`分别限制生产端还是消费端？

### 必交与通过

- 交三线程泳道图、JPEG所有权表、一个吞吐演算。
- 闭卷说清分配、借用、释放位置，并区分“最新帧采样”与“排队处理”。
- 能用线程证据解释为什么慢云端不直接拖住录像主路。

## 2.2 · JPEG到结构化事件：云请求与失败边界

源码：`cloud_ai.c:23-43,72-197,199-284`；`event_bus.h:8-16`  
时间盒：10分钟分块 + 10分钟请求/响应树 + 5分钟失败矩阵 + 5分钟闭卷

### 本遍目标

```text
JPEG字节 → base64 → 请求JSON → HTTP响应
→ choices.message.content → JSON子串 → event_t → 发布/丢弃
```

只读各助手函数的输入、输出、失败返回和释放路径，不背第三方API。

### 引导问题

1. `process_one_frame()`有哪些阶段？每阶段失败后还会发布吗？
2. 图片位于请求JSON的哪条路径？数据形态是什么？
3. curl失败、HTTP非200、响应结构不对、模型内容不是JSON，分别属于哪层？
4. `none`在`cloud_ai`还是`event_bus`中被过滤？其他发布者能否发布`none`？
5. `enable_thinking=false`是本项目目标端点的扩展参数，还是所有OpenAI兼容端点的必选字段？
6. 检查`b64/body/resp/model_text/json_str`的malloc/free是否在提前返回中配对。

### 必交与通过

- 交请求JSON树、六阶段数据形态表、分层失败矩阵、malloc/free清单。
- 能区分传输、HTTP、协议结构、业务语义四层失败。
- 不要求默写base64/curl/json-c实现。

### 预期状态表

| 旧enabled | 新enabled | 预期动作 |
| ---: | ---: | --- |
| 0 | 0 | 更新配置，不启线程 |
| 0 | 1 | start |

## 2.5 · Phase 2闭卷验收

时间盒：10分钟作图 + 10分钟口答 + 10分钟回证/纠错

### 必交产出

1. 拉流/抽帧、AI发布、报警、Web客户端四泳道图，每个箭头标数据、所有权和同步/异步。

3. 无JPEG、云HTTP失败、event_bus失败、GPIO禁用、Web失败五场景降级矩阵。
4. 30秒面试复述：一张JPEG如何形成事件、报警并在Web展示。

### 闭卷题

1. 为什么JPEG返回malloc拷贝？
2. 为什么慢云请求不阻塞录像，却降低AI实际采样率？
3. 为什么event_bus回调必须快返回，延时报警要放线程？
4. `none`在哪里过滤？是event_bus强制规则吗？
5. alarm回调和GPIO延时分别在哪个线程？
6. Web事件列表是推送还是查询？
7. DB成功、快照失败时系统怎样表现？
8. AI关闭时录像、预览、本地转发为什么仍可继续？

### 通过标准

- 图、表、降级矩阵均≥80%。
- JPEG拷贝、回调快返回、慢云端不阻塞录像三题必须全对。
- 必须区分同步发布/异步报警、报警订阅/Web查询。
- 能定位至少5处真实源码证据。

## 已复核的口径修正

- event_bus回调与发布者同线程、同步，但真实实现是解锁后回调；快返回是为了不阻塞AI发布线程。
- `none`只在`cloud_ai`过滤，不是event_bus对所有发布者的规则。
- `enable_thinking=false`是目标提供方扩展，不泛化为OpenAI兼容协议的必选字段。
- `ai_max_queue`当前未构成队列；快照清理只删JPEG，不同步删DB行。
- 热更新要以“消费者是否重新读取”判定；复制了新值不代表已生效。
