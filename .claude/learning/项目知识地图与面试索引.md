## 一、线程模型事实底座(已核实,2026-08-19)

| 线程 | 创建点 | 职责一句话 |
| --- | --- | --- |
| 主线程 | main | 初始化各模块、装 sigaction(SIGINT)后等待运行 |
| 拉流线程 receiver_thread | `stream_receiver.c:194` | 连接→读包→**同步三分发**(录像/抽帧/RTSP 转发) |
| Web 监听线程 web_thread | `web.c:1012` | accept 循环,SO_REUSEADDR |
| Web 客户端线程 client_thread | `web.c:994`(每连接一个) | 处理一个 HTTP 客户端(MJPEG 流式/Range/API) |
| RTSP 监听线程 listen_thread | `rtsp_server.c:574` | RTSP 信令+媒体转发 |
| AI 线程 ai_thread | `cloud_ai.c:328` | 取 JPEG→上云→发事件 |
| 报警线程 alarm_thread | `alarm.c:124` | 条件变量等待→GPIO 动作 |

信号:main.c:125-128 `sigaction(SIGINT)`(优雅停止入口)。

## 三、技术选型 why 清单(面试"为什么这么设计"弹药库)

| # | 选型 | 一句话答案骨架 | 状态 |
| --- | --- | --- | --- |
| 1 | 端/边/云三层 | 算力分层:端侧只编码,边侧汇聚存储,云端智能 | ✅已掌握 |
| 2 | 录像 remux 不转码 | IMX6ULL 无 H.264 硬解 VPU,转码 CPU 扛不住;remux 只重打时间戳 | ✅已掌握 |
| 3 | fMP4 | 提高中断后可恢复性(不保证零丢失);传统 MP4 断电丢 moov 全废 | ✅已掌握(谨慎表述) |
| 4 | 单线程同步三分发 | 省内存无队列、时序确定、录像主路顺序可控;消费者都够快 | ✅已掌握 |
| 5 | 关键帧起段/切段 | 非关键帧起头缺参考帧不可解码 | ✅已掌握 |
| 6 | 输出时基 1/90000 | 沿用 RTP/MP4 的 90kHz 传统;前提是输入也是 90kHz(未传 tb,脆弱假设) | ✅已掌握(含审计) |
| 7 | frame_grabber 只存最新帧 | 预览和 AI 都只要"现在",队列费内存且旧帧无价值 | ✅已掌握 |
| 8 | get_jpeg 返回 malloc 拷贝 | 锁保护一致性,拷贝隔离锁外生命周期 | ✅已掌握 |
| 9 | CLOCK_MONOTONIC 节流 | 墙钟会被 NTP/手动改,单调钟保证节流稳定 | ✅已掌握 |
| 10 | 浏览器预览用 MJPEG | 浏览器原生不播 RTSP;MJPEG 轻量兼容好 | 概念已建立 |
| 11 | 回放用 HTTP Range | 大文件分段拉取+拖动 seek;配合 MP4 索引 | 待 Phase 3 |
| 12 | 报警条件变量不轮询 | 事件驱动:延迟低不空转 CPU;while 防虚假唤醒 | 待 Phase 2 |
| 13 | 回调快返回+报警线程 | 回调在发布者线程同步执行,慢回调拖上游 | 待 Phase 2 |
| 14 | 原子保存 tmp+rename | 防"写一半"坏配置;rename 原子;fsync 保数据落盘 | 待 Phase 3 |
| 15 | 自研 RTSP server | 轻依赖、可控、贴合转发场景(讲法:理解协议而非黑盒) | 待 Phase 1.5 |
| 16 | MQTT 预留未实现 | 扩展性设计:结构留位,业务后补 | 概念 |

2. **Phase 6 整理骨架**:表三=选型话术清单、表四=基础挂靠自查、表五=弹药清点。
3. **面试前过一遍表四**:每行自问"能不能用项目里的代码答"。
