# P3-3.1 · HTTP 路由与 API 地图（60min，L1–L2）

> 时间盒 10min路由+10min数据源+5min表格+5min闭卷
> 前置：C4（HTTP 模型）必备；C3 建议

## 0. 开块审查

`grep -n "handle_client_inner\|serve_" web.c | head -30`；路由区实测 862-951（手册 840-930 已漂移）。

## 1. 任务目的（四层）

① 这是 Phase 3 的「地图卡」：先立全量 API 面，后面 MJPEG/Range/配置三张卡是在三个点上深钻——避免读 web.c 千行迷路。② 项目背景：自研 HTTP 服务器的路由=一串 strcmp/strncmp——让学生亲眼看到「框架的 Route 背后是什么」。③ 岗位背景：给陌生系统画 API 地图是入职第一课，也是「REST 理解」的项目化证据。④ 学完产出方法/路径/输入/输出/数据源表，3.2/3.3 直接按表索引。

## 2. 数据流坐标

链路 D 入口：`连接fd → client_thread → handle_client_inner（recv→解析请求行→分发）→ 11 个 serve_*`；POST 唯一入口 `/api/config`（2.4 已从 reload 侧看过，本卡从 HTTP 侧合拢）。

## 4. 卡内前置（铁律 21/22）

- 迁移：scandir/qsort（1.6C cleanup_disk 同族——这里升序 alphasort vs recorder 那边也是 alphasort，但录像要降序所以包了 strcmp_desc c:305-308）。
- 词源：`route`（路由=按路径分发）；`handler`（处理函数）；`query string`（?后的参数串）。

## 5. 引导问题（手册 5 问照用）

1. `/api/snapshot`、`/stream`、`/snap/<name>` 三者数据源有何不同？（当前帧拷贝 / 持续帧流 / 历史事件快照文件——「同一张 JPEG 的三个身份」）
2. `/api/events` 是推送还是查询？（2.3B 复收口）
3. `/rec/<name>` 的 Range 从哪个头取？（c:913-914 预取传入）
4. POST 只支持哪个 API？串起哪两个函数？（conf_save c:816+conf_apply_hot c:823）
5. 哪些是媒体输出、哪些是控制/状态面？（/stream+/rec+/snap=媒体；其余 JSON=控制面——媒体三链各自 L3 卡）

## 6. 产出与通过标准

全量 API 表（方法/路径/输入参数/成功输出/失败码/后端模块）；闭卷区分两条媒体链与通用 JSON API。通过=表完整+三张 JPEG 身份题答对。

## 7. 闭卷与变式（已过深度滤网）

- 闭卷：口述 handle_client_inner 五步（recv→请求行→头→体→分发）。
- V1（审计⑨）：请求头+体超过 4096B 会怎样？（头被截→解析乱/体丢——POST 大 JSON 风险；一句话+动手池）
- V2：为什么 POST 其它路径直接 404 而 GET 有静态兜底？（c:941-943 设计取舍一句话）

## 8. 预制时审计发现

⑨recv 一次 4096B 截断假设；serve_recordings 动态扩容注释自证「固定 8KB 会截断」的历史（c:313-314）——同类问题一个修了一个没修，好素材。
