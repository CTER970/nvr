## 1. 任务目的（四层）

① 2.3B 的 alarm 循环悬在「没事件时线程如何不空转、signal 丢了怎么办」上，不懂则 while 两个条件、停止延迟都读成轮询。② 项目背景：GPIO 拉高-延时必须放独立线程，回调里不能 sleep——C1 只回答了「快返回」，本块回答「延时动作放哪、怎么等」。③ 岗位背景：轮询 vs 等待/通知、丢失唤醒、while 不是 if，是嵌入式 Linux 应用岗高频三连问。④ 学完能默写等待循环骨架，2.3B 对着代码标两个谓词即可收口，不再讲一遍理论。

## 2. 词源与前置（铁律 21/22）

- **condition variable**（条件变量）：不存数据的「床位」；真正的条件在**谓词**变量里（这里是 `g_pending`）。cv 本身不记忆谁 signal 过。
- `pthread_cond_wait(&c,&m)` = 原子地【解锁 m + 睡眠】→被唤醒后【重新加锁】返回。`signal` 醒至少一个等待者，`broadcast` 醒全部。
- **spurious wakeup**（虚假唤醒）：OS 允许没人 signal 也醒 → 醒来必须重查谓词（这就是 while）。
- V4L2 桥：select/poll 阻塞等 fd 可读 vs 忙轮询 DQBUF——同是等待/通知。

## 3. 执行卡（短闭环，不是协议六阶段）

**① L1 观察（读完清单后，答案应在刚读的行上）**

- 没事件时，报警线程停在哪一行？是在循环里空转，还是在某个调用里睡着？
- on_event 里改了哪个变量之后才 signal？（`alarm.c:80-83`）

**② 最小模型（三件套，铁律 24）**

- 全面概念：等待/通知三件套 = 锁 + 条件变量 + 谓词循环。等待者睡在 cv 上，通知者改谓词后 signal。
- 项目结合：`while (g_running && g_pending==0) pthread_cond_wait`（`alarm.c:95-97`）；on_event 锁内置 pending 再 signal（c:80-83）；stop 也 signal（c:144-146）。
- 生动例子：取号叫号——睡在椅子上等叫号，不是每秒问「到我了没」；被叫后抬头**再看一眼屏幕** = while 重查谓词。

**③ 纸笔（只留一张图）**

画 wait/signal 时序（锁内改谓词 → signal → wait 返回仍持锁 → 取走清零 → 解锁 → 干活）。再故意画一版「if 谓词 + 先 signal 后 wait」让学生指出丢失唤醒窗口。

**④ 闭卷**

默写骨架：`lock → while 谓词 wait → 取数据清谓词 → unlock → 干活`，每步各一句为什么。

**⑤ 变式（只留一道主菜）**

- **V2（必过）**：为什么 cond_wait 必须拿着锁进、醒来自动拿回锁？（谓词检查与睡眠原子，否则「查完到睡下」窗口里 signal 恰好发生 → 丢失唤醒）
- 提升池（一句话，不问不讲）：多等待者才需要 broadcast；本项目单线程 signal 够用。glibc 底层 futex 不展开。g_pending 换成队列时骨架不变、谓词改成「队列非空」——留 2.3B。

**⑥ 重逢**：下一张 2.3A 仍是 publish；**2.3B 才对着 alarm_thread 逐行落地**。停止延迟双例（alarm ≤1s / cloud_ai 可达 30s）留 2.4。

## 5. 快问快答（收口用，4 题）

1. cv 里存了「事件」吗？（不；状态在谓词 `g_pending`）
2. 忘写 signal / 忘写 while 各怎样？（睡死；虚假唤醒或谓词被清后仍往下走）
3. signal 时没有等待者，通知去哪了？（消失——所以必须先改谓词再 signal，且都在锁内）
4. wait 返回时一定有事件吗？（不一定 → while）
