## 1. 任务目的（四层）

① alarm 的 GPIO 拉高-延时-复位必须放独立线程，而线程没事件时如何不空转？条件变量是答案，也是 2.3B/2.4 的读码地基。② 项目背景：报警线程等 `g_pending`，事件到来 signal 唤醒——网关五个线程里唯一的「等待/通知」结构，也是最常考的 pthread 原语。③ 岗位背景：轮询 vs 等待/通知、丢失唤醒、while 谓词三连问是嵌入式 Linux 应用岗高频题；与「中断下半部/tasklet」同构。④ 学完能独立读 alarm_thread 全循环并答 2.4 停止延迟对比。

## 2. 词源与前置（铁律 21/22）

- **condition variable**（条件变量）：不存数据的「床位」对象，配合锁使用；**谓词**（predicate）=真正表达条件的共享变量（这里是 `g_pending`）——cv 本身不记忆谁 signal 过。
- `pthread_cond_wait(&c,&m)` = 原子地【解锁 m + 睡眠】→被唤醒后【重新加锁】返回；`signal` 唤醒至少一个等待者，`broadcast` 唤醒全部。
- **spurious wakeup**（虚假唤醒）：OS 允许没人 signal 也醒——所以醒来必须重查谓词（这就是 while）。
- V4L2 桥：select/poll 阻塞等 fd 可读 vs 忙轮询 DQBUF——同是「等待/通知」，一个等内核事件、一个等用户态谓词。

## 3. 六阶段执行卡

**① 钩子（破坏式）**：报警线程没事件时在干什么？每 100ms 轮询 g_pending 的代价（CPU 唤醒/延迟颗粒）？signal 发生在 wait 之前，通知丢哪了（cv 不计数不记忆→丢；锁+谓词才救回来）？

**② 最小模型（三件套）**：
- 全面概念：等待/通知三件套=锁+条件变量+谓词循环；等待者睡在 cv 上，通知者改谓词后 signal。
- 项目结合：alarm_thread `while(g_running && g_pending==0) pthread_cond_wait`（alarm.c:95-97）；on_event 锁内置 g_pending 再 signal（c:80-83）；stop 也用 signal 唤醒退循环（c:144-146）。
- 生动例子：取号叫号（睡在椅子上等叫号，不是每秒问「到我了没」；被叫后抬头**再看一眼屏幕**=while 重查谓词——叫号可能是别人的）。

**③ 纸笔操作**：画 wait/signal 时序图；再故意画一版「if 谓词 + 先 signal 后 wait」让学生找丢失唤醒；while/if 两版对比（if 醒来不再查→虚假唤醒/被抢走后直接往下跑）。

**④ 闭卷重建**：默写 alarm 等待循环骨架（lock → while 谓词 wait → 取数据清谓词 → unlock → 干活）+ 每步为什么。

**⑤ 变式纠偏（已过深度滤网）**：
- V1：两个报警线程共用一个 cv，signal 只醒一个会怎样？什么时候必须 broadcast？（多类等待者/需要全醒时；本项目单线程 signal 够用）
- V2：为什么 cond_wait 必须拿着锁进、醒来自动拿回锁？（谓词检查与睡眠原子，否则「查完谓词到睡下」窗口里 signal 恰好发生→丢失唤醒）
- V3：把 g_pending 从 int 换成「事件队列」，等待循环骨架变吗？（结构不变，谓词=队列非空；本项目故意用单槽，见 2.3B）
- 提升池（一句话）：glibc 底层用 futex 实现，不展开。

**⑥ 重逢绑定**：2.3B alarm_thread 精读；2.4 停止延迟（stop 的 signal+join）；对照 stream_receiver 的阻塞读唤醒问题（Phase 1 V3 学过 AVIOInterruptCB 是标准解——本项目未用，同一家族）。

## 5. 快问快答（收口用）

1. cv 保存「事件」吗？（不；只做等待/唤醒，状态在谓词变量里）
2. 忘写 signal 会怎样？忘写 while 会怎样？（睡死；虚假唤醒/谓词又被清后仍往下走）
3. signal 时没有等待者，通知去哪了？（消失，无计数——所以必须先改谓词再 signal，且都在锁内）
4. wait 返回时一定有事件吗？（不一定→while）
5. on_event 里 signal 为什么必须发生在持锁期间？（与等待者的谓词检查互斥，防丢）
6. 轮询和条件变量各损失什么？（轮询耗 CPU+延迟颗粒；cv 需要锁纪律+易错）
