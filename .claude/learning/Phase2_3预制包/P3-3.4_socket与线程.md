# P3-3.4 · socket、accept 与客户端线程生命周期（75min，L3）

> 时间盒 10min启动+15min accept/线程+10min stop+10min异常审查（机动 30min）
> 前置：C3 必备（本卡=C3 的实现层落地）

## 0. 开块审查

`grep -n "web_start\|web_thread\|web_stop\|client_thread" web.c`（955-1028；手册 932-1005 已漂移）。main.c:161-163 启动、174 停机首站。

## 1. 任务目的（四层）

① C3 建了「总机/分机」模型，本卡逐行落地并审计四个真实缺口（异步启动/accept 错误吞吐/线程资源/停止语义）。② 项目背景：web 是停机顺序第一站（main.c:174）——为什么它先停？（MJPEG/Range 是最长连接，先掐输出面再停数据源，反向则 web 线程用到已释放模块=UAF 风险——与 Phase 1 停机顺序设计同族）。③ 岗位背景：socket 生命周期+线程模型是 Linux 应用必考；「start 返回 0 但端口没起来」这类异步失败是真实事故题。④ 学完交三泳道生命周期图，Phase 3 的传输底座闭合。

## 2. 数据流坐标

链路 D 传输底座：`main: web_start → web 线程：socket→bind→listen→accept 循环 → 每连接 client_thread(detach) → close(cfd) → web_stop: shutdown 监听 fd→join`。

## 4. 卡内前置（铁律 21/22）

- 迁移：fd=内核对象句柄（C3）；join 语义（2.4）；停机顺序设计（1.7A）。
- 词源：`shutdown(fd, SHUT_RDWR)`（切断 fd 上的读写，**阻塞中的 accept 立即出错返回**——与 close 的区别：close 只减引用计数，未必通知阻塞方）；`backlog`（监听队列长度）；`EINTR`（被信号打断的系统调用惯例返回值）。

## 5. 引导问题（手册 6 问照用）

1. web_start 与 web_thread 各负责什么？socket/bind/listen 在哪个线程发生？（启动管理 / 服务器主循环；全在 web 线程——异步于 start 返回）
2. accept 的 fd 交给谁？detach 后谁 close？（client_thread 自己）
3. web_stop 为什么先 shutdown/close 监听 fd 再 join？（否则 accept 阻塞永不醒，join 悬挂——对照 cloud_ai stop 无中断手段的 30s 延迟：**accept 有现成解，curl 没有**）
4. 每连接一线程：慢客户端隔离效果？大量客户端资源风险？（隔离佳；栈内存×N+调度开销——C3-V2 落地）
5. start 返 0 但 bind 失败，调用者能立即知道吗？g_running/g_listen_fd 收口吗？（不能；g_running 残留 1、g_listen_fd 残留 -1/未清——**审计**：下一次 stop 会 join 一个已退出的线程=无害但混乱，状态残留）
6. 怎么改造让 API 报告 bind 真实结果？（预置答案：bind/listen 挪到 web_start 同步做，或加「就绪信号」cond/管道回传——3.6 设计题素材）

## 6. 产出与通过标准

主线程/web 线程/客户端线程三泳道生命周期图（标两种 fd 生灭点、detach 后无 join、stop 的 shutdown 动作点）。通过=闭卷讲清「启动返回值≠已监听」+ shutdown 唤醒链。

## 7. 闭卷与变式（已过深度滤网）

- 闭卷：口述 web_thread 主循环+三种失败分支（accept<0/create失败/正常）。
- V1：把 accept 循环里的 `if (cfd<0) continue` 改成 `break`，行为变化？（一次瞬态错误（如 EINTR 被误当致命）就下线整个服务——错误分类意识：哪些可续哪些该退）
- V2：MJPEG 客户端连接中执行 web_stop，那个客户端线程会立即死吗？（不会——detach 线程不受 join 影响，跑到 send 失败/自身循环结束；g_running=0 会让 serve_mjpeg 循环退出——查 g_running 是共享标志。**潜在审计**：stop 后 client 线程可能还在用 g_cfg/调 frame_grabber，而停机顺序下一站 cloud_ai/receiver 已停——顺序敏感，一句话结论入池）
- 提升池（一句话）：epoll 单线程多路复用可去线程化，代价是状态机复杂度。

## 8. 预制时审计发现（核实后用）

异步启动失败不回传（c:975-978 vs 1003-1018）；accept 错误不分型全 continue（c:989-991）；stop 与残留 client 线程的模块使用竞态（V2——设计上靠「客户端先因 send 失败自然退出」兜底，不保证）。

## 9. 快问快答

1. 监听 fd 谁关？连接 fd 谁关？（web_stop / client_thread——各自终点）
2. detach 和 join 的选择依据？（一次性短任务 detach；需同步结束点才 join）
3. 为什么 web 是停机第一站？（长连接先停输出面，防下游先亡产生 UAF——让学生用 3.2 的 MJPEG 循环推）
4. SO_REUSEADDR 一句话？（TIME_WAIT 后立即可重绑，重启服务不卡端口）
