## 0. 开块审查

`grep -n "json_get_int\|new_cfg" web.c | head`（732-830 区域）；确认用户同意动码。

## 1. 任务目的（四层）

① Phase 3 的动手出口：把前三卡看到的缺口（越界值直通、掩码回写、大写降级）变成一次自己的防御性编码——简历「分析并验证」④后半的落点。② 项目背景：POST 链当前对端口 99999、fps=-3、quality=9999 照单全收——conf 层无校验、消费层各自容错，属于典型「信任边界缺失」。③ 岗位背景：输入校验+失败响应设计（400+可机读字段）是工程完成度信号；「校验放哪一层」是设计题。④ 学完 Phase 3 闭合，触发收口同步。

## 2. 动手任务（手册矩阵照用）

给 `POST /api/config` 加最小校验，覆盖：端口 1–65535（特权端口提示）/ `web_mjpeg_fps、ai_fps` 正值带上限 / `segment_seconds` 正值 / `ai_jpeg_quality` 1–100 / `alarm_min_confidence` 0–1 / 字符串长度+空值+token 掩码语义（"前8位+****" 形态拒绝）。

**实现骨架**：`serve_config_post` 解析后、`conf_save` 前插 `validate_conf(&new_cfg)` → 失败 `400 {"ok":false,"error":"<field>: <reason>"}`。改动集中一个 static 函数+一处调用，不碰 conf.c。

**代做选项（推荐，对齐 1.8）**：用户若把时间留给闭卷/面试，AI 写函数，学生独立答下面 4 问 + 测试矩阵即过。用户要自己写也可以，不卡在编译细节。

## 3. 验收问题（手册 4 问）

1. 校验应在写入 new_cfg 前、全部解析后、还是 conf_save 后？如何保证不部分应用？（全部解析后统一验——本实现 new_cfg 是栈副本，验证失败直接 400 返回，天然不部分应用；若在解析中逐字段验→部分覆盖已发生，语义脏）
2. 失败响应用什么码和字段？（400+字段级 error；对比 500=服务器自己的错 vs 400=客户端的错）
3. 字符串长度安全 ≠ 业务值合法——举例？（rtsp_transport 8 字节内但值 "banana" 语义非法；两层正交）
4. 怎么设计测试？（边界值 0/1/65535/65536、类型错误（字符串给 int 字段→atoi=0）、缺失字段、掩码串回传）

## 4. Phase 3 闭卷（收口）

- 必答：MJPEG 一帧的完整旅程（multipart 定界）/ 三个 Range 样例演算 / socket 三泳道+停机唤醒链 / 热更新边界三栏表。
- 三必对：Range 分层（传输 vs 内容索引）/ shutdown 唤醒 accept / 原子写+生效判定法。
- 现实边界 **任选 3 项**口述即可（短写 / Range 越界重置 0 / 异步启动失败 / 掩码回写 / 目录 fsync）。不要凑满五项拖时间。

## 5. 快问快答（收口）

1. 为什么校验函数吃 const 指针？（只判不改——签名自证意图）
2. 校验加在 web 层而不是 conf 层，理由？（conf_load 也要能读「历史遗留的怪值」宽容启动；Web 是不可信输入边界——分层信任一句话）
3. 掩码回传和端口越界，哪个危害更隐蔽？（掩码——静默换 token 掉线难排查 vs 端口立即可见）
